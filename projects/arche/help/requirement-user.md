需求用户 RequirementUser（格式版本 2）

定义：需求用户是为了产品设计研究而设定的假想使用者（persona），用来代表一类人
的处境、目标和行为，帮助研究怎样更好地进行产品设计。它不是真实人物，也不是系统
账号；禁止把真实人物的姓名、年龄、身份、联系方式或其他个人信息写进需求用户。
用户的所有字段都是设计假设，不是采集到的个人数据。

创建：

  arche create requirement-user <role-id> --display-name <假想角色姓名>

修改：

  arche update <user-qname> --display-name <假想角色姓名>
  arche update <user-qname> --age <年龄> --occupation <角色/职位> \
    --priority <core|primary|secondary|peripheral>
  arche update <user-qname> \
    --situation "<处境/困难>" \
    --hobby "<爱好>" \
    --need "<用户目标>" \
    --story <故事-qname>

`arche update` 接受与 `arche create` 相同的字段参数，并且只修改传入的字段：

- display_name、age、occupation、priority 替换原值；
- situation、hobby、need 追加到对应列表；
- story 替换 stories 引用列表。

一次写入全部字段：

  arche create requirement-user <role-id> \
    --display-name <假想角色姓名> \
    --age <年龄> \
    --occupation <角色/职位> \
    --priority <core|primary|secondary|peripheral> \
    --situation "<处境/困难>" \
    --situation "<另一个处境>" \
    --hobby "<爱好>" \
    --need "<用户目标>" \
    --need "<另一个用户目标>" \
    --story <故事-qname>

`--situation`、`--hobby`、`--need`、`--story` 可以重复传入；不需要的字段省略。

批量创建多个用户：

  arche batch users.json

  {
    "objects": [
      {
        "kind": "requirement-user",
        "name": "warehouse-admin",
        "display_name": "张三",
        "age": "30",
        "occupation": "仓管员",
        "priority": "core",
        "situations": ["负责仓库日常收货"],
        "needs": ["希望快速完成收货登记", "希望及时看到库存变化"]
      }
    ]
  }

qname 为 `requirement/user/<role-id>`。`name`（`<role-id>`）由智能体按用户角色
命名，例如 `project-sponsor`、`warehouse-admin`，不能是随机 key；qname 中不写
角色姓名。

用户设计原则（先划分用户，再设计人物）：

  1. 产品中处于不同角色的人是不同的用户。角色职能不同，权限、目标和行为天然
     不同，不能合并成一个用户。
     例：系统普通用户和系统管理员；仓库管理员和快递员。

  2. 同一角色的用户，如果偏好或状况的差异会导致对产品有意义的差异化行为，也是
     不同的用户。
     例：同样是普通客户，学生资金相对不充裕，更倾向于对比多种同类商品、寻找
     优惠券；公司职员更倾向于尽快完成交易。两者的浏览、决策和下单行为不同，
     应建成两个用户。
     反例：两个人的差异只体现在姓名、年龄上，行为和对产品的需求没有有意义的
     差别，不应拆成两个用户。

对每一个用户类型设计一个用户，并根据该类型的特征设计人物：姓名、年龄、职业、
处境、爱好和需求都要体现这一类型的差异。根据产品定位为每一个用户标定优先级：
core（核心用户）、primary（主要用户）、secondary（次要用户）、peripheral
（边缘用户）。优先级用于指导故事和交互设计：核心用户的需求优先满足，核心用户
的操作路径尽量短。

人物设定约束：

- 用户是假想角色，用于研究“这类人需要什么、会怎样使用产品”，不是真实用户档案；
- 姓名、年龄、职业、爱好都是为推演设计而设的假设，应当合理设定并保持自洽，
  不要求来自真实资料；
- 禁止使用真实人物的姓名、年龄、身份、联系方式或其他可识别信息；
- 一个用户代表一类使用者，不要把差异很大的多类人塞进同一个用户。

字段写作说明（统一格式）：

  含义  这个字段回答什么问题。
  写法  内容粒度、顺序、语气和格式要求。
  正例  可以直接对照采用的例子。
  反例  常见错误，出现即应改写。
  约束  与其他字段、对象或检查的关系。

display_name  String
  含义：假想角色的姓名或代称，用于页面展示和故事引用。
  写法：给假想角色起一个自然、稳定的人名或代称，以 2～4 个字为主；同一项目内
        保持唯一。它是人物称呼，不是角色描述，也不得指向真实人物。
  正例：张三；李娜；王芳（均为虚构代称）。
  反例：平台管理员；受邀管理员；warehouse-admin；用户1；某位真实同事的姓名。
  约束：角色、职位或用户类型写到 occupation；name 是角色 id；禁止使用真实人物
        的姓名或其他可识别信息。

age  String
  含义：假想角色的年龄或年龄段，用于推演使用场景和界面适配。
  写法：根据角色的职业、资历和处境，设定一个合理年龄或年龄段，作为设计假设；
        同一角色的年龄、职业、资历和处境要自洽。该字段不要求也不允许来自真实
        人物资料。
  正例：30；28；35-40 岁。
  反例：中年（无法用于推演）；某位真实人物的年龄；unknown；为了填字段随手写 1。
  约束：与 occupation 的资历、situations 中的工作年限一致；如果年龄对设计没有
        影响，可以省略该字段，而不是编造真实资料。

occupation  String
  含义：用户在组织中的角色、职位或身份，决定其权限和关注点。
  写法：用用户能听懂的职位名，或“组织 + 角色”；一个用户写一个主要身份，多重身份
        概括成一句话。
  正例：平台管理员；仓库收货员；产品经理；车间班组长。
  反例：张三；普通用户；管理员（脱离业务场景太泛）。
  约束：与 situations 的工作处境一致，与故事中的操作权限一致；角色职能与已有
        用户不同时，应新建用户，不能并入已有用户。

situations  DocumentList
  含义：用户在真实工作中所处的状况、限制或面临的困难。
  写法：每条写一个具体场景，交代人物或组织背景、当前做法、痛点或限制；只写“处境”，
        不写任务、功能、流程步骤，也不写系统应该做什么。
  正例：
    - 罗大虎有一家自己的公司，需要开发一款 APP，但他不是专业的开发人员，无法
      自己进行开发，雇人开发成本又太高。
    - 张三负责软件开发工作。他擅长软件设计，但传统开发方式使他不得不花大量时间
      在代码编写上，无法集中力量进行设计工作。
    - 张小梅负责产品设计，她经常有一些不错的产品方面的创意，但由于软件开发成本
      太高，无法快速尝试。
  反例（这些是任务、功能或检查项，不是处境）：
    - 平台管理员：首次部署时建立账户。
    - 登记智能体与版本并评测。
    - 核对平台自举进度。
  约束：needs 应针对这些处境提出目标；故事应能体现这些处境。

hobbies  DocumentList
  含义：用户的爱好、习惯或使用偏好，用于解释交互和界面选择。
  写法：每条写一个具体爱好或稳定习惯，优先写会造成产品行为差异的偏好；与产品
        使用无关时可以省略；不写性格评价和空泛描述。
  正例：习惯用手机处理日常工作；喜欢先用纸质单据勾选，再集中录入系统。
  反例：性格开朗；喜欢好东西；无；等等。
  约束：写了就要能在故事或交互的 ui 中找到对应体现，否则删除。

needs  DocumentList
  含义：用户希望达成的目标，即用户对系统的需求。
  写法：用用户视角写“希望……”，每条一个可被故事满足的目标；写结果和感受，不写
        功能名、实现方式、操作步骤或验收清单。
  正例：
    - 希望让系统帮助完成其他环节，自己专心负责设计环节。
    - 希望通过模糊的描述软件的定位，让系统自动完成开发。
    - 希望得到软件之后，通过试用反馈，让系统继续改进软件。
    - 希望把项目的权限管理起来，只允许自己批准的其他用户能够加入项目。
  反例（这些是任务或实现要求，不是用户目标）：
    - 显式建立账户与全局角色，不依赖默认账户。
    - 平台是否可用由平台自身的研发记录判断，并逐项核对。
  约束：每条 needs 必须被该用户参与的一组故事完备覆盖。这些故事要在 requirement
        中写入对应条目，并共同解决满足需求过程中的问题（信息不足、缺货、失败、
        取消、超时、不满意、退货、售后等）；通常不能只靠一个故事覆盖整条需求。

priority  优先级
  含义：用户对产品的重要程度。优先级不是排序标签，而是故事设计和交互设计的依据：
        核心用户的需求优先满足，并且尽量让核心用户的操作路径更短。
  写法：根据产品定位为每一个用户标定一个级别：

        core         核心用户
        primary      主要用户
        secondary    次要用户
        peripheral   边缘用户

        命令接受英文名和中文名，例如 --priority core 或 --priority 核心用户。
  正例：core；primary；secondary；peripheral。
  反例：高；P0；很重要；随意分级。
  约束：同一项目内每个用户都必须有明确级别。设计故事和交互时必须使用这个依据：
        - 故事设计：优先安排核心用户的需求，核心用户的故事优先形成完整闭环；
        - 交互设计：核心用户完成关键任务的路径最短，步骤、页面跳转和等待最少；
          次要用户和边缘用户可以使用更长路径或更低频的入口。

优先级的使用：

  1. 先看故事的主角是谁。主角是 core 用户的故事优先设计，优先级高于 primary、
     secondary、peripheral 用户的故事。
  2. core 用户的关键任务要有一条最短路径：步骤最少、跳转最少、必要操作前置；
     不要为了覆盖低频场景而把核心路径变长。
  3. 同样的功能，如果 core 用户和边缘用户都要用，优先保证 core 用户的路径；
     边缘用户可以通过次级入口、批量操作或低频页面完成。
  4. 评审时检查：core 用户的需求是否有故事优先覆盖，core 用户的关键交互是否
     确实比其他人更短，而不是只给用户标了一个级别却没有影响设计。

stories  Vec<SymbolHash>
  含义：与该用户关联的故事，用于页面跳转和完整性检查。
  写法：只列真正包含该用户的故事 qname；通常先写故事的 users，再回填这里，保持双向
        一致。
  正例：
    arche update requirement/user/warehouse-admin \
      --story requirement/story/receive-goods \
      --story requirement/story/adjust-stock
  反例：列出用户没有参与的故事；把功能或模块 qname 写进 stories。
  约束：覆盖该用户每条 needs 所需的全部故事都必须出现在这里；与 story.users
        双向一致。arche check 校验故事侧的 users，不会自动回填这里，需要人工
        保持一致。

与故事的完整性：

一个需求通常需要一组故事共同满足，而不是一个故事对应一条 needs。覆盖同一需求的
故事集合必须完备并形成闭环，解决满足需求过程中可能出现的各种问题。

逐条 needs 检查：

  1. 列出包含该用户的全部故事；
  2. 在每个故事的 requirement 中找该 needs 的对应条目，没有就补；
  3. 检查故事集合是否覆盖：
     - 正常完成路径；
     - 需求发生前的问题：信息不足、不了解选项、资格或权限不足、前置条件不满足；
     - 需求进行中的问题：缺货、失败、取消、超时、重复提交、并发冲突、外部依赖
       失败、操作错误；
     - 需求完成后的后续问题：不满意、退货、退款、投诉、售后、撤销、再次使用；
  4. 检查每个问题是否有结果和恢复方式，故事之间是否闭环；
  5. 缺哪类问题就补故事；一个故事无法覆盖整条需求时，必须联合其他故事。

例：用户的“购物”需求不能只由“购买商品”故事满足。还需要“浏览商品”“与卖家
沟通”解决信息不足，“预购/缺货登记”解决缺货，“退货/退款”解决不满意；这些
故事联合起来，才算完备覆盖“购物”需求。

检查：

  arche show requirement/user/<role-id>
  arche check
