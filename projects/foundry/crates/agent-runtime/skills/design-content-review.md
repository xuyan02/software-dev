# 设计内容评审技能

内容评审不要只找设计错误。你同时负责：

- 设计内容是否正确、完整、可理解；
- 文档格式、块序列、必填块和顺序是否符合 `design-writing`；
- 技术设计 Section 层级是否与结构树一致，`ds doc check` 是否通过；
- 术语是否清楚、一致、不混淆；
- 高复杂度部分是否有专门说明；
- 设计、代码、需求之间是否一致；
- 接口、边界、依赖、状态/生命周期、数据/存储结构、并发/调度、错误/失败语义、部署/运行约束等关键细节是否覆盖。

审查时重点关注设计要点：它是设计文档的核心，必须覆盖无法自然推定、需要说明的设计内容，达到“根据文档本身就可以完全理解设计，并决定怎么写代码”的程度。

你仍然不修改正文、不替作者做设计，也不替作者决定设计取舍。

## 1. 规范违反：直接说明

适用：

- 块缺失、块顺序不对；
- Method/Function 缺少“参数”或“返回值”块，或参数/返回值缺少含义、失败语义；类型由“函数原型”表达，不要求重复；
- 设计原则空泛、不可判定（例如“遵循 SOLID”“高内聚低耦合”），或不是一条简短、可判定的设计规范；
- 设计原则 Section/块混入定位、职责、非职责、功能、非功能、不变量、约束、对外依赖、设计要点、用法或其他块；
- 把单个成员或函数的职责、不变量、约束或实现策略写成设计原则；
- 专业词汇没有概念定义或概念引用，或 `[[concept:...]]` 引用无法解析到 Concept 对象；
- 章节层级不符合结构；
- `ds doc check` 失败；
- 必填内容缺失；
- 文档结构、命名或格式不符合规范；
- 设计文档写进实现细节、成员清单等禁止内容。

反馈格式：位置 + 违反的规则 + 证据/通过条件。不需要写成问题，也不要替作者改写正文或给修改方案。

示例：

```text
documents/design/technical/section1 的块顺序是“定位 → 设计要点 → 职责”，
不符合 design-writing 的“定位 → 职责 → 非职责 → 功能 → 非功能 → 不变量 → 约束 → 设计原则 → 对外依赖 → 用法 → 设计要点”。
```

```text
ds doc check 失败：documents/design/technical/section2/section1 的父级
应为 .../section1，当前不是。
```

## 2. 需要作者判断的设计缺口：以问题反馈

适用：

- 术语不易理解、前后不一致、未定义；
- 名称与定位或职责不一致，名字需要正文解释才能理解；
- 常见术语被挪用于偏离其惯常含义的地方，例如用“数据库”指缓存或任意文件集合；
- 同一对象有多个名字，或不同对象共用一个名字；
- 任何看不懂、有歧义、容易误解的表述；必须提出质疑，不要自行补全作者意图；
- 需要知道但文档没写的信息；
- 文档内部、文档之间相互矛盾；
- 高复杂度部分没有专门说明；
- 设计原则放置的位置无法确定其适用范围，或原则之间、原则与局部设计之间相互矛盾；
- 概念定义不清、缺少特征或关系/区别，导致文档中的术语仍有歧义；
- 设计意图无法从文档判断。

每个问题必须包含：位置、原文/现象、为什么不理解或为什么矛盾、需要作者说明什么。不写“应该改成……”“建议补充……”。

示例：

```text
documents/design/technical/section1/section1 说认证失败会重试，但没有说明
重试上限和最终失败后的行为；这两种情况分别是什么？
```

```text
同一节里 token 和 credential 交替使用；它们是指同一个东西，还是两个
不同概念？如果是两个，区别是什么？
```

```text
这里引用了 Session 的生命周期，但文档没有定义它从创建到失效的状态；
能否说明这些状态和转换？
```

## 3. 设计与代码不一致：给证据，问应然设计

适用：

- 文档描述和代码行为不一致；
- 文档有对象但代码没有，或反之；
- 文档和需求/架构不一致。

反馈要写清文档 qname、代码位置/提交和差异，然后问哪一边是应然设计，不直接判断“改代码”或“改设计”。

示例：

```text
文档 documents/design/technical/section1/section1 写“认证失败返回 401”，
代码 src/auth.rs:120 返回 403。哪一个是应然设计？
```

## 4. 通用要求

- 一条反馈只写一个问题或一个规范违反；
- 必须可定位：文档 qname、章节或原文；设计-代码问题还要给代码位置；
- 不重复已有评论；作者已经解释或修改的，确认后 resolve；
- 不修改正文，不做设计决定，不直接给修改方案；
- 纯语言和表达问题交给 style reviewer。

## 5. 设计草案

审查 `documents/design/drafts/<draft-id>` 时，按 `design-draft` 检查：

- 章节骨架是否完整，顺序是否正确；
- 草案是否使用自己的 ID 和名字，Issue 只在背景中引用；
- 设计要点是否覆盖本次设计的关键机制和所有可能产生疑问的内容；
- 设计要点是否逐点写清设计决定、不变量/约束、正常/异常路径、交互和容易误解之处；
- 方案选择是否只在确实存在多个可行方向时出现，且只写思路、取舍和选择原因；
- 是否没有验收标准、待定问题和开放问题；
- 目标设计、设计要点和实施计划是否足以直接指导 apply。

缺少设计要点，或设计要点只写泛泛的“实现细节”“注意事项”，直接打回。
