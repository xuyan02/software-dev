# 交互设计审查技能

## 目标

审查需求文档的「交互设计」章节是否完整、可用，并与需求、故事和功能一致。

交互设计必须与需求文档的子系统结构一一对应：子系统 → 功能集 → 功能，名称完全一致；交互视角额外检查信息架构、页面清单和用户操作。

只审查，不修改文档，不审批或发布。

## 审查前必须读取

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
6. `document`，`action = "toc"`，`kind = "requirements"` 读取需求结构和交互设计的锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取已有批注。
8. `task_allowed_operations` 确认当前允许的操作。

内容规则以《需求文档写作说明书》的「交互设计」一节为准。

## 审查方法

先建立覆盖矩阵：

```text
需求：子系统 → 功能集 → 功能
交互：子系统 → 功能集 → 功能
```

逐层对照名称，再检查每一层的内容。

### 1. 覆盖与名称

- 需求文档中的每个子系统、功能集、功能是否都有同名交互节点？
- 是否有交互节点在需求文档中找不到来源？
- 名称是否完全一致，没有改写、合并或拆分？

### 2. 子系统

- 是否有交互概述？
- `信息架构` 是否说明导航层级、区域划分和页面关系？
- `页面清单` 是否覆盖该子系统涉及的全部页面？
- 每个页面是否写清区域、入口、主要跳转和支撑功能？
- 是否把页面细节写进了功能，导致页面清单不完整？

### 3. 功能集

- 是否写清共享页面、共享区域、统一入口、共同状态和跨功能连续操作？
- 是否写成了功能列表或概念清单？
- 交互上下文是否与下属功能一致？

### 4. 功能

- 用户发起的功能：是否有触发、入口和操作？
- 系统发起的功能：是否有触发条件和用户观察点？是否硬写了不存在的操作？
- `页面结构` 是否只引用页面清单中的页面？是否说明层级和跳转？
- `操作` 是否写清操作、控件和结果？
- `反馈与状态` 是否覆盖加载、成功、失败、空、确认、撤销和错误提示？
- `文案` 是否给出按钮、提示和错误文案的关键内容？
- `无障碍` 是否覆盖键盘、焦点、读屏和触控的具体要求？

### 5. 一致性与成本

- 交互设计与功能、故事和反馈是否矛盾？
- 页面名称、控件名称和状态名称是否前后一致？
- 是否重复需求文档的系统变化、前置条件或业务规则？
- 是否混入视觉样式、颜色、字体、图片、设计 token 或技术实现？
- 正常路径是否有不必要的步骤、确认或跳转？
- 出错后是否要求用户重做已完成步骤？

## 逻辑推演

### 场景推演

把每个功能当成一次真实操作，从头走到尾：

1. 用户从哪里进入？
2. 每一步看到什么页面和控件？
3. 出错时怎么知道、怎么恢复？
4. 成功后怎么确认？
5. 用户能否取消或返回？

### 状态推演

- 默认、加载、空、错误、成功状态是否覆盖？
- 控件在不可用、必填、超限时行为是否清楚？
- 状态之间是否能走通？

### 页面推演

- 功能引用的页面是否都在页面清单里？
- 页面清单里的页面是否都有支撑功能？
- 页面之间的跳转是否双向可达，是否有死路？

## 输出

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：toc 中问题所在的交互设计锚点。
- `quote`：引用原文。
- `body`：具体缺陷、规则依据、修改建议和通过条件。

只写必须修改的问题；只要写了标注，就必须拒绝。每条标注必须能写清通过条件。已解决或不影响结论的问题不重复报。

提交结论：

- 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `rejected` 操作名。
- 一条标注都没写时，才调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `approved` 操作名。

## 不要做的事

- 不修改文档。
- 不审查需求分析内容或 UI 设计。
- 不写建议性、非阻塞标注。
- 不在写了标注后仍然通过。
- 不审批、不发布。
