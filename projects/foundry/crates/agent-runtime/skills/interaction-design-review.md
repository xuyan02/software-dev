# 交互设计审查技能

## 目标

审查每个功能的交互设计是否完整、可用、与需求和故事一致。只审查，不修改文档，不审批或发布。

## 审查前必须读取

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
6. `document`，`action = "toc"`，`kind = "requirements"` 读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取已有批注。
8. `task_allowed_operations` 确认当前允许的操作。

## 检查什么

对每个功能：

- 是否有一行 `交互设计：`，且只有一行？
- 是否覆盖页面结构、控件、用户操作、反馈与状态、文案、无障碍？
- 用户能否从进入功能走到完成或放弃？
- 加载、成功、失败、空状态是否都有交代？
- 反馈的信息内容是否与功能的“反馈”一致？
- 是否与故事的操作顺序、错误处理和成功确认一致？
- 是否混入业务规则、系统结果、状态变化明细、数据影响、异常结果或权限？
- 是否混入视觉样式、颜色、字体、间距、图标、图片或设计 token？
- 是否把细粒度交互拆成多个字段或标题？
- 是否混入技术实现、接口、数据库或算法？

## 逻辑推演

### 1. 场景推演

把交互设计当成一次真实操作，从头走到尾：

1. 用户从哪里进入？
2. 每一步看到什么页面、什么控件？
3. 每一步是否知道要做什么？
4. 出错时怎么知道、怎么恢复？
5. 成功后怎么确认？
6. 用户能否取消或返回？

### 2. 状态推演

对页面和控件问：

- 默认态、加载态、空态、错误态、成功态是否覆盖？
- 控件在不可用、必填、超限时行为是否清楚？
- 状态之间是否能走通，是否有无法离开的状态？

### 3. 矛盾检测

- 交互设计与功能描述是否矛盾？
- 交互设计与故事的操作顺序是否矛盾？
- 反馈信息与功能的“反馈”是否矛盾？
- 页面结构与控件描述是否自相矛盾？
- 是否引入了需求中没有的新功能或新规则？

### 4. 成本推演

- 正常路径是否有不必要的步骤、确认或跳转？
- 是否要求用户重复录入系统已有的数据？
- 出错后是否要求重做已完成步骤？
- 高频故事的交互是否足够直接？

## 输出

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：功能锚点；交互设计写在功能正文的 `交互设计：` 行里。
- `quote`：引用原文。
- `body`：具体缺陷 + 规则依据 + 修改建议 + 通过条件。

只写必须修改的问题；只要写了标注，就必须拒绝。每条标注必须能写清通过条件。已解决或不影响结论的问题不重复报。

**必须修改的问题**：

- 功能缺少交互设计。
- 用户无法完成故事，或存在无法走通的状态。
- 交互设计与功能、故事或反馈矛盾。
- 混入业务规则、系统结果、视觉样式或技术实现。
- 把细粒度交互拆成多个交互项。
- 高频故事存在明显不合理的操作成本。

**不要写非阻塞标注**：

- 可以更简洁、更顺滑但不影响完成。
- 控件或文案可以优化。
- 等价写法或位置调整。
- 个人偏好或建议性补充。

## 审查收敛规则

1. 只写必须修改的问题；每条标注写清通过条件。
2. 已解决的问题不重复提。
3. 不值得拒绝的问题不写标注。
4. 多轮审查只检查上次标注项。
5. 人类决策项写明决策人和所需决定，不反复拒绝。
6. 只要写了标注就拒绝，没有标注才通过。

## 流程

1. 读取输入。
2. 对每个功能做场景推演、状态推演、矛盾检测和成本推演。
3. 汇总必须修改的问题；不值得拒绝的不写标注。
4. 写锚点批注。
5. 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "rejected"`。
6. 一条标注都没写时，才调用 `task_operation`，`operation = "approved"`。
7. 不修改文档，不审批，不发布。
