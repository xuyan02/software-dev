# UI 设计审查技能

## 目标

审查每个功能的 UI 设计是否完整、与交互设计一致。UI 设计只由图片列表组成；只审查，不修改文档，不审批或发布。

## 审查前必须读取

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
5. `document`，`action = "toc"`，`kind = "requirements"` 读取目录和锚点。
6. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取已有批注。
7. `task_allowed_operations` 确认当前允许的操作。

## 检查什么

对每个功能：

- 是否有 UI 设计图片列表？
- 图片顺序是否与交互设计描述的顺序一致？
- 图片是否覆盖交互设计中的页面和关键状态？
- 每个图片项的标题是否就是图片名称。
- 每项是否按 `名称：`、`链接：` 两行写？
- 是否混入动画、动图、帧序列或动画说明？
- 是否混入颜色、字体、字号、间距、圆角等视觉规范文字？
- 是否混入页面结构、控件行为、交互逻辑、业务规则或技术实现？
- 是否用“见设计稿”代替了具体图片？
- 图片与交互设计是否矛盾，例如缺少某个页面或状态？

## 逻辑推演

### 1. 顺序推演

按交互设计的顺序逐个页面和状态检查：

- 第一张图对应第一个页面或状态吗？
- 顺序是否连续？
- 是否有页面或状态没有图？
- 是否有多余的图不对应任何页面或状态？

### 2. 覆盖推演

对交互设计中的每个页面和关键状态问：

- 默认态有图吗？
- 加载、空、错误、成功状态有图吗？
- 跳转后的页面有图吗？

### 3. 矛盾检测

- 图片列表与交互设计的页面、控件和状态是否矛盾？
- 图片引用是否指向不存在的资产或链接？
- 是否引入了交互设计中没有的新页面或新状态？

## 输出

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：图片项或所属功能的锚点。
- `quote`：引用原文。
- `body`：具体缺陷 + 规则依据 + 修改建议 + 通过条件。

只写必须修改的问题；只要写了标注，就必须拒绝。每条标注必须能写清通过条件。已解决或不影响结论的问题不重复报。

**必须修改的问题**：

- 功能缺少 UI 设计图片列表。
- 图片顺序与交互设计不一致。
- 关键页面或状态缺少图片。
- 图片列表与交互设计矛盾。
- 混入动画或文字视觉规范。
- 只有“见设计稿”而没有具体图片。

**不要写非阻塞标注**：

- 图片名称或说明可以更清楚。
- 可以补充非关键状态的图片。
- 等价写法或位置调整。
- 个人偏好或建议性补充。

## 审查收敛规则

1. 只写必须修改的问题；每条标注写清通过条件。
2. 已解决的问题不重复提。
3. 不值得拒绝的问题不写标注。
4. 多轮审查只检查上次标注项。
5. 人类决策项写明决策人和所需决定，不反复拒绝。
6. 只要写了标注就拒绝，没有标注才通过。

## 流程

1. 读取输入。
2. 对每个功能做顺序推演、覆盖推演和矛盾检测。
3. 汇总必须修改的问题；不值得拒绝的不写标注。
4. 写锚点批注。
5. 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "rejected"`。
6. 一条标注都没写时，才调用 `task_operation`，`operation = "approved"`。
7. 不修改文档，不审批，不发布。
