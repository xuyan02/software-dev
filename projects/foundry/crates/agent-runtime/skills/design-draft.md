# 设计草案撰写技能

本技能只说明设计草案怎么写；设计文档本身的块规则见 `design-writing`。

设计草案用于 `design`：先把根源性的设计修改写成一份完整、可实施的设计，
由智能体和人类 review，通过后再按草案修改设计空间。

草案不是设计建议，必须拿出一个完整设计，保证可行并解决问题。

## 1. 位置、ID 和名字

```text
文档 qname：documents/design/drafts/<draft-id>
文档标题：设计草案：<draft-name>
```

- `<draft-id>` 是草案自己的稳定 ID，创建时生成，例如 `draft-7f3a2c9e`，在 drafts 目录下唯一；
- `<draft-name>` 是人类可读名字，写在 Document 标题里；
- Issue 不进入 ID 或名字，只在“背景”中引用。

## 2. 章节骨架

按顺序创建顶层 Section；只有标“可选”的可以省略。

```markdown
# 背景

- Issue：[[issue:<issue-id>|<issue-title>]]
- 触发原因：
- 本次设计要解决的问题：
- 目标：
- 非目标：

# 现状设计

- 相关 System / Module / 元素 / 文档：
  - [[ds:<qname>|<name>]]
- 当前职责和边界：
- 当前接口和契约：
- 当前数据、状态和生命周期：
- 当前依赖方向：
- 当前设计与代码 / 需求不一致的地方：

# 问题与根因

- 问题现象：
- 根因：
- 为什么现有设计无法解决：
- 影响范围和风险：

# 方案选择（可选）

仅当确实存在多个可行方向时写；只写思路、取舍和选择原因，不展开候选详细设计。

- 方向 A：一句话思路；优点 / 代价
- 方向 B：一句话思路；优点 / 代价
- 选择本方案的原因：

# 目标设计

- 目标 System / Module / 元素结构：
- 职责和边界：
- 与现有设计的关系：
- 明确的非目标：

# 设计要点

本次设计最关键的部分。按具体要点拆成 topic，每个 topic 标题写清要点名，
例如“会话状态转换”“认证接口继承体系”“令牌存储格式”“并发刷新顺序”。

每个设计要点至少写清：

- 设计决定是什么；
- 不变量、约束和边界；
- 正常路径、异常路径、失败/恢复语义；
- 与其他对象、流程或外部系统的交互；
- 容易误解或需要特别说明的地方；
- 必要的示例（用文字或列表，不写代码）。

以下清单用于自检；与本次设计相关的项不能省略：

- 状态机 / 生命周期：状态集合、事件、转换、非法转换、持久化与恢复；
- 对象 / 接口继承体系：类型层次、继承/实现关系、扩展点、覆盖规则、兼容性；
- 参数设计：含义、单位、默认值、取值范围、校验、错误语义；类型选择或类型变更的理由；
- 数据格式：字段、类型、编码、版本、缺省值、兼容和演进；
- 存储格式：表/键/值结构、序列化、索引、事务边界、迁移和保留策略；
- 流程设计：步骤、分支、异常、重试、超时、幂等、顺序；
- 并发安全：锁、事务、访问顺序、竞态、死锁、幂等和重入；
- 原则 / 语义调整：术语变化、不变量、边界条件、错误语义、兼容承诺；
- 接口 / 协议契约：调用方可以依赖什么，实现方必须保证什么；
- 依赖和调用方向：谁依赖谁、为什么、是否允许反向依赖；
- 失败 / 降级 / 恢复：哪些失败可重试、哪些必须中止、如何恢复；
- 配置 / 部署 / 运行约束：配置来源、默认值、环境差异、启动顺序；
- 权限 / 安全：谁能做什么、认证授权边界、敏感数据；
- 性能 / 容量：关键路径、上限、降级点、观测方式；
- 兼容 / 迁移：旧数据、旧接口、旧行为如何过渡；
- 其他任何可能导致疑问和误解的设计内容。

写作规则：

- 不能写“同上”“见代码”“显而易见”“按现有实现”；
- 如果读者必须看代码才能理解，就必须写进设计要点；
- 只有真正不言而喻的内容才可以省略；
- 不写代码、伪代码或逐行实现；
- 接口可以写成契约文字；
- 高复杂度要点必须单独成 topic，不能合并成一段泛泛说明。

# 影响范围

- 新增的设计对象和文档：
- 修改的设计对象和文档：
- 删除的设计对象和文档：
- 对代码、任务、流程和兼容性的影响：
- 迁移考虑：
- 回滚考虑：

# 实施计划

- 设计空间修改顺序：
  1. 结构树：
  2. 技术设计文档：
  3. 目录设计文档：
  4. 命名空间设计文档：
- 草案内容如何落到正式设计文档：
- 验证方式：
  - ds structure check
  - ds doc layout
  - ds doc check
  - ds verify
- 实施风险：

# 关键取舍（可选）

- 已作出的取舍：
- 选择理由：
- 对阅读者需要特别注意的影响：
```

## 3. 内容规则

- “目标设计”只写整体结构和边界；具体机制全部写进“设计要点”。
- 不写验收标准。
- 不写“待定”“待确认”“开放问题”；所有设计决定必须在草案里做出。
- 确实需要读者注意的已决定取舍，写进“关键取舍”。
- 设计要点不是补充说明，是草案主体；高复杂度部分必须有专门 topic。
- 本次新增或修改设计原则时，把它作为“设计要点”的一条写清楚；草案不新增“设计原则”章节。
- 草案必须能直接指导 apply 阶段修改设计空间。

## 4. 引用

草案中的 Issue、对象、文档和代码位置使用 DS 引用格式：

```text
[[issue:<issue-id>|<label>]]
[[task:<task-id>|<label>]]
[[ds:<qname>|<label>]]
[[code:<path>[:<start>-<end>]|<label>]]
```

引用只是文本约定，不是 DS 对象；Web 渲染为超链接。详见 `design-space` 技能的“引用”一节。
