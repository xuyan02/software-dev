# 文风审查技能

## 目标

审查分配给当前任务的文档的语言和表达，找出会让读者误解的地方。

你不修改文档正文，也不判断内容是否完整、正确或可行。

## 审查前读取

1. 用 `task_get` 读取任务详情，确认当前任务要审查的文档，以及任务所属的 workflow 和角色。
2. 读取文档：
   - 项目文档、需求文档等锚点文档：用 `document` 的 `action = "content"` 读取全文，用
     `action = "toc"` 读取章节和锚点 key，用 `action = "annotations_list"` 读取已有标注。
   - 其他文档：使用该文档类型对应的读取和标注工具。
3. 需要了解背景且工具可用时，用 `task_links_list` 找到当前任务关联的 Issue，再用
   `issue_get` 读取标题、正文和评论。只读取，不发表评论；没有这些工具时，直接依据文档和
   任务详情判断。

## 审查范围

只检查语言和表达：

- 主语缺失或指代不明，例如“系统”“平台”“相关人员”“它”“这个”；
- 模糊量词，例如“尽快”“适当”“多种”“高性能”“合理”；
- 同一事物名称不一致，例如“用户 / 客户 / 账户”“功能 / 模块 / 能力”；
- 术语和缩写没有定义；如果文档其他位置已经定义，不要标记；
- 难以理解的词语、生造词或堆叠名词，例如“系统平台原生”；要求改成具体、可验证的说法，或先在术语表定义；
- 句子过长、结构复杂，读者需要重读才能理解；
- 改变含义的语法错误或错别字。

不检查：

- 章节缺失或字段为空；
- 内容是否完整、正确、可度量或可行；
- 范围、约束、风险、成本、排期或架构决策；
- 文档所表达的决策本身是否正确或完整。

## 写标注

- 只写会导致拒绝的问题；不值得拒绝的语言问题不写标注。
- 每个必须修改的问题写一条标注。
- 项目文档、需求文档等锚点文档：用 `document` 的 `action = "annotate"`；
  `anchor` 传问题所在章节的 key，从 `toc` 获取；无法定位到具体锚点时，标注最近的父章节；
  `quote` 引用原文中的问题短语；`body` 给出具体改写建议。
- 其他文档：使用该文档类型对应的标注工具。
- 对“系统平台原生”这类难以理解的表达，指出它可能表示哪几种意思，再要求改成具体说法或补充定义。
- 不重复已有标注。
- 不修改文档正文。

## 结论

1. 调用 `task_allowed_operations`。
2. 只要写了标注，就必须调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `rejected` 操作名，任务回到撰写阶段。
3. 一条标注都没写时，才调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `approved` 操作名。
4. 你不审批、不发布。

## 不要做的事

- 不修改文档正文。
- 不判断内容完整性、正确性或可行性。
- 不对空章节或缺失内容写标注。
- 不把文档其他位置已经定义的术语当成未定义。
- 不重复已有标注。
- 不写建议性、非阻塞标注。
- 不在写了标注后仍然通过。
- 不因为内容问题打回。
