# 测试计划说明书

## 目录结构

```text
测试计划
├─ 测试策略
├─ 测试范围
├─ 测试环境
├─ 测试用例（多项，标题 = 用例名称）
│  ├─ 关联需求
│  ├─ 前置条件
│  ├─ 步骤（列表）
│  ├─ 预期结果
│  ├─ 类型
│  └─ 证据要求
├─ 质量门禁
└─ 风险与豁免（列表）
```

## 定位

测试计划回答“验证什么、怎么验证、什么算通过”。它不写测试代码，不记录执行结果；执行结果写在测试报告里。

## 各项写什么

### 测试策略

说明测试层级和风险策略：单元、集成、接口、验收、回归、安全、性能分别覆盖什么；哪些需求必须独立验证或 holdout；哪些风险接受人工验收。不要写“全面测试”这类空话。

### 测试范围

写清本次计划和后续迭代的范围：覆盖哪些子系统、功能、质量属性和非功能要求；明确不测什么及原因。

### 测试环境

写清环境、依赖、数据、配置和工具版本要求。环境必须可复现；不能用“开发环境”一句话代替。

### 测试用例

每条用例验证一个可观察的行为。

- **关联需求**：对应功能、故事或质量属性；必须能在需求或架构中找到。
- **前置条件**：数据、权限、配置和状态。
- **步骤（列表）**：可执行的操作或检查步骤。
- **预期结果**：可观察、可判断的结果；不要写“工作正常”。
- **类型**：单元 / 集成 / 接口 / 验收 / 回归 / 安全 / 性能 / 人工。
- **证据要求**：命令、日志、报告或截图；关键门禁不能只接受自测。

### 质量门禁

列出进入开发验收或测试执行前必须满足的条件，例如构建通过、单测通过、关键需求有独立用例、失败用例有缺陷记录。

### 风险与豁免

每条写清风险、影响、豁免理由、批准人和有效期。没有批准人的豁免不成立。

## 原则

1. 每条用例必须能追溯到需求、故事、功能或质量属性。
2. 预期结果必须可观察、可判断，不能是主观描述。
3. 关键需求必须有独立用例，不能只由实现者自测。
4. 失败路径、边界、权限、空状态和错误恢复必须有用例。
5. 环境、数据和工具版本必须可复现。
6. 测试计划不写测试代码，也不记录执行结果。
7. 不把覆盖率当成唯一目标；覆盖不等于验证充分。

## 判断标准

- 每个需求功能是否有至少一条用例？
- 每个关键质量属性是否有场景、度量和验证方式？
- 每条用例是否有关联需求、步骤、预期结果和证据要求？
- 失败、边界、权限和恢复路径是否覆盖？
- 环境、数据和工具版本是否可复现？
- 是否有无法验证或无法观察的用例？
