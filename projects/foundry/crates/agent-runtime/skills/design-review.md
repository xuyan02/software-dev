# 详细设计审查技能

## 目标

审查详细设计是否完整、可实现、可测试，并与需求、架构和项目约束一致。

只审查，不修改文档，不审批或发布。

## 审查前必须读取

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
6. `document`，`action = "content"`，`kind = "architecture"` 读取架构设计。
7. `document`，`action = "content"`，`kind = "design"` 读取详细设计。
8. `document`，`action = "toc"`，`kind = "design"` 读取锚点。
9. `document`，`action = "annotations_list"`，`kind = "design"` 读取已有批注。
10. `task_allowed_operations` 确认当前允许的操作。

内容规则以《详细设计说明书》为准。

## 审查方法

建立覆盖矩阵：

```text
需求：功能 / 子系统
架构：组件 / 接口 / 数据 / 质量属性
设计：子系统 / 模块 / 任务
```

### 1. 覆盖

- 架构中的每个组件是否有模块承接？
- 需求中的每个功能是否至少被一个模块承接？
- 是否有模块没有需求或架构来源？
- 任务是否覆盖所有模块和交付物？

### 2. 模块

- 职责是否内聚，是否写成“处理所有业务”？
- 接口是否写清输入、输出、错误、幂等性和兼容性？
- 数据所有权、一致性、迁移是否清楚？
- 错误处理是否覆盖可预期错误、重试/降级/回滚？
- 依赖是否有用途和失败影响？
- 配置是否说明来源、默认值和校验？
- 实现约束是否可执行？
- 测试要点是否覆盖关键行为、边界和失败路径？

### 3. 任务分解

- 每个任务是否关联模块？
- 交付物是否明确？
- 依赖是否清楚？
- 验收条件是否可验证，并能对应需求或架构约束？

### 4. 一致性

- 是否重新定义了架构边界或接口？
- 是否与需求、架构、项目约束矛盾？
- 是否混入代码、伪代码、表结构或具体实现细节？
- 是否重复需求和架构内容？

## 逻辑推演

### 实现推演

对每个模块问：

- 开发者能否只凭这份设计实现它？
- 接口调用方能否知道如何调用、如何处理错误？
- 数据迁移和回滚是否有路径？
- 失败时系统处于什么状态，如何恢复？

### 测试推演

- 每个测试要点是否能转成测试用例？
- 是否存在无法观察或无法验证的验收条件？
- 关键失败路径是否有测试？

## 输出

用 `document`，`action = "annotate"`，`kind = "design"`：

- `anchor`：toc 中问题所在锚点。
- `quote`：引用原文。
- `body`：具体缺陷、规则依据、修改建议和通过条件。

只写必须修改的问题；只要写了标注，就必须拒绝。每条标注必须能写清通过条件。

提交结论：

- 写了标注：调用 `task_allowed_operations`，再用返回的 reject 操作调用 `task_operation`。
- 没有标注：用返回的 approve 操作调用 `task_operation`。

## 不要做的事

- 不修改文档。
- 不审查需求或架构本身。
- 不写建议性、非阻塞标注。
- 不在写了标注后仍然通过。
- 不审批、不发布。
