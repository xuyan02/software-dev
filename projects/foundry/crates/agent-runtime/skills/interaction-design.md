# 交互设计技能

## 目标

为需求文档中的每个功能补全一行交互设计。交互设计写在功能项正文的 `交互设计：` 行里，描述该功能的页面结构、控件和用户如何操作，不写业务规则和视觉样式。

## 输入

每一轮开始前重新读取：

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
6. `document`，`action = "toc"`，`kind = "requirements"` 读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取批注。
8. `task_allowed_operations` 确认当前允许的操作。

内容规则以《需求文档写作说明书》为准。

## 工作流程

1. 用 `document`，`action = "draft_open"`，`kind = "requirements"` 打开草稿；没有草稿时 `draft_create`；保留 `revision`。
2. 从目录找出所有功能，记录每个功能的锚点。
3. 对每个功能：
   - 读取功能项正文，保留名称、功能描述、系统变化、前置条件、反馈各行。
   - 读取使用该功能的故事，理解用户操作顺序、错误和成功确认。
   - 设计该功能的交互。
   - 用 `action = "update_text"` 更新功能项正文：保留已有字段行，只替换或追加 `交互设计：` 行。
4. 每批修改后用 `action = "validate"` 校验，修复所有 error。
5. 处理已有批注；能改的改，不能改的写明理由并 `resolve_annotation`。
6. 调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "completed"`。

## 每个功能写什么

一个功能只有一行 `交互设计：`，内容必须覆盖：

- **页面结构**：涉及哪些页面或区域、层级关系和跳转关系。
- **用户操作**：按顺序写用户如何完成功能，包括点击、填写、选择、提交和取消；写功能级操作，不逐条解释细粒度交互。
- **控件**：控件类型、位置、默认值、可用或禁用条件、关键行为。
- **反馈与状态**：加载、成功、失败、空状态、确认、撤销和错误提示如何呈现。
- **文案**：按钮、提示和错误文案的关键内容。
- **无障碍与操作方式**：键盘操作、焦点顺序、读屏和触控要求中影响交互的部分。

## 不写什么

- 业务规则、系统结果、状态变化明细、数据影响、异常结果和权限；这些不写进需求文档。
- 视觉样式、颜色、字体、字号、间距、圆角、图标、图片和设计 token；这些属于 UI 设计。
- 把“填写单据 ID”“选择供应商”“点击提交”拆成独立字段或标题；一个功能只有一行 `交互设计：`。
- 技术实现、接口、数据库和算法。
- 用户画像本身；只引用用户。
- 指标、团队、排期和人力。

## 检查

- 每个功能是否只有一行 `交互设计：`？
- 是否覆盖从进入功能到完成或放弃的用户操作，但没有拆成多个字段或标题？
- 页面结构和控件是否足以让 UI 设计继续？
- 反馈的信息内容是否与功能的“反馈”一致？
- 加载、成功、失败和空状态是否都有交代？
- 是否混入了业务规则、系统结果、视觉样式或技术实现？
- 是否与故事的操作顺序、错误处理和成功确认一致？

## 缺失信息

- 缺关键决定时，用 `issue_comment` 提问并结束本轮，等待人类回复。
- 不要编造页面、控件或交互；无法确认的内容留在 Issue。

## 被审查打回后：按标注修改

### 1. 读取

- 用 `task_get` 读取任务详情和打回原因。
- 用 `action = "annotations_list"`，`kind = "requirements"` 读取全部批注。
- 用 `action = "content"` 和 `action = "toc"`，`kind = "requirements"` 读取当前草稿全文和锚点。
- 用 `action = "draft_open"` 打开草稿，保留最新 `revision`。

### 2. 建立批注清单

逐条记录批注 id、`anchor_key`、引用原文、内容建议和状态。同一功能上的多条批注也要逐条处理：每处理完一条立即 resolve，再处理下一条。

### 3. 逐条判断和处理

每处理完一条批注，立即 resolve 该批注，再处理下一条。不要先改完全部批注再统一 resolve。

对每条批注：

1. 找到 `anchor_key` 对应的功能；锚点失效时按引用原文和所处功能定位。
2. 对照《交互设计技能》《需求文档写作说明书》、功能描述、故事和功能的反馈，判断批注是否成立。
3. **成立**：读取功能正文，保留其他字段行，替换或修正 `交互设计：` 行后，用 `update_text` 更新功能项。
   - 保持一个功能只有一行 `交互设计：`。
   - 覆盖页面结构、控件、用户操作、反馈与状态、文案、无障碍。
   - 不把细粒度交互拆成独立字段或标题。
4. **不成立或与说明书冲突**：不修改正文，在 `resolve_annotation` 里写清理由。
5. **当前草稿已经改好**：直接 `resolve_annotation`，说明已处理。
6. **需要未确认的信息**：不要编造页面、控件或交互；不修改正文，在 `resolve_annotation` 里说明无法确认的原因。

只修改功能正文中的 `交互设计：` 行，不修改其他字段。批注要求修改需求分析内容或 UI 设计时，不改正文，在 resolve 说明里写明属于需求分析或 UI 设计任务。

### 4. 标记已处理

- 每处理完一条批注，立即用 `action = "resolve_annotation"` 标记，再处理下一条。
- `resolution` 写一句具体说明，例如“已补充提交失败的字段级错误提示”。
- 不要攒到最后批量 resolve，也不要在没有修改的情况下 resolve。
- 不把批注当成不存在。

### 5. 复查

- 重新用 `action = "annotations_list"` 读取批注，确认没有未处理的 open 批注；仍有则继续处理。
- 重新用 `action = "content"` 检查修改后的交互设计，确认与功能、故事和反馈一致。
- 用 `action = "validate"` 校验，修复所有 error。
- 校验通过后调用 `task_operation`，`operation = "completed"` 再次提交。
