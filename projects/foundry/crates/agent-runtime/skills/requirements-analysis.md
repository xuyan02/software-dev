# 需求分析技能

## 目标

把项目文档、澄清 Issue 和已有需求文档转化为可执行的需求模型：用户、子系统、功能集、故事、功能。

本技能只做需求分析，不做交互设计，也不做 UI 设计。页面、控件、视觉稿和动画留给后续阶段。

分析结果必须同时满足：

- **满足用户需求**：每个项目目标都能落到用户诉求、故事和功能。
- **操作成本最小**：用最少的用户操作完成目标；不重复录入、不做不必要的确认和交接。
- **闭环**：故事、功能集、子系统都能端到端完成一个目标。
- **不遗漏**：用户、目标、异常、非软件环节和跨边界交接都有覆盖。
- **可实现**：每个功能都是具体、可验证的系统变化。

## 分析前必须读取

每一轮开始前重新读取，不依赖上一轮记忆。按顺序执行：

1. `task_links_list`：找到当前任务的 Issue。
2. `issue_get`：读取 Issue 标题、正文和全部评论。
3. `project_get`：读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"`：读取项目文档全文。
5. `document`，`action = "content"`，`kind = "requirements"`：读取需求文档全文。
6. `document`，`action = "toc"`，`kind = "requirements"`：读取元数据、目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"`：读取已有批注。
8. 如果任务从审查打回，用 `task_get` 读取任务详情。
9. `task_allowed_operations`：确认当前任务允许哪些操作。

读取后确认：

- 项目目标、非目标、约束和风险分别是什么。
- 澄清 Issue 已经确认了哪些结论，哪些还留在 Issue。
- 需求文档中哪些章节为空、哪些需要修改。
- 有哪些未解决批注。
- 当前是否已有草稿；没有草稿时下一步创建。

内容写法以《需求文档写作说明书》为准；本技能只决定分析顺序和操作步骤。

## 分析顺序与文档顺序

- **分析顺序**：用户 → 诉求和典型场景 → 故事 → 功能 → 功能集 → 子系统。
- **文档顺序**：用户 → 子系统 → 功能集 → 故事和功能。
- 先自底向上推导，再按文档树自顶向下写入。

---

## 第 0 步：读取并建立覆盖清单

先不要写文档。先建立一张工作清单：

```text
项目目标 G1, G2, ...
项目非目标 NG1, ...
项目约束 C1, ...
用户 U1, U2, ...
├─ 诉求 A1, A2, ...
故事 S1, S2, ...
功能 F1, F2, ...
功能集 FS1, FS2, ...
子系统 SS1, SS2, ...
```

检查点：

- 每个项目目标至少有一个候选用户和诉求。
- 每个非目标都能判断当前分析是否越界。
- 每个约束都能影响某个功能或子系统。
- 没有来源的推断标记为“待确认”，不写进文档。

## 第 1 步：识别用户

用户是具体画像，不是抽象角色。固定字段：姓名、年龄、基本状况、爱好、职业、典型场景、诉求、主次。每个用户只写一段正文，按 `字段：值` 每行一项，不拆成子字段。

### 1.1 从现有用户开始

先看需求文档里是否已有用户。按职业、诉求和典型场景匹配：

- 能匹配：复用，不新建。
- 只是姓名不同但职业、诉求和场景相同：合并，不重复建。
- 只是爱好或年龄不同，但使用系统的方式相同：不要因此新建用户。

### 1.2 什么时候创建新用户

出现以下任一情况，创建新用户：

1. 一个故事的操作者无法匹配任何已有用户。
2. 项目目标或约束涉及新的使用群体，例如审批人、审计人、外部合作方。
3. 新的子系统或使用形态服务于不同群体，例如现场移动端用户和后台 Web 端用户。
4. 已有用户的诉求和典型场景无法覆盖新的业务目标。

### 1.3 怎么写用户正文

用户项只有一个正文，按下面的字段顺序逐行写 `字段：值`，不要把字段拆成子标题或子字段。新增用户时，`title` 传姓名：

- **姓名**：具体姓名或化名，一项一个姓名。
- **年龄**：具体年龄或年龄段。
- **基本状况**：家庭、身体、经济、工作条件中影响系统使用的部分；不相关不写。
- **爱好**：用户的爱好。
- **职业**：职业或岗位。
- **典型场景**：用户平时怎么做事、在什么环境和节奏下使用系统；只写与系统有关的部分。
- **诉求**：用户想获得的结果，不是功能或方案。
- **主次**：主要或次要。

示例：

```text
姓名：张伟
年龄：35 岁
基本状况：需要轮班并照顾孩子，只能在交接班时集中处理单据。
爱好：钓鱼、看历史纪录片
职业：仓库管理员
典型场景：每天先巡库，再用纸质单据核对到货，收货后集中补录系统。
诉求：到货后能快速确认数量并找到可放库位。
主次：主要
```

检查点：

- 每个用户至少有一个诉求。
- 每个主要用户至少对应一个项目目标或核心故事。
- 没有“所有用户”“普通用户”这类泛称。
- 没有把多个用户合并成一项。

## 第 2 步：识别诉求和典型场景

对每个用户：

1. 从项目目标和背景痛点推导诉求，写“用户想获得什么结果”。
2. 检查诉求是否被写成了功能或方案；如果是，改回结果。
3. 写典型场景：用户平时怎么做事、系统在其中的位置、操作环境。
4. 只保留与系统有关的典型场景；与系统无关的家庭和生活细节不写。
5. 区分典型场景和故事：典型场景没有明确目标和功能序列；故事必须有。

检查点：

- 每个用户诉求能对应至少一个故事。
- 每个诉求不是功能、页面或技术方案。
- 典型场景没有被写成故事。

## 第 3 步：写故事

一个故事只满足一项用户需求；多项需求拆成多个故事。

### 3.1 故事模板

固定四项，写在故事项正文里，每行一个 `字段：值`：

- 名称。
- 前置条件。
- 发生频率：高、中、低。
- 故事描述。

新增故事时，`title` 传故事名称。

### 3.2 写故事描述

按顺序执行：

1. 写具体用户的姓名。
2. 写用户想达成的结果。
3. 从起点开始，逐步写出用户先做什么、后做什么。
4. 每一步判断：是否产生可观测的系统变化？
   - 是：落到一个功能，写功能名称。
   - 否：它是某个功能内部的交互，或是不跟软件交互的环节。
5. 不跟软件交互的环节也要写清楚，例如人工核对、纸质单据、电话沟通，并说明它前后如何与软件操作衔接。
6. 写错误：哪一步可能出错、用户怎么得知、怎么处理。
7. 写成功：用户怎么确认操作成功，例如看到编号、状态或数量变化。
8. 检查正常路径是否最短；能合并的重复操作合并，能复用的数据不再要求用户录入。

### 3.3 故事检查

- 只满足一项用户需求。
- 有具体用户姓名。
- 每个操作都落到了一个功能。
- 非软件环节写清楚了。
- 有错误处理和成功确认。
- 没有交互细节、页面、控件、文案和业务规则。
- 不是用户的典型场景。

## 第 4 步：识别功能

功能是产生可观测系统变化的最小单位。

### 4.1 功能判定

对故事中的每一步问：

1. 完成后系统是否发生可观测变化（创建、修改、删除、状态迁移）？
   - 否：不是功能，是交互或不跟软件交互的环节。
   - 是：继续。
2. 这个变化是否还能拆成多个各自产生系统变化的功能？
   - 能：拆成多个功能。
   - 不能：它是最小功能。
3. 同一个业务对象和同一种系统变化是否已经有功能？
   - 有：复用，不重复建。
   - 没有：新建功能。

### 4.2 功能固定字段

写在功能项正文里，每行一个 `字段：值`：

- 名称：写在 `名称：` 行；新增功能时 `title` 传功能名称。
- 功能描述：一两句话说明这个功能的作用。
- 系统变化：改哪个业务对象、什么状态、从什么状态变成什么状态。
- 前置条件：功能发生前必须成立的条件。
- 反馈：功能完成后系统返回或告知用户什么信息。
- 交互设计：后续阶段补全，写成正文中的一行 `交互设计：`，不单独建子章节。

不写：交互步骤、页面、控件、业务规则、结果细节、状态变化明细、数据影响、异常、权限、边界。交互设计和 UI 设计属于后续阶段。

### 4.3 功能检查

- 每个功能都有可观测的系统变化。
- 每个功能都是最小单位。
- 一个功能只改变一类业务对象或完成一个结果。
- 功能名称在文档内能唯一定位。
- 没有把交互、页面、控件或技术实现写成功能。

## 第 5 步：识别功能集

功能集是若干功能组成的有机整体，必须共同协作才能满足一个用户需求；单个功能不独立产生用户价值。

### 5.1 聚类规则

把功能按“共同满足的用户需求”和“同一业务对象”聚类：

- 同一业务对象、同一用户需求：放在同一个功能集。
- 不同用户需求：拆成不同功能集。
- 只是被同一个故事使用，但服务不同需求：不要强行合并。
- 只是技术实现相关：不要归为同一功能集。

### 5.2 功能集成立条件

一个功能集必须同时满足：

1. 包含多个功能。
2. 这些功能必须协作才能满足一个用户需求。
3. 去掉关键功能后，用户需求无法满足。
4. 覆盖该需求需要的主要生命周期，例如创建、查询、修改、删除或状态迁移。
5. 有明确分界，与相邻功能集不重叠。

### 5.3 功能集固定字段

写在功能集项正文里，每行一个 `字段：值`：

- 名称：写在 `名称：` 行；新增功能集时 `title` 传功能集名称。
- 满足的用户需求。
- 覆盖用户：写职业，例如“仓库管理员”。
- 协作关系：功能如何配合形成整体。
- 闭环位置：支撑子系统的哪个端到端目标，与上下游功能集如何衔接。
- 分界：不包含什么，哪些能力属于其他功能集。

功能和故事只作为子项，正文不罗列。

### 5.4 功能集检查

- 不是单个功能。
- 不是无关功能的堆砌。
- 不是技术模块或服务。
- 每个功能集只负责一个需求范围。
- 主要生命周期完整，没有明显缺口。
- 与相邻功能集没有职责重叠。

## 第 6 步：识别子系统

子系统是用户可感知的一个软件，例如 Web 端、移动端；它由多个功能集组成并形成闭环。

### 6.1 子系统判定

对候选子系统问：

1. 用户是否能识别这是一个可以使用的软件或入口？
   - 否：它可能是业务领域、功能集或技术模块，不是子系统。
   - 是：继续。
2. 它包含的功能集是否能共同完成至少一个端到端目标？
   - 否：功能集不完整，或它还不是一个子系统。
   - 是：继续。
3. 它是否按使用入口或形态划分，例如 Web 端、移动端？
   - 是：子系统。
   - 否：检查是否把“库存”“采购”这类业务领域误当成子系统。

### 6.2 子系统固定字段

写在子系统项正文里，每行一个 `字段：值`：

- 软件名称：写在 `软件名称：` 行；新增子系统时 `title` 传软件名称。
- 软件形态：Web 端、移动端、桌面端等。
- 覆盖用户：写职业，不写具体用户姓名。
- 闭环目标：用户通过它完成哪些端到端目标。
- 与其他子系统的关系：共享数据、能力或流程，入口和渠道如何分工；没有写“无”。
- 边界：不包含什么，哪些能力由其他子系统承载。

### 6.3 子系统检查

- 是用户可感知的软件，不是业务领域或服务。
- 功能集能形成端到端闭环。
- 覆盖用户写职业。
- 与其他子系统的关系单独写清。
- 功能集只作为子项，正文不罗列。

## 第 7 步：闭环与覆盖检查

用矩阵检查，不靠记忆：

### 7.1 目标覆盖

每个项目目标至少对应：

```text
目标 → 用户诉求 → 故事 → 功能集 → 功能
```

没有对应故事的目标，要么补故事，要么确认目标不在本期范围。

### 7.2 用户覆盖

- 每个用户的每个诉求至少对应一个故事。
- 每个主要用户至少有一个核心故事。
- 没有只创建用户、却没有诉求或故事的孤立用户。

### 7.3 故事覆盖

- 每个操作都落到一个功能。
- 故事用到的每个功能都已在文档中定义。
- 每个故事都有前置条件、发生频率、错误处理和成功确认。
- 没有多个需求混在一个故事里。

### 7.4 功能集闭环

- 业务对象的主要状态都有功能覆盖：创建、查询、修改、状态迁移、必要的删除或归档。
- 没有只被故事引用、却没有归属功能集的功能。
- 没有只包含一个功能的功能集。
- 没有与相邻功能集重叠的能力。

### 7.5 子系统闭环

- 每个子系统至少有一个端到端闭环目标。
- 跨子系统的交接点写清了输入、输出和由谁完成。
- 没有功能集悬空，没有子系统缺失关键功能集。

### 7.6 边界覆盖

- 非目标中的内容没有出现在故事、功能或功能集里。
- 约束没有被违反；外部依赖没有变成跨项目需求。
- 错误分支、非软件环节和跨边界交接都有覆盖。

检查结果记录为“已覆盖 / 缺口 / 待确认”。缺口必须在提交前补上或留在 Issue 继续澄清。

## 第 8 步：操作成本优化

目标是让用户用最少的操作完成需求。这里只优化需求和功能层面，不设计页面和控件。

### 8.1 计数

对每个故事，数一数正常路径需要：

- 多少次用户操作；
- 多少次手工录入；
- 多少次人工核对或交接；
- 多少次确认或审批；
- 多少次上下文切换。

这些计数只用于分析，不写进需求文档。

### 8.2 优化规则

1. **删除无系统变化步骤**：不产生系统变化的操作不单独成为功能。
2. **复用已有数据**：系统已经有的数据不要再让用户录入。
3. **避免重复录入**：同一数据在多个功能中只录入一次，后续功能复用。
4. **合并重复功能**：同一业务对象、同一系统变化只保留一个功能。
5. **减少不必要交接**：不改变用户目标的审批、确认和转交不写进故事。
6. **批量处理**：高频故事中，多个相同系统变化可以合并为一次功能操作。
7. **最短正常路径**：正常路径上的每一步都必须推进目标。
8. **错误可恢复**：出错后保留已完成的工作，不让用户从头再来。
9. **保留必要决策**：需要用户判断的地方不能为了省操作而自动替用户决定。

### 8.3 检查

- 正常路径是否每一步都必要？
- 是否有数据被要求重复录入？
- 是否有不改变目标的交接或确认？
- 高频故事是否可以批量处理？
- 错误恢复是否需要重做已完成步骤？
- 简化后是否仍然满足需求和闭环？

## 第 9 步：合理性、可实现性检查

### 9.1 设计合理

- 一个功能只有一个可观测系统变化。
- 一个功能集只满足一个用户需求。
- 一个子系统能形成端到端闭环。
- 功能集之间、子系统之间没有职责重叠。
- 每个功能都有明确归属，没有孤立功能。
- 用户诉求、故事、功能、功能集、子系统之间能双向追溯。

### 9.2 操作简易

- 正常路径最短。
- 没有重复录入和不必要确认。
- 高频操作可以批量完成。
- 错误处理不要求重做已完成步骤。
- 用户不需要记住系统之外的信息才能完成操作。

### 9.3 可实现

- 每个功能都是具体、可验证的系统变化。
- 没有“提升体验”“优化流程”这类无法判断的目标。
- 没有把技术方案、架构、接口或数据模型写进需求。
- 满足项目约束和非目标。
- 外部系统能力记录为依赖、约束或风险，不创建跨项目需求。
- 现有事实不足以确认的内容不编造，留在 Issue 继续澄清。

## 第 10 步：创建草稿、写入、校验、结束

### 10.1 打开或创建草稿

1. 用 `document`，`action = "draft_open"`，`kind = "requirements"` 打开草稿。
2. 返回 `revision` 时保留它，后续每次写操作都使用最新 revision。
3. 如果没有草稿，用 `action = "draft_create"` 创建。
4. 创建或打开后，用 `action = "toc"` 重新确认章节锚点。

### 10.2 写入和修改

按文档顺序写入：用户 → 子系统 → 功能集 → 故事和功能。

- **多项项正文**：用 `action = "add"` 时，`text` 直接写完整的 `字段：值` 正文。例如用户、子系统、功能集、故事、功能、图片都在一项正文里写完所有字段。
- **标题**：`add` 必须传 `title`。用户用姓名，子系统用软件名称，功能集、故事、功能、图片用名称。标题不从正文推导。
- **修改标题**：用 `action = "update_title"`，带锚点和新的 `title`；只有多项标题能改，单次章节和分组章节不能改。
- 不要为字段创建子章节，也不要用 `update_text` 逐个填“姓名”“系统变化”这类字段。
- 新增功能集时，会同时创建 `故事`、`功能` 两个容器章节；它们只是分组，不是字段，不要把字段值写进容器。
- UI 设计的图片是功能下的列表项；每个图片项的正文按 `名称：`、`链接：` 两行写。
- **正文型项和单次章节**：用 `action = "update_text"`。
- **调整顺序**：用 `action = "move"`。
- **删除**：用 `action = "delete"`；单次章节不能删除。
- **每次操作**都带 `kind = "requirements"`、`expected_revision` 和对应锚点。
- 使用上一步返回的 `revision`，不要复用旧 revision。
- 按锚点增量修改，不重写整篇文档。
- 先写父章节，再写子项：用户 → 子系统 → 功能集 → 故事/功能 → 图片。

### 10.3 分析完成后的检查

1. 用第 7 步的覆盖矩阵确认没有断链。
2. 用 `action = "validate"`，`kind = "requirements"` 校验草稿。
3. 修复所有 `error`；`warning` 是评审提示，不阻塞提交。
4. 重新读取 `toc` 和 `content`，确认固定字段齐全、顺序正确、没有空章节。
5. 确认所有固定字段都以 `字段：值` 写在项正文中，没有为字段创建子章节或标题。
6. 确认标题正确：用户用姓名，子系统用软件名称，功能集、故事、功能、图片用名称；没有“用户 1”“功能 2”这类序号标题。
7. 确认没有把交互设计、UI 设计、业务规则、技术方案写进需求分析内容。
8. 处理已有批注：能改的改；不能改的写明理由并用 `action = "resolve_annotation"` 标记。
9. 如果仍有未解决的关键决定，回到 Issue 提问，不要带着缺口提交。

### 10.4 结束

1. 调用 `task_allowed_operations`，确认当前任务允许 `completed`。
2. 调用 `task_operation`，`operation = "completed"`，把需求文档提交给评审。
3. 不要审批或发布；批准由人类完成。

如果缺少关键决定：

1. 用 `issue_comment` 提出具体问题。
2. 结束本轮，等待人类回复。
3. 不要调用 `completed`。

### 10.5 被审查打回后

见下方「被审查打回后：按标注修改」。

## 被审查打回后：按标注修改

### 1. 读取

- 用 `task_get` 读取任务详情和打回原因。
- 用 `action = "annotations_list"`，`kind = "requirements"` 读取全部批注。
- 用 `action = "content"` 和 `action = "toc"`，`kind = "requirements"` 读取当前草稿全文和锚点。
- 用 `action = "draft_open"` 打开草稿，保留最新 `revision`。

### 2. 建立批注清单

逐条记录批注 id、`anchor_key`、引用原文、内容建议和状态。同一锚点上的多条批注也要逐条处理：每处理完一条立即 resolve，再处理下一条。

### 3. 逐条判断和处理

每处理完一条批注，立即 resolve 该批注，再处理下一条。不要先改完全部批注再统一 resolve。

对每条批注：

1. 找到 `anchor_key` 对应的当前内容；锚点失效时按引用原文和上下文定位。
2. 对照《需求分析技能》《需求文档写作说明书》、澄清 Issue 和当前文档，判断批注是否成立。
3. **成立**：按锚点增量修改需求分析内容。
   - 正文型项和单次章节用 `update_text`。
   - 用户、子系统、功能集、故事、功能等多项项用 `add`、`move`、`delete` 调整。
   - 只改用户、诉求、故事、功能、功能集、子系统、功能描述等需求分析内容。
   - 不修改功能正文中的 `交互设计：` 行，也不修改功能下的图片列表；它们属于后续任务。批注要求改这两部分时，不改正文，在 resolve 说明里写明“属于交互设计/UI 设计任务”。
4. **不成立或与说明书冲突**：不修改正文，在 `resolve_annotation` 里写清理由。
5. **当前草稿已经改好**：直接 `resolve_annotation`，说明已处理。
6. **需要未确认的信息**：不要编造；不修改正文，在 `resolve_annotation` 里说明无法确认的原因，留给人工评审判断。

### 4. 标记已处理

- 每处理完一条批注，立即用 `action = "resolve_annotation"` 标记，再处理下一条。
- `resolution` 写一句具体说明，例如“已把功能集分界改为不含库位分配”。
- 不要攒到最后批量 resolve，也不要在没有修改的情况下 resolve。
- 不把批注当成不存在。

### 5. 复查

- 重新用 `action = "annotations_list"` 读取批注，确认没有未处理的 open 批注；仍有则继续处理。
- 重新用 `action = "content"` 检查修改后的全文，确认没有引入新的断链或矛盾。
- 用 `action = "validate"` 校验，修复所有 error。
- 校验通过后调用 `task_operation`，`operation = "completed"` 再次提交。

## 提交前质量门槛

逐项确认：

- [ ] 每个用户有固定字段、明确诉求和主次。
- [ ] 每个诉求至少对应一个故事。
- [ ] 每个故事只满足一项需求，有前置条件、发生频率、错误处理和成功确认。
- [ ] 每个操作都落到了一个功能。
- [ ] 每个功能都有可观测系统变化，且是最小单位。
- [ ] 每个功能集由多个功能协作组成，覆盖必要生命周期，有分界。
- [ ] 每个子系统是用户可感知的软件，功能集形成端到端闭环。
- [ ] 项目目标、用户诉求、故事、功能集、功能之间没有断链。
- [ ] 非目标和约束没有被违反。
- [ ] 错误分支、非软件环节和跨边界交接没有遗漏。
- [ ] 正常路径操作最少，没有重复录入和不必要交接。
- [ ] 没有写交互设计、UI 设计、技术方案或业务规则细节。

## 常见错误

- 为每个角色建一个用户，或使用“所有用户”“普通用户”这类泛称。
- 把用户的典型场景写成故事，或把故事写成一句话用户故事模板。
- 把交互当成功能，把功能当成功能集。
- 把业务领域（库存、采购）或技术服务当成子系统。
- 功能集只包含一个功能，或把无关功能堆在一起。
- 功能集缺少查询、修改、状态迁移等必要生命周期。
- 只写正常路径，遗漏错误处理、非软件环节或成功确认。
- 为了“完整”增加不必要的审批、字段和确认，抬高操作成本。
- 把交互设计、UI 设计、技术方案或业务规则细节写进需求。
- 只覆盖局部目标，没有检查项目目标到功能的完整链路。
