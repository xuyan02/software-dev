# 需求分析技能

## 目标

把项目文档、澄清 Issue 和已有需求文档转化为可执行的需求模型：领域模型、用户肖像、故事、功能、功能集、子系统。

本技能只做需求分析，不做交互设计，也不做 UI 设计。页面、控件、视觉稿和动画留给后续阶段。

需求分析不是一次线性走完，而是反复补齐，直到一整轮不再产生新的用户、需求、故事、概念、功能、功能集、子系统、前置条件或关联需求。

## 核心原则

- **从用户可感知的需求出发**：需求必须落到具体用户肖像和用户能理解的结果。
- **功能是用户可观测的系统变化**：功能由用户或系统发起，必须产生用户可观测的变化；用户无法观察的内部动作不是功能。
- **功能粒度按用户认知**：用户能区分的变化才拆成不同功能；用户只能感知最终产出时，最终产出可以是一个功能。
- **功能集围绕独立概念**：概念是否属于同一功能集，看它们能不能独立管理，不看功能是否共同满足一个需求。
- **完整性靠循环**：每轮都检查缺口，发现新项就回到对应步骤补齐，直到固定点。
- **不写实现**：不写交互步骤、页面控件、UI 细节、业务规则、技术方案和数据库实现。

## 分析前必须读取

每一轮开始前重新读取，不依赖上一轮记忆：

1. `task_links_list`：找到当前任务的 Issue。
2. `issue_get`：读取 Issue 标题、正文和全部评论。
3. `project_get`：读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"`：读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"`：读取需求文档全文。
6. `document`，`action = "toc"`，`kind = "requirements"`：读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"`：读取已有批注。
8. 如果任务从审查打回，用 `task_get` 读取任务详情。
9. `task_allowed_operations`：确认当前任务允许哪些操作。

内容写法以《需求文档写作说明书》为准；本技能决定分析顺序、循环和完成条件。

## 台账

先建立一张工作台账，并在每一轮更新。台账不写进需求文档，只用于分析。

```text
项目目标 G1, G2, ...
项目非目标 NG1, ...
项目约束 C1, ...

领域模型 DM1, DM2, ...
用户肖像 U1, U2, ...
├─ 需求 N1, N2, ...
故事 S1, S2, ...
前置条件 P1, P2, ...
关联需求 RN1, RN2, ...
功能 F1, F2, ...
功能集 FS1, FS2, ...
子系统 SS1, SS2, ...
```

每一项都标状态：

- `已覆盖`：已经写入文档，并且有下游覆盖。
- `缺口`：已识别，但还没有对应内容。
- `待确认`：需要 Issue 追问，不能自行编造。

提交前所有条目必须是 `已覆盖`，不能留下 `缺口` 或 `待确认`。

## 初始识别

从项目文档和 Issue 中先识别：

1. 初始用户肖像。
2. 每个用户肖像的初始需求。
3. 初始领域模型。
4. 初始故事。
5. 初始子系统规划。

初始识别不要求完整，后续循环会补齐。

## 循环流程

每一轮按顺序执行 1–7；任何一步发现新项，都回到对应步骤补齐，然后继续。

### 1. 用户与需求覆盖

对每个用户肖像：

- 列出它的全部需求。
- 对每个需求，检查已有故事是否满足。
- 没有故事：写新故事。
- 一个故事混了多个需求：拆成多个故事。
- 新需求找不到归属用户：创建新用户肖像。
- 新需求属于已有用户，但角色、场景或偏好差异会影响软件设计：拆出新用户肖像。
- 完全相同的用户合并成一项。

检查点：

- 每个用户至少有一个需求。
- 每个需求至少有一个故事。
- 每个故事只对应一个需求。
- 没有孤立用户，也没有无主需求。

### 2. 故事展开

对每个故事：

1. 检查前置条件是否完整。
2. 对每个前置条件，回答：这个条件由谁、通过什么动作、在哪个功能中建立？
   - 系统或外部已经保证：写进前置条件，并记录为假设或外部依赖。
   - 需要用户完成某个动作或能力：产生一个新需求。
   - 例如“已登录”会产生“注册”“登录”需求；“已有账户”可能产生“创建账户”“找回密码”需求。
   - 只展开项目范围内、用户必须完成、且会影响软件设计的前置条件需求。
   - 超出项目范围或由外部系统保证的，记录为非目标、约束或假设，不继续展开。
3. 检查故事是否覆盖所有用户可观察到的反馈和变化。
4. 检查故事是否产生关联需求。
   - 例如“购买”会产生“退货”“换货”“查询订单”等需求。
   - 每个关联需求都要找到归属用户；找不到就创建用户肖像。
   - 每个关联需求都要有故事覆盖；没有就继续写故事。
5. 对每个新需求，重复本步骤，直到没有新的前置条件需求或关联需求。

检查点：

- 前置条件都有来源，不是凭空成立。
- 前置条件需要用户动作时，已经转化为需求。
- 关联需求已列出，并且都有故事覆盖。
- 新需求都有归属用户。
- 故事描述覆盖所有可观测变化，并写清这些信息对用户的作用。
- 不跟软件交互的环节写清楚，并与前后操作衔接。

### 3. 概念与功能提取

写故事时，识别用户能感知到的概念类和系统变化：

- 故事中出现的业务对象，是否为新的概念类？
- 新概念类是否有用户能感知且有用的属性？
- 概念类之间是否独立？
  - 独立概念：分别建模。
  - 同一动作产生、不能独立管理的从属概念：归入主概念。
- 每个用户可观测的系统变化，是否对应一个功能？
- 功能是用户发起还是系统发起？
- 功能是否只对应一个用户能区分的系统变化？
- 功能是否可以继续拆分？

把新概念补进领域模型，把新功能放到对应子系统，并规划功能集。

检查点：

- 每个故事步骤要么落到一个功能，要么是不跟软件交互的环节。
- 每个功能都能追溯到至少一个故事。
- 每个功能都改变一个用户可感知的概念或状态。
- 每个新概念都有归属，不重复、不遗漏。
- 每个功能都属于一个功能集。
- 每个功能集都属于一个子系统。

### 4. 功能集检查

对每个功能集：

- 它是否围绕一个独立概念？
- 是否混入了独立概念的功能？有就拆出去。
- 是否把同一动作产生、不能独立管理的从属概念错误拆出去？有就合并回来。
- 功能集内部是否有职责重叠？需要合并就合并，需要拆分就拆分。
- 对功能集所服务的需求和故事，所需的能力是否齐全？
  - 不是要求每个功能集都有完整 CRUD。
  - 而是故事需要的操作必须存在。例如故事要求创建后还能查到，就不能只有创建没有查询。
- 功能集是否有明确边界，不属于它的独立概念是否写清？

检查点：

- 功能集围绕独立概念。
- 没有混入独立概念。
- 没有错误拆出从属概念。
- 对所属故事，闭环成立。
- 边界清晰。

### 5. 功能检查

对每个功能：

- 是否有明确、用户可观测的系统变化？
- 是否只对应一个用户能区分的变化？
- 是否需要拆成多个功能？
- 发起方写得是否正确？
- 用户发起的功能是否有瞬时反馈？系统发起的功能是否没有反馈？
- 功能是否有故事覆盖？没有就补故事。
- 功能是否归属一个功能集？
- 功能是否落到一个子系统？
- 功能名称是否唯一？

系统发起的功能必须有故事覆盖。用观察或受益该结果的用户故事覆盖，例如“买家查看订单已被取消”；不创建“系统故事”。

检查点：

- 每个功能都有故事覆盖。
- 每个功能都有可观测变化。
- 每个功能只做一件事。
- 每个功能都有唯一归属。
- 没有孤立功能。

### 6. 子系统检查

对每个子系统：

- 是否是用户可感知的软件或入口，例如 Web 端、移动端？
- 是否由多个功能集组成？
- 功能集是否共同完成至少一个端到端目标？
- 是否写清与其他子系统的关系？
- 边界是否清楚，不包含的独立能力是否写明？
- 每个功能集是否都归属一个子系统？
- 是否有功能集悬空？

### 7. 固定点检查

完成一轮 1–6 后，重新扫描：

- 有没有新用户肖像？
- 有没有新需求？
- 有没有新故事？
- 有没有新前置条件需求或关联需求？
- 有没有新概念？
- 有没有新功能？
- 有没有新功能集？
- 有没有新子系统？
- 有没有功能没有故事、故事没有功能、功能没有功能集、功能集没有子系统？
- 有没有关联需求没有故事覆盖？
- 有没有前置条件需要用户动作但没有对应需求？
- 有没有台账条目仍是 `缺口` 或 `待确认`？

如果还有任何一项，回到对应步骤继续。

只有当一整轮不再产生任何新项，并且所有台账条目都是 `已覆盖`，才允许进入提交检查。

## 各项写作规则

### 领域模型

- 每项是一个用户能感知的概念类，用名词或名词性短语。
- 属性必须用户可感知、对满足用户需求有用。
- 独立概念分别建模；同一动作产生、不能独立管理的从属概念归入主概念。
- 不写功能、页面、技术字段和数据库实现。

### 用户肖像

- 用户肖像是从用户群体抽象出的假想代表，不是真实个人。
- 完全相同的用户合并；需要针对不同类型用户区分设计时拆出新用户。
- 固定字段：姓名、年龄、基本状况、爱好、职业、典型场景、诉求、主次。
- 每个用户至少一个需求，每个主要用户至少对应一个项目目标或核心故事。

### 故事

- 一个故事只满足一个需求；用户所有可能产生的需求都要有故事覆盖。
- 前置条件要写清；前置条件需要用户动作时，转化为需求。
- 故事描述要覆盖所有可观察反馈和变化，说明这些信息对用户的作用。
- 关联需求要列出，并确保有故事覆盖。
- 不写交互步骤、页面控件、业务规则和技术实现。

### 功能

- 用户发起或系统发起，产生用户可观测的系统变化。
- 一个功能一个可观测变化；用户能区分的变化要拆开。
- 粒度按用户认知：用户只能看到最终产出时，最终产出可以是一个功能；能看到中间状态时，中间状态分别成为功能。
- 用户发起的功能写瞬时反馈；系统发起的功能不写反馈。
- 功能必须有故事覆盖，必须属于一个功能集和一个子系统。

### 功能集

- 通常围绕一个独立概念组织。
- 独立概念分别成集；同一动作产生、不能独立管理的从属概念归入同一集。
- 不要求完整生命周期；闭环只要求覆盖所属故事需要的操作。
- 功能只作为子项，不在正文罗列；故事是顶层章节。
- 边界写清哪些独立概念不属于本功能集。

### 子系统

- 用户可感知的软件或入口，例如 Web 端、移动端。
- 由多个功能集组成，完成至少一个端到端目标。
- 写清覆盖用户、闭环目标、与其他子系统的关系和边界。
- 不是业务领域、代码模块、服务或部署单元。

## 写入文档

1. 用 `document`，`action = "draft_open"`，`kind = "requirements"` 打开草稿；没有草稿时 `draft_create`；保留 `revision`。
2. 按文档顺序写入：领域模型 → 用户肖像 → 故事 → 子系统 → 功能集 → 功能 → 功能描述。
3. 多项项用 `add` 并传 `title`；单次章节用 `update_text`；调整用 `move` / `delete`；改多项标题用 `update_title`。
4. 每次操作带 `kind = "requirements"`、`expected_revision` 和锚点；使用最新 revision。
5. 被审查打回后，读取批注，逐条修改并立即 `resolve_annotation`。

## 提交前门槛

只有同时满足才能调用 `completed`：

- 台账全部是 `已覆盖`，没有 `缺口` 或 `待确认`。
- 每个项目目标都有“目标 → 用户需求 → 故事 → 功能 → 功能集 → 子系统”的完整链路。
- 每个用户肖像的每个需求至少有一个故事。
- 每个故事列出的关联需求都有故事覆盖。
- 每个前置条件都有来源；需要用户动作的前置条件已经转化为需求。
- 每个故事步骤要么落到一个功能，要么是不跟软件交互的环节。
- 每个功能都有用户可观测的系统变化，且只对应一个用户能区分的变化。
- 每个功能都有故事覆盖，并属于一个功能集和一个子系统。
- 每个功能集围绕独立概念，没有混入独立概念。
- 每个功能集对它服务的 stories 所需能力闭环；不要求完整 CRUD。
- 每个子系统是用户可感知的软件，功能集形成端到端闭环。
- 没有空白的必需章节，没有孤立项。
- `validate` 没有 error。
- 所有批注已处理。

## 缺失信息

- 缺关键决定时，用 `issue_comment` 提出具体问题。
- 结束本轮，等待人类回复。
- 不要带着关键缺口调用 `completed`。

## 被审查打回后

1. 用 `task_get` 读取任务详情和打回原因。
2. 用 `annotations_list` 读取全部批注。
3. 用 `content` / `toc` 读取当前草稿和锚点。
4. 逐条判断批注是否成立；成立的按锚点修改，不成立的写明理由。
5. 每处理完一条立即 `resolve_annotation`。
6. 重新执行固定点检查和提交前门槛，再 `validate` 和 `completed`。

## 常见错误

- 只做局部用户、故事或功能，就认为分析完成。
- 不维护台账，不检查目标、用户需求、关联需求和功能的覆盖。
- 不展开前置条件产生的需求，例如“已登录”没有对应“注册”“登录”。
- 不展开关联需求，例如“购买”没有“退货”故事。
- 新需求没有归属用户，或发现新用户却不创建用户肖像。
- 把多个用户可区分的系统变化合并成一个功能。
- 把独立概念并入同一个功能集，或把同一动作产生的从属概念错误拆出。
- 要求功能集覆盖完整 CRUD，而不是按所属故事判断闭环。
- 系统发起的功能没有故事覆盖，或硬写反馈。
- 只检查字段格式，不检查跨章节链路。
