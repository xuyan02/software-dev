# UI 设计技能

## 目标

为需求文档中的每个功能补全 UI 设计。UI 设计是功能下的图片列表，按交互设计描述的顺序排列；目前不支持动画。每个图片项正文写 `名称：` 和 `链接：` 两行。

## 输入

每一轮开始前重新读取：

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
5. `document`，`action = "toc"`，`kind = "requirements"` 读取目录和锚点。
6. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取批注。
7. `task_allowed_operations` 确认当前允许的操作。

内容规则以《需求文档写作说明书》为准。

## 工作流程

1. 用 `document`，`action = "draft_open"`，`kind = "requirements"` 打开草稿；没有草稿时 `draft_create`；保留 `revision`。
2. 从目录找出所有功能，记录每个功能的锚点，以及功能正文中的 `交互设计：` 行。
3. 对每个功能：
   - 读取交互设计，确认页面、区域、控件和关键状态的顺序。
   - 为需要界面的页面和状态准备图片引用。
   - 在功能锚点下用 `action = "add"` 添加图片项；`title` 传图片名称，正文写 `名称：…` 和 `链接：…`（或资产 ID）。
   - 图片顺序与交互设计描述的顺序一致。
4. 每批修改后用 `action = "validate"` 校验，修复所有 error。
5. 处理已有批注；能改的改，不能改的写明理由并 `resolve_annotation`。
6. 调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "completed"`。

## 写什么

- **图片列表**：每个功能一个列表，每项一张图片，正文按 `名称：`、`链接：` 两行写。
- **顺序**：按交互设计中页面和状态的顺序排列。
- **覆盖**：覆盖交互设计中的页面和关键状态，包括默认、加载、空、错误和成功状态。

## 不写什么

- 动画、动图、帧序列和动画说明；目前不支持。
- 视觉规范的文字描述，例如颜色、字体、字号、间距、圆角和组件样式。
- 页面结构、区域层级、跳转关系和控件行为；这些属于交互设计。
- 交互步骤、加载和错误提示的交互逻辑；这些属于交互设计。
- 业务规则、系统结果和状态变化明细；需求文档不写。
- 技术实现、接口、数据库和前端框架。
- 指标、团队、排期和人力。
- 只有“见设计稿”而没有具体图片的引用。

## 检查

- 每个需要界面的功能是否都有图片列表？
- 图片顺序是否与交互设计描述的顺序一致？
- 图片是否覆盖交互设计中的页面和关键状态？
- 是否混入了动画、视觉规范、页面结构、控件行为或业务规则？
- 是否用“见设计稿”代替了具体图片引用？
- 每个图片项是否按 `名称：`、`链接：` 两行写？

## 缺失信息

- 缺图片、页面或状态时，用 `issue_comment` 提问并结束本轮。
- 不要编造图片资产或设计稿链接。

## 被审查打回后：按标注修改

### 1. 读取

- 用 `task_get` 读取任务详情和打回原因。
- 用 `action = "annotations_list"`，`kind = "requirements"` 读取全部批注。
- 用 `action = "content"` 和 `action = "toc"`，`kind = "requirements"` 读取当前草稿全文和锚点。
- 用 `action = "draft_open"` 打开草稿，保留最新 `revision`。

### 2. 建立批注清单

逐条记录批注 id、`anchor_key`、引用原文、内容建议和状态。同一功能的图片列表问题也要逐条处理：每处理完一条立即 resolve，再处理下一条。

### 3. 逐条判断和处理

每处理完一条批注，立即 resolve 该批注，再处理下一条。不要先改完全部批注再统一 resolve。

对每条批注：

1. 找到 `anchor_key` 对应的功能或图片项；锚点失效时按引用原文和所处功能定位。
2. 对照《UI 设计技能》《需求文档写作说明书》和该功能的交互设计，判断批注是否成立。
3. **成立**：在对应功能下调整图片列表。
   - 用 `add` 添加图片项并传 `title`，用 `move` 调整顺序，用 `delete` 删除错误图片。
   - 图片顺序与交互设计的页面和状态顺序一致。
   - 每项正文按 `名称：`、`链接：` 两行写，标题与图片名称一致；只放静态图片。
4. **不成立或与说明书冲突**：不修改正文，在 `resolve_annotation` 里写清理由。
5. **当前草稿已经改好**：直接 `resolve_annotation`，说明已处理。
6. **缺少图片或资产**：不要编造图片链接或资产 ID；不修改正文，在 `resolve_annotation` 里说明无法确认的原因。

只修改功能下的 UI 设计图片列表。批注要求修改需求分析或交互设计时，不改正文，在 resolve 说明里写明属于需求分析或交互设计任务。

### 4. 标记已处理

- 每处理完一条批注，立即用 `action = "resolve_annotation"` 标记，再处理下一条。
- `resolution` 写一句具体说明，例如“已按交互设计顺序补充错误态图片”。
- 不要攒到最后批量 resolve，也不要在没有修改的情况下 resolve。
- 不把批注当成不存在。

### 5. 复查

- 重新用 `action = "annotations_list"` 读取批注，确认没有未处理的 open 批注；仍有则继续处理。
- 重新用 `action = "content"` 检查图片列表顺序和覆盖范围。
- 用 `action = "validate"` 校验，修复所有 error。
- 校验通过后调用 `task_operation`，`operation = "completed"` 再次提交。
