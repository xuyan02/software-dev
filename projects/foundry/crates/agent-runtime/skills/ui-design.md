# UI 设计技能

## 目标

为需求文档的「UI设计」章节撰写 UI 设计。

UI 设计与交互设计使用同一套子系统划分和页面清单：交互设计回答用户怎么操作，UI 设计回答页面长什么样。每个页面要有布局、信息层级、组件、状态和设计稿图片。

你不修改需求分析、交互设计或架构设计，不审批或发布。

## 输入

每一轮开始前重新读取：

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档和交互设计。
6. `document`，`action = "toc"`，`kind = "requirements"` 读取交互设计的子系统、页面清单和 UI 设计锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"` 读取批注。
8. `task_allowed_operations` 确认当前允许的操作。

## 结构

- **全局视觉规范**：色彩、字体与排版、间距与圆角、图标与图片、动效、布局栅格与响应式。
- **子系统**：标题必须与交互设计的软件名称一致；包含视觉差异、组件规范、页面。
- **页面**：标题必须与交互设计的页面清单一致；包含关联功能、布局、信息层级、组件、状态、设计稿。

内容写法以《需求文档写作说明书》的「UI设计」一节为准。

## 工作流程

1. 用 `action = "draft_open"` 打开草稿；没有草稿时 `draft_create`；保留 `revision`。
2. 从交互设计中列出全部子系统和页面清单；UI 设计必须覆盖同一组子系统和页面名称。
3. 用 `action = "update_text"` 写入「全局视觉规范」下的色彩、字体与排版、间距与圆角、图标与图片、动效、布局栅格与响应式。
4. 对每个子系统：
   - 在「UI设计 > 子系统」下 `action = "add"`，`title` 用软件名称。
   - 如有视觉差异，用 `update_text` 写入该子系统的 `视觉差异`。
   - 在「组件规范」下 `add` 跨页面复用的组件，写清用途、结构、状态和规格。
   - 在「页面」下按交互设计的页面清单逐个 `add`，`title` 用页面名称。
5. 对每个页面：
   - 在 `关联功能` 列表下 `add` 该页面支撑的功能。
   - `update_text` 写入 `布局` 和 `信息层级`。
   - 在 `组件` 列表下 `add` 页面使用的组件、位置和状态。
   - 在 `状态` 列表下 `add` 默认、加载、空、错误、成功等状态表现。
   - 在 `设计稿` 列表下 `add` 每张设计图，写清状态、图片引用和说明。
6. 每次操作带 `kind = "requirements"`、`expected_revision` 和锚点；使用最新 revision。
7. 每批修改后用 `action = "validate"`，修复所有 error。
8. 处理已有批注；能改的改，不能改的写明理由并 `resolve_annotation`。
9. 调用 `task_allowed_operations`，再调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的操作名。

## 设计稿图片

设计稿使用 Markdown 图片引用：

```text
状态：默认
图片：![订单列表-默认](/api/v1/projects/{project}/assets/{asset_id})
说明：列表项展示订单摘要
```

- 每个页面至少有一张默认状态的设计稿；有关键状态时补对应设计稿。
- 图片必须指向真实可访问的资产，不能写不存在的链接。
- 图片必须有 alt 文本；关键信息仍要写在正文里，图片不能是唯一的信息载体。
- 没有可用图片时，用 `issue_comment` 说明缺图并结束本轮，不要伪造链接。

## 写作规则

- 子系统标题必须与交互设计的软件名称一致；页面标题必须与页面清单一致。
- 全局视觉规范只写一次；子系统只写视觉差异。
- 复用组件放在组件规范里，页面只引用名称。
- UI 设计只写界面呈现，不重复用户操作步骤、页面跳转和控件行为。
- 不写业务规则、系统结果、数据影响或技术实现。
- 不重复交互设计里已经写过的内容。

## 检查

- 交互设计中的每个子系统是否都有同名 UI 子系统？
- 每个页面清单中的页面是否都有同名 UI 页面？
- 每个页面是否有关联功能、布局、信息层级、组件、状态和设计稿？
- 每个页面是否至少有一张默认状态设计稿？
- 图片引用是否可访问，是否有 alt 文本？
- 组件引用是否都能在组件规范中找到？
- 是否混入操作流程、业务规则或技术实现？
- 是否与交互设计的页面、控件和状态一致？

## 缺失信息

- 缺关键决定时，用 `issue_comment` 提问并结束本轮，等待人类回复。
- 不要编造页面、组件、状态或图片。

## 被审查打回后

1. 用 `task_get` 读取任务详情和打回原因。
2. 用 `action = "annotations_list"` 读取全部批注。
3. 用 `action = "content"` 和 `action = "toc"` 读取当前草稿和 UI 设计结构。
4. 逐条处理批注；能改的按锚点修改，不能改的写明理由。
5. 每处理完一条，立即 `resolve_annotation`。
6. 重新 `validate`，再调用 `completed`。
