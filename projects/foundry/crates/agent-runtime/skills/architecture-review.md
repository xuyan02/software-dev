# 架构设计审查技能

## 目标

审查架构设计是否完整、一致、可实现，并能支撑需求。只审查，不修改文档，不审批或发布。

## 审查前必须读取

1. `task_links_list` 找到当前任务的 Issue。
2. `issue_get` 读取 Issue 正文和全部评论。
3. `project_get` 读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"` 读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"` 读取需求文档。
6. `document`，`action = "content"`，`kind = "architecture"` 读取架构设计。
7. `document`，`action = "toc"`，`kind = "architecture"` 读取目录和锚点。
8. `document`，`action = "annotations_list"`，`kind = "architecture"` 读取已有批注。
9. `task_allowed_operations` 确认当前允许的操作。

内容规则以《架构设计说明书》为准。

## 审查方法

先建立支撑关系：

```text
需求：用户 / 故事 / 功能 / 功能集 / 子系统
  → 架构：组件 / 接口 / 数据 / 部署 / 质量属性 / 决策
```

再检查：

### 1. 需求支撑

- 每个子系统是否有对应组件或运行单元？
- 每个功能集是否有组件承接？
- 关键用户故事是否能在架构中走通？
- 是否有需求没有架构承接，或架构组件没有需求来源？

### 2. 组件

- 每个组件是否有明确职责，且职责内聚？
- 是否按代码目录或技术分层拆组件？
- 组件之间的依赖是否清楚，是否有循环依赖或职责重叠？
- 每个组件是否说明接口、依赖和数据？
- 是否有组件没有需求来源，或需求没有组件承接？

### 3. 接口与契约

- 每个接口是否说明提供方、消费方、版本和兼容性？
- 是否有跨组件或外部系统的契约没有写？
- 契约是否与组件职责一致？
- 是否只写“见接口文档”而没有具体契约？

### 4. 数据与存储

- 数据所有权是否清楚？
- 一致性要求和迁移策略是否说明？
- 是否与组件职责冲突？
- 是否写成数据库表结构或 ORM 实现？

### 5. 部署与运行

- 运行时单元、环境和部署边界是否清楚？
- 可观测性要求是否说明？
- 是否与组件和依赖矛盾？
- 是否写成具体部署脚本？

### 6. 质量属性

- 每条质量属性是否有场景、度量、目标和验证方式？
- 是否可度量、可验证？
- 是否覆盖需求中的关键非功能要求？
- 是否写“高性能”“高可用”而没有判断标准？

### 7. 关键决策

- 每条决策是否写清背景、选项、结论、后果和影响范围？
- 是否只有一个选项而没有说明“无替代方案”的理由？
- 决策是否与组件、接口、数据、部署矛盾？
- 不可逆决策是否说明批准人？

### 8. 技术债与风险

- 技术债是否有位置、影响、风险和偿还计划？
- 风险是否有事件、影响、缓解和负责人？
- 是否把普通任务或已发生问题当成风险？
- 是否有高风险债务没有进入发布门禁？

### 9. 一致性与可实现性

- 组件、接口、数据、质量属性和决策之间的名称是否一致？
- 架构是否违反项目约束或非目标？
- 是否依赖未定义的外部系统或能力？
- 是否把需求、UI 或代码实现写成架构？
- 架构是否足以指导后续设计和实现？

## 输出

用 `document`，`action = "annotate"`，`kind = "architecture"`：

- `anchor`：用 `toc` 得到的章节锚点。
- `quote`：引用原文。
- `body`：具体缺陷 + 违反的规则 + 修改建议 + 通过条件。

只写必须修改的问题；只要写了标注，就必须拒绝。每条标注必须能写清通过条件。已解决或不影响结论的问题不重复报。

提交结论：

- 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `review_rejected` 操作名。
- 一条标注都没写时，才调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `review_approved` 操作名。

## 不要做的事

- 不修改文档。
- 不审查代码实现。
- 不写建议性、非阻塞标注。
- 不在写了标注后仍然通过。
- 不审批、不发布。
