# 需求可行性审查技能

## 目标

判断需求文档在现有约束下是否可交付：技术可行、依赖可控、成本可接受、风险可管理、范围可完成、结果可验证。

本技能只做可行性审查，不修改文档，不审批或发布，也不做架构设计和技术选型。可行性结论必须来自逐项推演，不能只凭“技术上应该可以做”。

## 审查前必须读取

每一轮开始前重新读取，不依赖上一轮记忆：

1. `task_links_list`：找到当前任务的 Issue。
2. `issue_get`：读取 Issue 标题、正文和全部评论。
3. `project_get`：读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"`：读取项目文档，重点是目标、非目标、约束和风险。
5. `document`，`action = "content"`，`kind = "requirements"`：读取需求文档全文。
6. `document`，`action = "toc"`，`kind = "requirements"`：读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"`：读取已有批注，避免重复。
8. `task_allowed_operations`：确认当前任务允许哪些操作。

内容规则以《需求文档写作说明书》为准；一般逻辑审查以《需求文档审查技能》为准；本技能只判断可行性。

## 可行性分析模型

对每个功能、功能集、子系统和故事，从八个维度推演：

```text
技术可行性
依赖可行性
成本可行性
风险可行性
范围可行性
可验证性
约束符合性
替代方案
```

## 可行性通过的最低标准

满足以下条件即可通过，不要求最优：

- 存在一条在项目约束内可交付的路径；
- 关键依赖有负责人、计划或降级方案；
- 主要风险有缓解措施和负责人；
- 范围可以完成，或可以分期完成；
- 系统变化可观察、可验证。

“可以更好”“不是最优”“换一种做法更好”不是阻塞理由，也不写标注。

## 审查收敛规则（防止无限驳回）

可行性审查的目标是判断“是否存在可交付路径”，不是不断提出改进项。必须遵守：

1. **只拦不可交付**：只有“在现有约束下无法交付”才写标注。可以更好、不是最优、换一种做法更好，都不写标注。
2. **每条标注必须有通过条件**：批注里写清“满足什么条件可以通过”。写不出通过条件的不写标注。
3. **不重复**：先读已有批注和当前文档；已经解决的问题不得再提；同一问题只保留一条批注。
4. **不写建议性标注**：替代方案、优化建议、可分期范围、已记录的依赖和已有缓解的风险，都不写标注。
5. **通过优先**：先找可行路径。关键依赖有负责人、计划或降级，主要风险有缓解，范围可完成，就应通过；不要求所有未知消失。
6. **未知事项**：能记录为依赖或风险并有负责人和计划的，不写标注；完全未知且无负责人、无计划的，标注一次，并写明需要谁决定。
7. **多轮收敛**：第一次拒绝后，下一轮只检查上次标注项是否解决，不新增非阻塞要求；不得因为出现新的优化想法再次拒绝。
8. **人类决策项**：标注项如果只能由人类或外部决定，批注写明决策项和决策人，交给人工评审；不要对同一项反复拒绝。
9. **不做技术选型**：不因架构、技术栈或实现方式偏好拒绝；只判断现有条件下是否可交付。
10. **决策一致**：只要写了标注，就必须拒绝；一条标注都没写才通过。

## 一、技术可行性

逐功能问：

- 这个系统变化需要什么能力？
- 现有技术、平台或已有系统是否具备这个能力？
- 是否需要研究、试验或尚未确定的技术？
- 行为是否确定、可实现、可重复？
- 需要的数据是否存在、可获得、质量是否足够？
- 是否需要集成外部系统？集成的协议、权限和边界是否明确？
- 是否有性能、规模、实时性、离线、设备或网络限制？项目约束是否覆盖？
- 是否涉及数据迁移、历史数据兼容或双写？
- 是否涉及安全、隐私、审计或合规要求？

判断规则：

- 需要的能力未定义、未具备或依赖未知研究：至少是阻塞风险。
- 行为无法确定或无法重复：不可验证，阻塞。
- 数据不存在或质量不明：标记为依赖或风险，必要时阻塞。
- 外部集成没有接口、权限或负责人：阻塞。

不要做技术选型，只判断“现有条件是否足以实现”。

## 二、依赖可行性

列出每个功能或功能集依赖的外部条件：

- 外部系统、API、数据源；
- 其他团队、审批、采购、许可证；
- 平台、设备、网络、运行环境；
- 第三方服务或供应商；
- 组织流程或人工环节。

对每个依赖问：

- 谁负责？
- 当前状态是什么：已具备、已承诺、未知、不可用？
- 有没有契约、接口或服务水平？
- 失败时有什么降级或替代方案？
- 依赖是否在项目约束或风险中记录？

判断规则：

- 关键依赖未知、无负责人或无降级方案：阻塞。
- 依赖可用但未记录：要求补充到约束或风险；不写标注。
- 外部能力不能变成跨项目需求；只能记录为依赖、约束或风险。

## 三、成本可行性

从交付和运行两个角度评估：

**交付成本**

- 功能数量、功能集数量、子系统数量是否与约束匹配？
- 是否需要大量集成、迁移、定制或数据清理？
- 是否需要新的团队、设备、采购或培训？
- 范围是否明显超过现有时间、人力或预算约束？

**运行成本**

- 高频故事是否依赖大量人工核对、录入或交接？
- 是否需要持续运维、监控、支持或人工审核？
- 数据存储、计算、外部调用是否带来持续成本？
- 错误处理是否会造成大量返工？

判断规则：

- 没有来源的数字不写；没有数据时用“高/中/低”做相对判断。
- 成本明显超出约束且没有替代方案：阻塞。
- 成本高但有明确约束依据或缓解方案：记录为风险；不写标注。
- 需求审查技能负责“操作成本是否合理”；本技能判断“剩余成本在约束下是否可接受”。

## 四、风险可行性

逐项检查交付、质量、安全、运维、外部依赖、采用和合规风险：

- 这个需求最可能在哪里失败？
- 失败的概率和影响如何？
- 有没有缓解措施？
- 谁负责？
- 风险是否已经记录在项目文档中？

判断规则：

- 高风险没有缓解措施或负责人：阻塞。
- 风险已识别但缓解措施不具体：要求补充，不写标注。
- 风险不在项目文档中，但需求明显依赖它：要求补充到项目风险或约束。
- 不把已解决的事项写成风险；不编造概率和影响数字。

## 五、范围可行性

检查：

- 范围是否过大，无法在约束内完成？
- 是否把多个目标或多个用户需求混在一起？
- 是否有开放式的“持续优化”“全面提升”之类无法完成的范围？
- 功能集和子系统是否职责重叠，造成重复建设？
- 是否可以分期交付，先做核心闭环，再做扩展？
- 非目标是否被悄悄实现？
- 范围是否与项目目标一致，没有做无关能力？

判断规则：

- 范围明显超出约束且没有分期方案：阻塞。
- 存在可以推迟的非核心内容：记录到分期计划，不写标注。
- 跨越非目标：阻塞。

## 六、可验证性

逐功能问：

- 系统变化是否可观察？
- 反馈是否足以让用户确认成功？
- 故事的成功确认是否与功能反馈一致？
- 是否能用现有手段验证，而不需要未定义的工具或数据？
- 是否有无法判断是否达成的模糊目标？

判断规则：

- 无法观察或无法验证：阻塞。
- 反馈不足但可以补充：不写标注。
- 只有“提升体验”“优化流程”这类模糊目标：阻塞，要求改成可判断的结果。

## 七、约束符合性

逐条对照项目文档：

- 目标是否被满足？
- 非目标是否被违反？
- 约束是否被违反？
- 风险是否被忽略？
- 是否假设了不存在的资源、权限、数据或外部承诺？
- 是否把技术方案、架构或采购决策当成了需求前提？

判断规则：

- 违反非目标或硬约束：阻塞。
- 假设未确认：要求回到 Issue 确认，不能默认成立。
- 技术方案被当成需求前提：要求改成需求结果，方案留给设计阶段。

## 八、替代方案

在判定不可行或成本过高前，先问：

- 现有功能、功能集或子系统能否满足这个需求？
- 能否复用已有数据、能力或流程？
- 能否用人工环节或外部系统替代？
- 能否缩小范围、分期交付或先做最小闭环？
- 是否真的需要新建功能，而不是扩展现有功能？
- 是否存在更简单的实现路径，而不改变需求结果？

判断规则：

- 有更简单的替代方案且不降低需求：作为修改建议。
- 替代方案会改变需求、范围或验收：不能擅自替换，要求回到 Issue 确认。
- 替代方案涉及技术选型或架构：只描述可行性影响，不做选型。

## 可行性推演示例

**技术不可行**

> 需求：移动端离线实时同步 10 万台设备的全部数据。
>
> 项目约束：移动端存储和网络受限，没有离线同步基础设施。

需要的能力与现有条件冲突。要么缩小数据范围或改为在线，要么把离线同步基础设施列为依赖并确认，否则阻塞。

**依赖缺失**

> 需求：下单后调用支付网关完成扣款。
>
> 文档没有支付网关、接口、权限、负责人和失败处理。

关键依赖缺失。要求补充依赖状态、契约和降级方案；未确认前阻塞。

**成本不合理**

> 发生频率：高。
>
> 故事：每笔订单都需要主管人工复核后才能在系统确认。

高频流程依赖人工复核，运行成本高。检查复核是否必要；如果必要，是否有批量或抽样方案；如果没有，标记为阻塞成本问题。

**范围过大**

> 一期同时覆盖 Web 端、移动端、开放 API、离线模式和第三方 marketplace。

范围明显超出常规一期约束，且没有分期。建议先完成核心闭环，其余分期；如果不能分期，阻塞。

**不可验证**

> 功能：提升用户操作体验。

没有可观察的系统变化，无法验证。要求改成具体的系统结果，例如减少某个操作步骤或返回明确状态。

**违反非目标**

> 项目非目标：不做移动端。
>
> 需求：新增移动端扫码收货子系统。

直接违反非目标。阻塞，回到项目目标或 Issue 确认范围。

**替代方案**

> 需求：新建一个独立报表功能。
>
> 现有功能集已经有查询和导出，只是筛选条件不同。

可能不需要新功能。建议扩展现有查询/导出；如果替代会改变需求，回到 Issue 确认。

## 审查输出

### 每条问题的写法

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：用 `toc` 得到的章节锚点。
- `quote`：引用原文。
- `body`：可行性缺陷 + 推演依据 + 具体修改建议 + **通过条件**。

每条批注只写一个可行性问题，不写风格、措辞或个人偏好。

### 标注与决策

**阻塞问题**必须同时满足两个条件：

1. 不解决就无法在现有约束下交付；
2. 能写清“满足什么条件可以通过”。

阻塞问题包括：

- 需要的能力未定义、未具备或依赖未知研究。
- 关键外部依赖未知、无负责人、无契约或无降级方案。
- 成本明显超出约束且无替代或缓解方案。
- 高风险没有缓解措施或负责人。
- 范围明显超出约束且不能分期。
- 违反非目标或硬约束。
- 功能不可观察、不可验证。
- 需求依赖未确认、且会直接导致无法交付的假设。

写不出通过条件的问题，不要写标注。

**不要写非阻塞标注**：

- 依赖已具备但未记录、风险缓解措施不具体、可分期但非必须、可补充反馈、有更简单替代方案、未知事项已有负责人/计划/降级，都不写标注。
- 只是可以做得更好、更优或更简单，不写标注。
- 不喜欢、不是最优、换一种做法更好，不写标注。

## 审查流程

1. 读取输入，建立可行性矩阵：功能/功能集/子系统 × 技术、依赖、成本、风险、范围、验证、约束。
2. 如果是多轮审查，先只看上次标注项是否解决，再决定是否继续；不新增非阻塞要求。
3. 逐功能做技术可行性推演。
4. 逐依赖做可用性、负责人、契约和降级推演。
5. 做交付成本和运行成本推演。
6. 做风险推演，检查缓解措施和负责人。
7. 做范围推演，检查约束、非目标和分期可能。
8. 做可验证性和约束符合性检查。
9. 在做阻塞判断前，先检查替代方案。
10. 汇总必须修改的问题；不值得拒绝的不写标注。
11. 对每条拟标注项写通过条件；写不出通过条件的不写标注。
12. 标注项如果只能由人类或外部决定，写明决策项和决策人，交给人工评审，不重复拒绝。
13. 用锚点写批注。
14. 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "rejected"`。
15. 一条标注都没写时，才调用 `task_operation`，`operation = "approved"`。
16. 不修改文档，不审批，不发布。

## 审查质量门槛

- [ ] 每个功能都做过技术可行性推演。
- [ ] 每个外部依赖都有状态、负责人、契约或降级判断。
- [ ] 交付成本和运行成本都评估过。
- [ ] 每个高风险都有缓解措施和负责人，或被标记为阻塞。
- [ ] 范围与项目约束、非目标对照过。
- [ ] 每个功能都检查过可观察性和可验证性。
- [ ] 判定不可行前检查过替代方案。
- [ ] 每条批注都有锚点、原文、缺陷、推演依据、修改建议和通过条件。
- [ ] 每条标注都写清了通过条件；写不出通过条件的不写标注。
- [ ] 没有重复提出已经解决的问题。
- [ ] 没有把优化建议、替代方案或可分期范围写成标注。
- [ ] 多轮审查只检查上次标注项，没有不断扩大范围。
- [ ] 人类决策项已写明决策人和所需决定，没有反复拒绝同一项。
- [ ] 没有编造数字、概率或成本估算。
- [ ] 没有纯风格或个人偏好问题。
- [ ] 结论与标注一致：写了标注就拒绝，没有标注才通过。

## 常见审查错误

- 只判断“技术上可能”，不检查依赖、成本、风险和范围。
- 把未知能力当成已具备。
- 忽略运行、维护、人工审核和返工成本。
- 忽略数据、安全、隐私和合规要求。
- 不检查非目标和硬约束。
- 不做替代方案检查，直接要求新建能力。
- 编造成本、概率或性能数字。
- 把架构选型当成可行性结论。
- 把“可以更好”“不是最优”当成阻塞。
- 重复提出已经解决的问题。
- 多轮审查不断增加新的非阻塞要求。
- 把优化建议写成标注。
- 对人类或外部决策项反复拒绝。
- 报风格和措辞问题。
- 有标注时仍然通过。
