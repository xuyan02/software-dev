# 需求文档写作说明书

## 目录结构

```text
需求文档
├─ 用户
│  └─ 用户（多项，正文按固定字段写）
├─ 子系统
│  └─ 子系统（多项，正文按固定字段写）
│     └─ 功能集（多项，正文按固定字段写）
│        ├─ 故事
│        │  └─ 故事（多项，正文按固定字段写）
│        └─ 功能
│           └─ 功能（多项，正文按固定字段写）
│              └─ 图片（多项，正文按固定字段写）
```

所有固定字段都写在项正文里，每行一个 `字段：值`；不要为字段创建子章节或标题。功能集下的「故事」「功能」只是分组标题，不是字段。

标题必须单独指定，不从正文推导：

- 用户标题用姓名。
- 子系统标题用软件名称。
- 功能集、故事、功能、图片标题用名称。

新增时通过 `add` 的 `title` 参数传入；已有项用 `update_title` 修改。单次章节和分组章节的标题固定，不能修改。

## 各项写什么

以下规则按文档结构逐项定义。

### 用户

#### 定位

用户是具体的使用者画像，用固定字段描述“谁在使用系统、他平时怎么做事、他想要什么”。用户为故事和功能提供被引用的对象；不是抽象角色。

#### 原则

1. **固定模板，正文不分字段**：每项用户只写一段正文，按固定字段逐行写成 `字段：值`；不把字段拆成子章节、子字段、表格或 JSON。基本状况和典型场景只在影响系统使用时才写。
2. **一个用户一项**：不把多个用户合并成一项，也不用“所有用户”“普通用户”这类泛称代替。
3. **诉求写需要，不写方案**：诉求是用户想获得的结果，不是功能、页面或技术方案。
4. **主次明确**：每项用户标注“主要”或“次要”；不限用户数量。
5. **系统相关**：基本状况和典型场景必须与系统使用有关；与系统无关的家庭、生活细节不写。
6. **与已确认信息一致**：画像细节可以补全，但不能与澄清结论冲突，也不编造真实人物或统计数据。

#### 写什么

每项用户正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **姓名**：用于引用，可以是化名，但一项只对应一个姓名。
- **年龄**：用户的年龄，写具体年龄或年龄段。
- **基本状况**（条件字段）：家庭、身体、经济、工作条件等中影响系统使用的部分；不相关不写。
- **爱好**：用户的爱好。
- **职业**：用户的职业或岗位。
- **典型场景**（条件字段）：用户平时怎么做事、在什么环境或节奏下使用系统；只写与系统有关的部分，不写目标、功能序列和异常分支。
- **诉求**：用户想从系统或工作中获得什么，写需求，不写功能。
- **主次**：写“主要”或“次要”。

用户标题使用姓名：新增时在 `title` 中传入姓名，修改时用 `update_title`。正文仍然保留一行 `姓名：…`，不要另建姓名标题。

#### 不写什么

- 权限、边界和使用频率。
- 与系统无关的基本状况、家庭生活、爱好细节和典型场景。
- 故事：明确目标、功能序列和异常分支。
- 功能、页面、交互流程、UI 布局。
- 技术实现、账号体系、权限模型的实现方式。
- 需求条目、验收标准、优先级。
- 固定字段之外的个人信息，例如性别、性格、履历。
- 把字段拆成子章节、子标题、表格或 JSON；字段只作为正文中的 `字段：值` 行。
- 没有来源的统计数据、引文、访谈记录和置信度判断。
- 组织架构、公司历史、行业背景。
- “所有用户”“普通用户”这类无法判断具体对象的泛称。
- 把多个用户合并成一项。

#### 判断标准

- 标题是否就是用户姓名？
- 姓名、年龄、爱好、职业、诉求、主次六项是否齐全，且没有添加模板外字段？
- 六项是否都写在用户项正文里，每行一个 `字段：值`，而不是拆成子字段或子章节？
- 基本状况和典型场景是否只在影响系统使用时才写？
- 典型场景是否被写成了故事，出现了目标、功能序列或异常分支？
- 姓名能否在文档内唯一定位这个用户？
- 诉求是否是用户需要，而不是功能或方案？
- 主次是否明确写了“主要”或“次要”？
- 是否混入了权限、边界或频率？
- 是否把多个用户合并成一项？

#### 正例

用户项正文（标题单独指定为“张伟”）：

> 姓名：张伟
> 年龄：35 岁
> 基本状况：需要轮班并照顾孩子，只能在交接班时集中处理单据。
> 爱好：钓鱼、看历史纪录片
> 职业：仓库管理员
> 典型场景：每天先巡库，再用纸质单据核对到货，收货后集中补录系统；常在走动和弱网环境下操作。
> 诉求：到货后能快速确认数量并找到可放库位，减少纸质单据核对。
> 主次：主要

#### 反例

**反例 1**

> 用户：仓库管理员

缺少姓名、年龄、爱好、诉求和主次，只剩一个职业名称。用户必须是具体画像，并按固定模板填写。

**反例 2**

> 姓名：张伟
> 权限：可修改库存，不能审批采购单。
> 边界：只负责自己所在的仓库。
> 频率：每天操作 3 次。

用户不写权限、边界和频率。这些内容属于功能或功能描述；用户项只写固定字段。

**反例 3**

> 诉求：一键导出报表，并支持批量删除。

这是功能和方案，不是诉求。诉求应写用户想获得的结果，例如“希望能快速汇总当日到货，减少手工抄录”。

**反例 4**

> 姓名：张伟
> 性别：男
> 性格：外向
> 履历：在本公司工作 10 年

这些是固定模板之外的字段。用户项只写姓名、年龄、基本状况、爱好、职业、典型场景、诉求和主次。

**反例 5**

> 用户：张伟和李娜，仓库管理员。

一项用户只能对应一个人。多个用户应分别成项，并各自标注主次。

**反例 6**

> 基本状况：家庭和睦，喜欢旅行。
> 典型场景：周末常和朋友聚会。

这些与系统使用无关。基本状况和典型场景只写会影响用户使用系统的部分。

**反例 7**

> 典型场景：用户先创建入库单，再扫码收货；库位不足时转到异常处理。

这是故事，有目标和功能序列，还写了异常分支。典型场景只描述用户平时怎么做事，例如“先巡库再收货，收货后集中补录”。

### 子系统

#### 定位

子系统是用户可感知的一个“软件”，例如“仓库管理系统 Web 端”“仓库管理系统移动端”。它由多个功能集组成，这些功能集共同形成闭环，提供完整的解决方案。子系统不绑定代码模块或部署单元。

#### 原则

1. **固定模板，正文不分字段**：每项子系统只写一段正文，按软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系、边界逐行写成 `字段：值`；不把字段拆成子章节或标题。
2. **用户可感知**：子系统有明确的用户入口、界面或使用形态，是一个用户能识别并使用的东西，不是代码模块、服务或技术分层。
3. **功能集闭环**：子系统包含的功能集必须能共同完成至少一个端到端的用户目标，形成完整解决方案；零散功能的集合不是子系统。
4. **覆盖用户写职业**：写仓库管理员、采购员这类职业，不写具体用户画像的姓名。
5. **功能集只作子项**：功能集作为子项维护，子系统正文不罗列功能集名称，也不展开功能细节。
6. **关系单独成字段**：与其他子系统的入口、渠道、共享能力、数据和流程衔接写成正文中的“与其他子系统的关系：”行；没有时写“无”。
7. **有依据**：来自项目文档、澄清 Issue 和已确认的结论；没有依据的划分不写。

#### 写什么

每项子系统正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **软件名称**：例如“仓库管理系统移动端”；标题单独用软件名称指定。
- **软件形态**：Web 端、移动端、桌面端等，以及用户通过什么入口或设备使用。
- **覆盖用户**：使用这个子系统的职业，例如“仓库管理员、采购员”。
- **闭环目标**：用户通过它完成哪些端到端目标，功能集如何共同形成完整解决方案。
- **与其他子系统的关系**：与哪些子系统共享数据、能力或流程，入口和渠道如何分工，各形态的差异；没有时写“无”。
- **边界**：不包含什么，哪些能力由其他子系统承载。

#### 不写什么

- 功能集名称清单；功能集只作为子项存在，不在正文罗列。
- 单个功能的行为、交互和 UI；这些放在功能集、功能及后续章节。
- 具体用户姓名或用户画像；覆盖用户写职业。
- 代码模块、服务、部署单元、技术栈、数据模型、接口或 API。
- 实现细节、算法、性能指标、数据库和基础设施。
- 项目文档已有的目标、非目标、约束和风险。
- 团队、组织架构、负责人、排期和人力。
- 没有来源的数字或规模。

#### 判断标准

- 标题是否就是软件名称？
- 软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系、边界是否齐全，且都写在项正文的 `字段：值` 行里？
- 用户能否识别这是一个可以使用的软件，而不是一个业务领域或技术模块？
- 其功能集能否共同完成至少一个端到端目标、形成闭环？
- 覆盖用户是否写的是职业，而不是具体用户姓名？
- 功能集是否只作为子项，正文没有罗列功能集或功能细节？
- 与其他子系统的关系是否单独写清；没有时是否写了“无”？
- 是否把“库存”“采购”这类业务领域、或代码服务误当成子系统？

#### 正例

> 软件名称：仓库管理系统移动端
> 软件形态：移动应用，仓库现场使用。
> 覆盖用户：仓库管理员。
> 闭环目标：完成从到货收货、上架到库存盘点的现场作业闭环。
> 与其他子系统的关系：与 Web 端共享库存和入库单数据；采购审批在 Web 端完成，移动端不提供。
> 边界：不含采购审批、账号管理和报表导出。

功能集作为子项存在：入库单管理、库位管理、库存盘点；子系统正文不罗列。

#### 反例

**反例 1**

> 子系统：库存

这是业务能力域，不是用户可感知的软件。库存能力应体现在具体子系统的功能集和功能中，例如“入库单管理”“库存盘点”。

**反例 2**

> 子系统：inventory-service，负责 /stock API 和库存表，依赖 Postgres。

这是实现和架构描述，不是需求。子系统只写软件形态、职业用户、闭环、与其他子系统的关系和边界，技术实现放到设计阶段。

**反例 3**

> 子系统：仓库管理系统移动端，包含入库单管理、库位管理、库存盘点。

功能集只作为子项存在，不在子系统正文罗列名称。正文应写软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系和边界。

**反例 4**

> 覆盖用户：张伟、李娜。

覆盖用户写职业，例如“仓库管理员、采购员”，不写具体用户画像的姓名。具体用户属于用户章节。

**反例 5**

> 与其他子系统的关系：调用 /api/inventory，依赖 Postgres 和消息队列。

这是技术依赖和接口，不是子系统关系。关系应写共享哪些数据或能力、入口和渠道如何分工、各形态的差异。

**反例 6**

> 子系统：仓库管理系统 Web 端，目标是把库存准确率提升到 99%，由 3 人团队在 Q3 完成。

这是指标、团队和排期，不是子系统描述。指标属于项目文档或后续验收，团队和排期不属于需求文档。

**反例 7**

> 子系统：仓库管理系统移动端，包含创建入库单、扫码和打印三个功能。

这些功能互不衔接，没有共同完成一个端到端目标。子系统应写清闭环目标，功能集必须能共同形成完整解决方案。

### 功能集

#### 定位

功能集是若干功能组成的有机整体，这些功能需要共同协作才能满足一个用户需求。单个功能通常不能独立产生用户价值；例如“创建入库单”不能单独构成“入库单管理”，还需要查询、修改和删除等功能的配合。

#### 原则

1. **固定模板，正文不分字段**：每项功能集只写一段正文，按名称、满足的用户需求、覆盖用户、协作关系、闭环位置、分界逐行写成 `字段：值`；不把字段拆成子章节或标题。
2. **共同满足一个需求**：功能集围绕同一个用户目标或业务对象组织，功能之间有明确的协作关系，不是任意功能的堆砌。
3. **集合才产生价值**：单个功能只完成局部系统变化；功能集组合起来才能满足用户需求。
4. **相对完整**：覆盖该需求的主要场景，例如创建、查询、修改和删除；不能只放一个功能就称为功能集。
5. **覆盖用户写职业**：写仓库管理员、采购员这类职业，不写具体用户画像的姓名。
6. **功能与故事只作子项**：功能集正文不罗列功能或故事，也不展开它们的行为细节。
7. **分界清晰**：一个功能集只负责一个需求范围，与相邻功能集不重叠。
8. **有依据**：来自项目文档、澄清 Issue 和已确认的结论；没有依据的组合不写。

#### 写什么

每项功能集正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“入库单管理”；标题单独用名称指定。
- **满足的用户需求**：这个功能集共同满足什么用户需求、管理什么业务对象。
- **覆盖用户**：使用这个功能集的职业，例如“仓库管理员”。
- **协作关系**：这些功能如何配合形成整体，例如共享同一业务对象、前后依赖或共同完成一个流程。
- **闭环位置**：它支撑子系统的哪个端到端目标，与上下游功能集如何衔接。
- **分界**：不包含什么，哪些能力属于其他功能集。

功能与故事作为子项维护，功能集正文只写上述字段。

#### 不写什么

- 功能清单或故事清单；它们只作为子项存在。
- 单个功能的行为细节、交互步骤和 UI。
- 交互和界面的设计；这些放在功能和后续章节。
- 代码模块、服务、接口、数据模型和技术实现。
- 具体用户姓名或用户画像；覆盖用户写职业。
- 指标、团队、排期和人力。
- 没有来源的数字或规模。
- 与子系统闭环无关的功能集合。

#### 判断标准

- 标题是否就是功能集名称？
- 名称、满足的用户需求、覆盖用户、协作关系、闭环位置、分界是否齐全，且都写在项正文的 `字段：值` 行里？
- 这个功能集是否围绕一个可识别的用户需求或业务对象？
- 其中的功能是否必须协作才能满足该需求，而不是任意拼在一起？
- 功能集是否相对完整，去掉关键功能后需求是否就无法满足？
- 覆盖用户是否写的是职业，而不是具体用户姓名？
- 功能与故事是否只作为子项，正文没有罗列或展开？
- 它是否只负责一个范围，与相邻功能集没有重叠？
- 是否误把单个功能、技术模块或跨需求的功能堆当成功能集？

#### 正例

> 名称：入库单管理
> 满足的用户需求：仓库管理员需要维护入库单的完整生命周期。
> 覆盖用户：仓库管理员。
> 协作关系：创建、查询、修改、删除和收货入库围绕同一张入库单；创建后由其余功能推进单据状态并维护数据。
> 闭环位置：支撑移动端“到货收货”环节，向下衔接库位分配。
> 分界：不含库位分配，它属于库位管理功能集；收货扫码是“收货入库”内部的交互。

功能与故事作为子项存在，功能集正文不罗列。

#### 反例

**反例 1**

> 功能集：创建入库单

这是单个功能，不构成功能集。只有创建而没有查询、修改和删除，用户无法维护入库单；应归入“入库单管理”功能集。

**反例 2**

> 功能集：入库单管理、报表导出、账号管理

这是功能堆砌，三部分服务不同需求，不共同满足一个用户目标。应拆成各自的功能集；账号管理属于账户管理功能集。

**反例 3**

> 功能集：入库单服务，提供 /inbound-orders API 和入库单表。

这是技术实现，不是需求。功能集只写用户需求、覆盖用户、协作关系、闭环位置和分界；服务和 API 放到设计阶段。

**反例 4**

> 功能集：入库单管理，包含创建入库单按钮、入库单列表页和弹窗样式。

这些是交互和 UI 细节，不是功能集层面的内容。功能集只写固定字段，交互和界面放到功能下的对应章节。

**反例 5**

> 功能集：收货入库

“收货入库”产生一次可观测的系统变化（入库单变为已收货、库存增加），是功能，不是功能集；扫码、确认等是它内部的交互。功能集应像“入库单管理”一样，围绕同一业务对象组合多个功能。

**反例 6**

> 功能集：入库单管理，包含创建入库单、查询入库单、修改入库单、删除入库单。

功能只作为子项存在，不在功能集正文罗列。正文应写满足的用户需求、覆盖用户、协作关系、闭环位置和分界。

**反例 7**

> 覆盖用户：张伟、李娜。

覆盖用户写职业，例如“仓库管理员、采购员”，不写具体用户画像的姓名。具体用户属于用户章节。

### 故事

#### 定位

故事描述一个具体用户（用姓名）为满足一项用户需求，按顺序操作软件完成的过程。故事必须把每个操作落到一个功能上，并写清不跟软件交互的环节、出错时怎么办、以及用户如何得知操作成功。故事不是用户的典型场景：典型场景只描述平时怎么做事，没有一项明确需求和完整的操作过程。

#### 原则

1. **一项需求一个故事**：一个故事只满足用户的一项需求；多项需求拆成多个故事。
2. **固定模板，正文不分字段**：每项故事只写一段正文，按名称、前置条件、发生频率、故事描述逐行写成 `字段：值`；字段只有这四项。
3. **频率用高/中/低**：发生频率只写“高”“中”“低”，不写数字、百分比或其他描述。
4. **用户写姓名**：使用用户章节中的姓名，不写职业或泛称。
5. **操作落到功能**：故事描述按顺序写用户先干什么、后干什么；每一个操作都必须对应一个功能，用功能名称引用，可以跨功能集和子系统。
6. **非软件环节写清楚**：人工核对、纸质单据、电话沟通等不跟软件交互的环节也要写，并说明它前后如何与软件操作衔接。
7. **错误与成功**：写清可能发生的错误、用户和系统如何处理、用户如何得知；以及用户如何确认操作成功。
8. **不重复细节**：不写交互步骤、页面控件、UI、功能规则和系统结果细节。
9. **不是典型场景**：必须有明确需求和完整操作过程，不是平时做事方式的描述。

#### 写什么

每项故事正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“到货入库”；标题单独用名称指定。
- **前置条件**：故事开始前必须成立的条件。
- **发生频率**：故事发生的频繁程度，只写“高”“中”或“低”。
- **故事描述**：一段连续文字，包含：
  - 具体用户的姓名；
  - 按顺序的操作，每一步对应哪个功能；
  - 不跟软件交互的环节；
  - 出错时发生什么、怎么处理、用户怎么得知；
  - 用户怎么确认操作成功。

#### 不写什么

- 把场景、目标、入口、功能序列、正常结果、异常分支、成功判据拆成独立行或独立字段；这些都写在故事描述里，模板只有名称、前置条件、发生频率和故事描述四项。
- 点击、填写、选择、提交等交互步骤；放在交互设计。
- 页面结构、控件、文案和视觉稿；放在交互设计和 UI 设计。
- 功能的前置条件、系统变化和反馈；这些由功能项承载。
- 业务规则、结果细节、状态变化明细、数据影响、异常和权限；需求文档不写。
- 功能、功能集、子系统的定义；只引用名称。
- 技术实现、接口、数据库和算法。
- 指标、团队、排期和人力。
- 多个无关需求混成一个故事。
- 只有正常路径、没有错误处理的故事。
- 抽象用户或职业代替姓名。
- 没有来源的数字或规模。

#### 判断标准

- 是否只满足一项用户需求？多项需求是否已拆分？
- 标题是否就是故事名称？
- 是否写全了故事名称、前置条件、发生频率和故事描述，且都在项正文的 `字段：值` 行里？
- 发生频率是否只写了“高”“中”或“低”？
- 用户是否用姓名，而不是职业或泛称？
- 每个操作是否都落到了一个功能，先后顺序是否清楚？
- 不跟软件交互的环节是否写清楚，并与前后操作衔接？
- 出错时怎么处理、用户怎么得知、操作成功后怎么确认，是否都写了？
- 是否只是用户的典型场景，缺少明确需求或完整操作过程？
- 是否重复了交互、UI 或功能内部的细节？

#### 正例

> 名称：到货入库
> 前置条件：仓库管理员张伟已登录移动端；入库单已创建并处于待收货状态；待收商品与入库单一致。
> 发生频率：高
> 故事描述：张伟需要把本次到货登记入库，让商品可用于后续出库。他打开“入库单管理”，选择待收货的入库单并进入收货（功能：查询入库单）。他用扫码枪逐件扫描商品（功能：收货入库）。遇到无法扫码的破损商品时，他暂停扫码，先在纸质异常单上人工登记，再回到系统使用“登记收货异常”（功能：收货入库）。全部扫完后提交收货（功能：收货入库）。如果扫码商品与入库单不符，系统拒绝该商品并提示原因，张伟核对后重新扫码或登记异常；如果网络中断，已扫明细保留，恢复后继续。提交成功后页面显示“已收货”，入库单状态变为已收货，张伟在库存中看到对应商品数量增加，以此确认操作成功。

#### 反例

**反例 1**

> 故事：仓库管理员张伟完成收货，并导出报表。

一个故事混了两个需求：收货和导出报表。应拆成两个故事，每个故事只满足一项用户需求。

**反例 2**

> 张伟在系统里完成收货。

没有说明用了哪个功能、先做什么后做什么。故事描述里的每一个操作都必须落到一个功能，并按顺序写清。

**反例 3**

> 张伟点击蓝色“提交”按钮，弹窗显示“提交成功”，随后页面跳转。

这是交互细节，属于交互设计。故事只写“张伟提交收货（功能：收货入库）”，不写控件、样式和提示文案。

**反例 4**

> 仓库管理员操作软件完成入库。

没有用姓名，也没有写具体操作和功能。故事必须用用户章节中的姓名，并逐个写出操作对应的功能。

**反例 5**

> 张伟创建入库单并收货，故事结束。

没有错误处理，也没有说明用户如何确认操作成功。扫码不符、网络中断等错误怎么处理、成功后在系统里看到什么，都要写清。

**反例 6**

> 张伟每天先巡库，再用纸质单据核对到货，最后集中补录。

这是用户的典型场景，没有一项明确需求和完整操作过程，应放在用户章节，不是故事。

**反例 7**

> 场景：供应商到货。
> 目标：完成入库。
> 功能序列：查询入库单 → 收货入库。

故事模板只有名称、前置条件、发生频率和故事描述四行；场景、目标、功能序列要写进故事描述，不新增字段。

**反例 8**

> 张伟扫码后提交收货。

遗漏了破损商品先在纸质异常单登记、再回系统登记异常的非软件环节。不跟软件交互的环节也要写清楚，并说明与前后操作的衔接。

**反例 9**

> 发生频率：每天 3 次。

发生频率只写“高”“中”或“低”，不写数字、百分比或其他描述。

### 功能

#### 定位

功能是产生可观测系统变化的最小单位。它由一次或多次交互组成；交互是功能内部的操作步骤，单次交互本身不一定改变系统，只有功能完成时系统才发生可观测变化。例如“填写单据 ID”是交互，提交后创建入库单才是功能。

#### 原则

1. **固定模板，正文不分字段**：每项功能只写一段正文，按名称、功能描述、系统变化、前置条件、反馈、交互设计逐行写成 `字段：值`；不把字段拆成子章节或标题。
2. **产生系统变化**：每个功能必须对应一个可观测的系统状态变化，例如创建、修改、删除或状态迁移；不产生系统变化的操作不单独成为功能。
3. **最小单位**：功能不能再拆成多个各自产生系统变化的功能；能拆说明它是功能集或多个功能。
4. **一个功能一份交互设计**：交互设计是功能正文中的一行 `交互设计：`，描述该功能的页面、控件和用户操作；不把“填写单据 ID”“点击提交”这类交互拆成独立字段或标题。
5. **单一结果**：一个功能只改变一类业务对象或完成一个结果，不把多个系统变化混成一条。
6. **归属一个功能集**：功能只属于一个功能集。
7. **不写边界**：功能不写“不包含什么”；边界在功能集的“分界”中表达。
8. **不写详细规则**：业务规则、结果细节、状态变化明细、数据影响、异常和权限都不写。
9. **有依据**：来自项目文档、澄清 Issue 和已确认的结论。

#### 写什么

每项功能正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“创建入库单”；标题单独用名称指定。
- **功能描述**：用一两句话说明这个功能的作用。
- **系统变化**：改变哪个业务对象、什么状态、从什么状态变成什么状态。
- **前置条件**：功能发生前必须成立的条件。
- **反馈**：功能完成后系统返回或告知用户什么信息，例如单据编号、结果状态、影响数量。
- **交互设计**：只写一行 `交互设计：`，描述该功能的页面、控件和用户如何操作。

UI 设计是功能下的图片列表，不在功能正文里写。

#### 不写什么

- 业务规则、结果细节、状态变化明细、数据影响、异常结果和权限条件。
- 交互步骤、页面布局、控件、文案、状态和异常提示；这些放在交互设计。
- 功能边界，例如“不包含扫码和库存增加”。
- 代码、接口、数据库、算法和技术实现。
- 用户画像本身；只引用用户章节。
- 指标、团队、排期和人力。
- 没有来源的数字或规模。
- 多个系统变化混成一个功能。
- 不产生系统变化的操作；它们属于交互。

#### 判断标准

- 标题是否就是功能名称？
- 名称、功能描述、系统变化、前置条件、反馈、交互设计是否齐全，且都写在项正文的 `字段：值` 行里？
- 完成后是否有可观测的系统变化？没有就不是功能。
- 是否还能拆成多个各自产生系统变化的功能？能就拆。
- 变化的对象和状态是否明确？
- 反馈是否写清了完成后返回或告知什么信息？
- 是否展开了业务规则、结果细节、状态变化明细、数据影响、异常或权限？
- 交互设计是否只有一行 `交互设计：`，覆盖页面、控件和用户操作，没有拆成多个交互项？
- 功能正文是否没有写交互步骤、页面或控件？
- 是否误写了功能边界？
- 是否把交互、页面或技术实现写成了功能？

#### 正例

> 名称：创建入库单
> 功能描述：让仓库管理员把一次到货登记成可继续收货的入库单。
> 系统变化：新增一张状态为“待收货”的入库单。
> 前置条件：已选择供应商和仓库；商品明细至少一行。
> 反馈：完成后返回新入库单编号和状态“待收货”。
> 交互设计：从“入库单管理”列表页进入创建页；用户填写供应商、仓库和商品明细后提交，提交中禁用重复提交，成功后跳转入库单详情。

UI 设计是功能下的图片列表，在后续章节定义。

#### 反例

**反例 1**

> 功能：填写单据 ID

这是交互，不是功能。填写本身不改变系统状态，只有提交后创建入库单才产生系统变化。

**反例 2**

> 功能：入库单管理

这是功能集，包含创建、查询、修改和删除等多个功能；单个功能集不能当作一个功能。

**反例 3**

> 功能：创建入库单页面有供应商下拉框、商品表格和提交按钮。

这是 UI 描述，不是功能。页面结构属于交互设计或 UI 设计，不是功能正文。

**反例 4**

> 功能：创建入库单时校验供应商存在、商品数量大于 0，失败时提示“供应商无效”。

这些是业务规则和异常提示，需求文档不写；功能只写简单说明、系统变化、前置条件和反馈。

**反例 5**

> 功能：调用 POST /inbound-orders 写入数据库。

这是技术实现，不是需求。接口、存储和调用方式放到设计阶段。

**反例 6**

> 功能：创建入库单。用户填写供应商、添加商品、点击提交。

交互步骤直接堆在功能描述里。一个功能只有一行 `交互设计：`，描述页面、控件和用户操作；功能描述、系统变化、前置条件和反馈分别写在各自的行里。

**反例 7**

> 边界：不包含扫码和库存增加。

功能不写边界。某个功能不包含什么，通过功能集的“分界”和功能定义本身表达。

**反例 8**

> 系统变化：新增一张状态为“待收货”的入库单。
> 前置条件：已选择供应商和仓库。
> 反馈：返回新入库单编号。

缺少功能描述。每个功能都要用一两句话说明它的作用。

**反例 9**

> 交互 1：填写单据 ID
> 交互 2：选择供应商
> 交互 3：点击提交

这些是功能内部的细粒度交互，不需要拆成独立字段。一个功能只写一行 `交互设计：`，统一描述页面、控件和用户操作。

**反例 10**

> 反馈：页面顶部弹出绿色成功提示，并在 3 秒后消失。

这是反馈的呈现方式，属于交互设计。功能项的反馈只写完成后返回或告知什么信息，例如单据编号、状态或影响数量。

**反例 11**

> 系统变化：新增一张状态为“待收货”的入库单。
> 前置条件：已选择供应商和仓库。

缺少反馈。每个功能都要写清完成后返回或告知用户什么信息。

### 功能描述

#### 定位

功能描述是功能正文中的一行 `功能描述：`，只写一两句话说明这个功能的作用，不展开业务规则、结果细节、状态变化明细、数据影响、异常和权限。系统变化和反馈分别写在功能正文的其他字段行。

#### 写什么

- 用一两句话说明这个功能做什么、为什么存在。

#### 不写什么

- 业务规则、校验规则、结果细节、状态变化明细、数据影响、异常结果和权限条件。
- 交互步骤、页面、控件、文案和提示；这些属于交互设计。
- 视觉样式、技术实现、用户画像、指标、排期和没有来源的数据。

#### 判断标准

- 是否只用一两句话说明了功能的作用？
- 是否没有展开业务规则、结果细节、状态变化、数据影响、异常和权限？
- 是否与功能项的名称和系统变化一致，没有重复或冲突？

#### 正例

> 功能描述：让仓库管理员把一次到货登记成可继续收货的入库单。

#### 反例

**反例 1**

> 商品明细至少一行；商品数量大于 0；同一供应商、仓库和单据日期不能重复。

这些是业务规则，需求文档不写业务规则和结果细节。

**反例 2**

> 新增一张状态为“待收货”的入库单，记录创建人和创建时间。

这是系统结果和状态变化明细。系统变化在功能项里用一句话写清，不在功能描述展开。

### 交互设计

#### 定位

交互设计是功能正文中的一行 `交互设计：`，一个功能只有一行。它描述该功能的页面结构、控件和用户如何操作，不把“填写单据 ID”“点击提交”这类细粒度交互拆成独立字段或标题；也不写业务规则、系统结果和视觉样式。反馈的信息内容写在功能的“反馈”行里，这里只写反馈如何呈现。

#### 原则

1. **一个功能一行**：每个功能只有一行 `交互设计：`，覆盖该功能，不把多个功能的交互混在一起，也不拆成多个字段或标题。
2. **覆盖用户操作**：按用户操作顺序写清用户如何完成功能，包括点击、填写、选择、提交和取消；写功能级操作，不逐条解释细粒度交互。
3. **页面结构清楚**：说明涉及哪些页面或区域、层级关系和跳转关系。
4. **控件明确**：说明用什么控件、控件状态和关键行为，足以让 UI 设计继续。
5. **反馈可执行**：说明反馈如何呈现，包括加载、成功、失败、空状态和关键提示；反馈的信息内容由功能项的“反馈”定义。
6. **不越界**：业务规则不写，视觉样式放 UI 设计。

#### 写什么

- **用户操作**：按顺序写用户如何操作完成这个功能，以及系统如何响应；不拆成独立字段或标题。
- **页面结构**：涉及的页面、区域、层级和跳转关系。
- **控件**：控件类型、位置、默认值、可用或禁用条件、关键行为。
- **反馈与状态**：反馈如何呈现，包括加载、成功、失败、空状态、确认、撤销和错误提示。
- **文案**：按钮、提示和错误文案的关键内容。
- **无障碍与操作方式**：键盘操作、焦点顺序、读屏和触控要求中影响交互的部分。

#### 不写什么

- 把“填写单据 ID”“选择供应商”“点击提交”这类细粒度交互拆成独立字段或标题。
- 业务规则、结果细节、状态变化明细、数据影响和异常；需求文档不写。
- 反馈的信息内容，例如单据编号、结果状态、影响数量；这些写在功能项的“反馈”里。
- 功能项的简单说明、系统变化和前置条件；只引用，不重复。
- 视觉样式、颜色、字体、字号、间距、圆角、图标、图片和设计 token；这些放在 UI 设计。
- 技术实现、接口、数据库和算法。
- 用户画像本身；只引用用户章节。
- 指标、团队、排期和人力。
- 多个功能的交互混成一份。
- 没有来源的数字或规模。

#### 判断标准

- 是否每个功能只有一行 `交互设计：`？
- 是否覆盖从进入功能到完成或放弃的用户操作，但没有拆成多个字段或标题？
- 页面结构和控件是否足以让 UI 设计直接继续？
- 是否把业务规则、结果细节写进了交互设计，或把视觉样式写进了控件描述？
- 反馈的呈现方式是否与功能项“反馈”里的信息内容一致？
- 加载、成功、失败和空状态是否都有交代？

#### 正例

> 交互设计：从“入库单管理”列表页进入“创建入库单”页；页面分为单据信息区、商品明细区和底部操作区。用户填写供应商、仓库和单据日期，点击“添加商品”打开商品选择弹窗，选择后回填商品明细表格，点击“提交”完成创建；必填项未完成时提交按钮禁用。提交中显示加载并禁用重复提交；成功后跳转入库单详情并显示新入库单编号和状态；失败时保留已填内容并在对应字段显示错误；商品明细为空时表格显示空状态。支持键盘完成填写、选择和提交，焦点按页面区域顺序移动。

#### 反例

**反例 1**

> 前置条件：供应商和仓库已启用；商品数量必须大于 0。

前置条件属于功能项；业务规则不写进需求文档。交互设计只写用户如何操作和系统如何响应。

**反例 2**

> 创建成功后，系统新增一张状态为“待收货”的入库单。

这是系统结果和状态变化，属于功能项的“系统变化”。交互设计可以写“成功后跳转详情”，但不写系统内部产生了什么状态。

**反例 3**

> 主按钮使用品牌蓝，圆角 8px，字号 14px，间距 16px。

这是视觉样式，属于 UI 设计。交互设计只写到“提交按钮”及其可用状态和反馈。

**反例 4**

> 用户先创建入库单，再收货，最后查看库存。

这跨了多个功能和流程，属于故事或更高层场景，不是单个功能的交互设计。

**反例 5**

> 调用 POST /inbound-orders 接口并刷新列表缓存。

这是技术实现，不是交互设计。接口和缓存策略放在设计阶段。

**反例 6**

> 交互 1：填写单据 ID
> 交互 2：选择供应商
> 交互 3：点击提交

这些细粒度交互不需要拆成独立字段。一个功能只写一行 `交互设计：`，统一描述页面、控件和用户操作。

### UI设计

#### 定位

UI 设计是功能下的图片列表，按交互设计描述的顺序排列。目前不支持动画。每个图片项只写 `名称：` 和 `链接：` 两行，不写页面结构、控件、交互逻辑或业务规则。

#### 原则

1. **图片列表**：UI 设计只由图片项组成；每项写 `名称：` 和 `链接：`，不写文字说明或视觉规范。
2. **按交互顺序排列**：图片的顺序必须与交互设计中页面和状态的描述顺序一致。
3. **覆盖交互设计**：图片覆盖交互设计描述的页面和关键状态；没有图的页面或状态不臆造。
4. **只放静态图片**：目前不支持动画，不放动图、帧序列或动画说明。
5. **不重复上游**：不写页面结构、控件行为、交互步骤、业务规则或系统结果。

#### 写什么

- **图片列表**：每项一张图片，标题用图片名称，正文按 `名称：…`、`链接：…`（或资产 ID）两行写；按交互设计描述的顺序排列。

#### 不写什么

- 动画、动图、帧序列和动画说明；目前不支持。
- 视觉规范的文字描述，例如颜色、字体、字号、间距、圆角和组件样式。
- 页面结构、区域层级、跳转关系和控件行为；这些放在交互设计。
- 交互步骤、加载和错误提示的交互逻辑；这些放在交互设计。
- 前置条件、系统变化和反馈；这些放在功能项。
- 业务规则、结果细节、状态变化明细、数据影响、异常和权限；需求文档不写。
- 功能定义、用户画像、项目背景和目标。
- 技术实现、接口、数据库和前端框架。
- 指标、团队、排期和人力。
- 只有“见设计稿”而没有具体图片的引用。

#### 判断标准

- 是否只有一个图片列表，没有文字说明或视觉规范？
- 每个图片项的标题是否就是图片名称？
- 每个图片项是否按 `名称：` 和 `链接：` 两行写？
- 图片顺序是否与交互设计描述的顺序一致？
- 图片是否覆盖交互设计中的页面和关键状态？
- 是否混入了动画、页面结构、控件行为、业务规则或技术实现？
- 是否用“见设计稿”代替了具体图片引用？

#### 正例

第一个图片项：

> 名称：创建入库单-默认态
> 链接：https://example.com/inbound-default.png

第二个图片项：

> 名称：创建入库单-错误态
> 链接：https://example.com/inbound-error.png

每个图片项都按这个格式写；顺序与交互设计中的页面和状态顺序一致。

#### 反例

**反例 1**

> 主按钮使用品牌蓝，圆角 8px，字号 14px，间距 16px。

UI 设计是图片列表，不写颜色、尺寸、间距等视觉规范的文字描述。

**反例 2**

> 页面分为单据信息区、商品明细区和底部操作区，提交后跳转详情页。

这是页面结构和交互流程，属于交互设计。UI 设计只列出对应的图片。

**反例 3**

> 提交成功动画：勾选图标放大后淡出（动图链接）。

目前不支持动画。UI 设计只放静态图片，不放动画稿。

**反例 4**

这不是图片列表，读者无法定位具体图片。应逐项写 `名称：` 和 `链接：`。

**反例 5**

> 2. 创建入库单-默认态（图片链接）
> 3. 创建入库单-错误态（图片链接）

顺序与交互设计描述不一致。图片列表必须按交互设计中页面和状态的顺序排列。
