# 需求文档写作说明书

## 目录结构

```text
需求文档
├─ 领域模型
│  └─ 领域模型（多项，正文按固定字段写）
├─ 用户肖像
│  └─ 用户肖像（多项，正文按固定字段写）
├─ 故事
│  └─ 故事（多项，正文按固定字段写）
├─ 子系统
│  └─ 子系统（多项，正文按固定字段写）
│     └─ 功能集（多项，正文按固定字段写）
│        └─ 功能（多项，正文按固定字段写）
│           └─ 功能描述
├─ 交互设计
│  ├─ 全局约定
│  │  ├─ 反馈与状态
│  │  ├─ 错误与恢复
│  │  ├─ 文案
│  │  └─ 无障碍
│  └─ 子系统（多项，标题 = 软件名称）
│     ├─ 信息架构
│     ├─ 页面清单（列表）
│     └─ 功能集（多项，标题 = 功能集名称）
│        └─ 功能（多项，标题 = 功能名称）
│           ├─ 页面结构
│           ├─ 操作（列表）
│           ├─ 反馈与状态
│           ├─ 文案
│           └─ 无障碍
└─ UI设计
   ├─ 全局视觉规范
   │  ├─ 色彩
   │  ├─ 字体与排版
   │  ├─ 间距与圆角
   │  ├─ 图标与图片
   │  ├─ 动效
   │  └─ 布局栅格与响应式
   └─ 子系统（多项，标题 = 软件名称）
      ├─ 视觉差异
      ├─ 组件规范
      │  └─ 组件（多项，标题 = 组件名称）
      │     ├─ 用途
      │     ├─ 结构
      │     ├─ 状态
      │     └─ 规格
      └─ 页面（多项，标题 = 页面名称）
         ├─ 关联功能（列表）
         ├─ 布局
         ├─ 信息层级
         ├─ 组件（列表）
         ├─ 状态（列表）
         └─ 设计稿（列表）
```

所有固定字段都写在项正文里，每行一个 `字段：值`；不要为字段创建子章节或标题。子系统下的「功能集」「功能」是结构层级，不是字段。

交互设计的子系统、功能集、功能标题必须与需求文档一致；UI 设计的子系统和页面标题必须与交互设计一致。页面在交互设计的子系统层定义一次，功能只引用页面名称；UI 设计的页面必须与这份页面清单一一对应。

## 各项写什么

以下规则按文档结构逐项定义。

功能正文只写名称、系统变化、前置条件和反馈；功能描述是功能下的唯一子章节。交互设计和 UI 设计写在各自顶层的章节树里，不写进功能正文或功能子章节。

### 领域模型

#### 定位

领域模型描述用户在使用软件产品时能够感知到的概念类。每个概念类是一个基本概念，用来帮助用户理解软件功能；它通常复用日常生活或工作中的概念，无法复用时才创造新概念。每个概念类由若干属性组成。

概念类不是功能、页面、操作或技术实体。

#### 原则

1. **名词性**：概念类用名词或名词性短语，例如“订单”“用户”“文档”；不用“下单”“管理订单”这类动作或功能名。
2. **用户可感知**：概念类必须是用户在使用软件时能感知、能说出、能理解的对象，不是数据库表、接口、代码类或内部状态。
3. **与产品相关**：概念类体现在产品设计中，是产品要呈现给用户的概念；与产品无关的概念不写进领域模型。每个概念类的属性也必须是用户能感知或使用、并且在满足用户需求的过程中有价值的信息。例如“账户”的“体重”属性对权限控制没有作用，不应出现；属性也不能是 `id`、`created_at`、`status_code` 这类技术字段。
4. **基本且单一**：一个概念类只表达一个基本概念；不把多个概念合并，也不把功能、页面、动作当成概念类。概念类可以依赖其他概念，例如“订单”的创建者是“账户”；依赖关系不把两个概念合并成一项，也不把被依赖概念的属性复制进来。
5. **复用优先**：优先使用用户日常或工作中已有的概念和名称；已有概念能表达时，不创造新词；只有没有可复用概念，且不创造就无法让用户理解功能时，才创造新概念。
6. **名称一致**：同一概念在全文档使用同一个名称；不同概念不用同一个词，避免同义词和同名异义。

#### 写什么

每个领域模型项写：

- **概念类名称**：用户能理解的名词或名词性短语。
- **概念类说明**：用一两句话说明用户在软件中感知到的这个对象是什么。
- **属性**：逐项列出用户能感知或使用、且对满足用户需求有用的属性，并说明每个属性的含义；例如“价格：用户看到的商品单价”。属性可以引用其他概念，例如“创建者：账户”。

#### 不写什么

- 功能、页面、操作、流程、权限和角色职责。
- 数据库表、接口、代码类、字段名、状态码、ID 生成规则等技术实现。
- 用户无法感知的内部状态、日志、缓存、索引和存储结构。
- 把多个概念合并成一项，或把同一概念拆成多项。
- 为了凑数创造用户不会使用的概念。
- 只写属性名不写含义；只写技术字段不写用户语言。
- 对满足用户需求没有作用、只是凑数的属性。
- 把被依赖概念的属性复制到当前概念类，而不是引用那个概念。

#### 判断标准

- 是否是名词性概念，而不是功能、页面、动作或技术实体？
- 这个概念类是否是用户在使用软件时能感知到的对象？
- 这个概念类是否体现在产品设计中，与产品相关？
- 是否优先复用了日常或工作中的已有概念？新概念是否确有必要？
- 一个概念类是否只表达一个基本概念？
- 是否列出了用户能感知且对满足用户需求有用的属性，并说明了每个属性的含义？
- 属性是否在需要时引用其他概念，而不是复制被依赖概念的属性？
- 是否混入了 `id`、`created_at`、`status_code` 等技术字段？
- 概念类名称和属性是否在全文档中一致？

#### 正例

> 概念类：订单
> 说明：用户提交的一次购买请求。
> 属性：
> - 订单号：用户用来识别和查询这次购买
> - 下单时间：用户提交订单的时间
> - 订单状态：用户看到的待支付、已支付、已发货、已完成等状态
> - 金额：用户需要支付的总额
> - 创建者：创建订单的账户

> 概念类：文档
> 说明：用户在系统中创建和编辑的一份内容。
> 属性：
> - 标题：文档名称
> - 正文：用户编写的正文内容
> - 作者：创建文档的用户
> - 创建时间：文档首次创建的时间

#### 反例

**反例 1**

> 订单管理

这是功能或功能集，不是用户感知到的概念类。概念类应是“订单”。

**反例 2**

> 订单表：id、user_id、status_code、created_at

这是数据库实现，不是用户概念。应写成“订单”，并列出用户能感知的订单号、状态、金额等属性。

**反例 3**

> 下单

这是用户动作，不是概念类。概念类应是动作作用的对象，例如“订单”。

**反例 4**

> 订单及售后

把两个概念合并成一项。订单和售后应分别建模，除非用户确实把它们理解为一个概念。

**反例 5**

> 文档：id、content、owner_id

只写技术字段，没有用户能理解的名称和属性含义。应写成标题、正文、作者等用户语言。

**反例 6**

> 概念类：账户
> 属性：姓名、体重

“体重”对账户在权限控制或身份识别中的用途没有作用，是无关属性。属性必须对满足用户需求有价值。

### 用户肖像

#### 定位

用户肖像是从用户群体抽象出来的假想代表，不是真实个人。它的作用是帮助细化用户需求，设计更易于使用的软件产品。不同用户的需求差异必须会影响软件设计；完全相同的用户合并成一项，需要针对不同类型用户区分设计时拆出新用户。用户肖像为故事和功能提供被引用的对象，不是泛化的角色名称。

#### 原则

1. **虚构代表者**：用户肖像是从用户群体抽象出来的假想代表，不是真实个人；它用于细化需求，帮助设计更易于使用的产品。
2. **按设计差异划分**：不同用户的需求差异必须会影响软件设计，例如角色、目标、场景或偏好不同；完全相同的用户合并成一项；一旦发现软件需要针对不同类型用户进行区分设计，就拆出新用户。
3. **固定模板，正文不分字段**：每项用户只写一段正文，按固定字段逐行写成 `字段：值`；不把字段拆成子章节、子字段、表格或 JSON。基本状况和典型场景只在影响系统使用时才写。
4. **诉求写需要，不写方案**：诉求是用户想获得的结果，不是功能、页面或技术方案。
5. **主次明确**：每项用户标注“主要”或“次要”；不限用户数量。
6. **系统相关**：基本状况和典型场景必须与系统使用有关；与系统无关的家庭、生活细节不写。
7. **与已确认信息一致**：画像细节可以补全，但不能与澄清结论冲突，也不编造真实人物或统计数据。

#### 写什么

每项用户正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **姓名**：用于引用，可以是化名，但一项只对应一个姓名。
- **年龄**：用户的年龄，写具体年龄或年龄段。
- **基本状况**（条件字段）：家庭、身体、经济、工作条件等中影响系统使用的部分；不相关不写。
- **爱好**：用户的爱好。
- **职业**：用户的职业或岗位。
- **典型场景**（条件字段）：用户平时怎么做事、在什么环境或节奏下使用系统；只写与系统有关的部分，不写目标、功能序列和异常分支。
- **诉求**：用户想从系统或工作中获得什么，写需求，不写功能。
- **主次**：写“主要”或“次要”。

#### 不写什么

- 权限、边界和使用频率。
- 与系统无关的基本状况、家庭生活、爱好细节和典型场景。
- 故事：明确目标、功能序列和异常分支。
- 功能、页面、交互流程、UI 布局。
- 技术实现、账号体系、权限模型的实现方式。
- 需求条目、验收标准、优先级。
- 固定字段之外的个人信息，例如性别、性格、履历。
- 把字段拆成子章节、子标题、表格或 JSON；字段只作为正文中的 `字段：值` 行。
- 没有来源的统计数据、引文、访谈记录和置信度判断。
- 组织架构、公司历史、行业背景。
- “所有用户”“普通用户”这类无法判断具体对象的泛称。
- 把需求差异会影响软件设计的用户合并成一项。
- 把完全相同的用户重复拆成多项。

#### 判断标准

- 姓名、年龄、爱好、职业、诉求、主次六项是否齐全，且没有添加模板外字段？
- 六项是否都写在用户项正文里，每行一个 `字段：值`，而不是拆成子字段或子章节？
- 基本状况和典型场景是否只在影响系统使用时才写？
- 典型场景是否被写成了故事，出现了目标、功能序列或异常分支？
- 姓名能否在文档内唯一定位这个用户？
- 诉求是否是用户需要，而不是功能或方案？
- 主次是否明确写了“主要”或“次要”？
- 是否混入了权限、边界或频率？
- 是否把需求差异会影响软件设计的用户合并成一项？
- 是否把完全相同的用户重复拆成多项？

#### 正例

用户项正文（张伟）：

> 姓名：张伟
> 年龄：35 岁
> 基本状况：需要轮班并照顾孩子，只能在交接班时集中处理单据。
> 爱好：钓鱼、看历史纪录片
> 职业：仓库管理员
> 典型场景：每天先巡库，再用纸质单据核对到货，收货后集中补录系统；常在走动和弱网环境下操作。
> 诉求：到货后能快速确认数量并找到可放库位，减少纸质单据核对。
> 主次：主要

#### 反例

**反例 1**

> 用户：仓库管理员

缺少姓名、年龄、爱好、诉求和主次，只剩一个职业名称。用户必须是具体画像，并按固定模板填写。

**反例 2**

> 姓名：张伟
> 权限：可修改库存，不能审批采购单。
> 边界：只负责自己所在的仓库。
> 频率：每天操作 3 次。

用户不写权限、边界和频率。这些内容属于功能或功能描述；用户项只写固定字段。

**反例 3**

> 诉求：一键导出报表，并支持批量删除。

这是功能和方案，不是诉求。诉求应写用户想获得的结果，例如“希望能快速汇总当日到货，减少手工抄录”。

**反例 4**

> 姓名：张伟
> 性别：男
> 性格：外向
> 履历：在本公司工作 10 年

这些是固定模板之外的字段。用户项只写姓名、年龄、基本状况、爱好、职业、典型场景、诉求和主次。

**反例 5**

> 用户：张伟和李娜，仓库管理员。

一项用户只能对应一个人。多个用户应分别成项，并各自标注主次。

**反例 6**

> 基本状况：家庭和睦，喜欢旅行。
> 典型场景：周末常和朋友聚会。

这些与系统使用无关。基本状况和典型场景只写会影响用户使用系统的部分。

**反例 7**

> 典型场景：用户先创建入库单，再扫码收货；库位不足时转到异常处理。

这是故事，有目标和功能序列，还写了异常分支。典型场景只描述用户平时怎么做事，例如“先巡库再收货，收货后集中补录”。

### 子系统

#### 定位

子系统是用户可感知的一个“软件”，例如“仓库管理系统 Web 端”“仓库管理系统移动端”。它由多个功能集组成，这些功能集共同形成闭环，提供完整的解决方案。子系统不绑定代码模块或部署单元。

#### 原则

1. **固定模板，正文不分字段**：每项子系统只写一段正文，按软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系、边界逐行写成 `字段：值`；不把字段拆成子章节或标题。
2. **用户可感知**：子系统有明确的用户入口、界面或使用形态，是一个用户能识别并使用的东西，不是代码模块、服务或技术分层。
3. **功能集闭环**：子系统包含的功能集必须能共同完成至少一个端到端的用户目标，形成完整解决方案；零散功能的集合不是子系统。
4. **覆盖用户写职业**：写仓库管理员、采购员这类职业，不写具体用户画像的姓名。
5. **功能集只作子项**：功能集作为子项维护，子系统正文不罗列功能集名称，也不展开功能细节。
6. **关系单独成字段**：与其他子系统的入口、渠道、共享能力、数据和流程衔接写成正文中的“与其他子系统的关系：”行；没有时写“无”。

#### 写什么

每项子系统正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **软件名称**：例如“仓库管理系统移动端”。
- **软件形态**：Web 端、移动端、桌面端等，以及用户通过什么入口或设备使用。
- **覆盖用户**：使用这个子系统的职业，例如“仓库管理员、采购员”。
- **闭环目标**：用户通过它完成哪些端到端目标，功能集如何共同形成完整解决方案。
- **与其他子系统的关系**：与哪些子系统共享数据、能力或流程，入口和渠道如何分工，各形态的差异；没有时写“无”。
- **边界**：不包含什么，哪些能力由其他子系统承载。

#### 不写什么

- 功能集名称清单；功能集只作为子项存在，不在正文罗列。
- 单个功能的行为、交互和 UI；这些放在功能集、功能及后续章节。
- 具体用户姓名或用户画像；覆盖用户写职业。
- 代码模块、服务、部署单元、技术栈、数据模型、接口或 API。
- 实现细节、算法、性能指标、数据库和基础设施。
- 项目文档已有的目标、非目标、约束和风险。
- 团队、组织架构、负责人、排期和人力。
- 没有来源的数字或规模。

#### 判断标准

- 软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系、边界是否齐全，且都写在项正文的 `字段：值` 行里？
- 用户能否识别这是一个可以使用的软件，而不是一个业务领域或技术模块？
- 其功能集能否共同完成至少一个端到端目标、形成闭环？
- 覆盖用户是否写的是职业，而不是具体用户姓名？
- 功能集是否只作为子项，正文没有罗列功能集或功能细节？
- 与其他子系统的关系是否单独写清；没有时是否写了“无”？
- 是否把“库存”“采购”这类业务领域、或代码服务误当成子系统？

#### 正例

> 软件名称：仓库管理系统移动端
> 软件形态：移动应用，仓库现场使用。
> 覆盖用户：仓库管理员。
> 闭环目标：完成从到货收货、上架到库存盘点的现场作业闭环。
> 与其他子系统的关系：与 Web 端共享库存和入库单数据；采购审批在 Web 端完成，移动端不提供。
> 边界：不含采购审批、账号管理和报表导出。

功能集作为子项存在：入库单管理、库位管理、库存盘点；子系统正文不罗列。

#### 反例

**反例 1**

> 子系统：库存

这是业务能力域，不是用户可感知的软件。库存能力应体现在具体子系统的功能集和功能中，例如“入库单管理”“库存盘点”。

**反例 2**

> 子系统：inventory-service，负责 /stock API 和库存表，依赖 Postgres。

这是实现和架构描述，不是需求。子系统只写软件形态、职业用户、闭环、与其他子系统的关系和边界，技术实现放到设计阶段。

**反例 3**

> 子系统：仓库管理系统移动端，包含入库单管理、库位管理、库存盘点。

功能集只作为子项存在，不在子系统正文罗列名称。正文应写软件名称、软件形态、覆盖用户、闭环目标、与其他子系统的关系和边界。

**反例 4**

> 覆盖用户：张伟、李娜。

覆盖用户写职业，例如“仓库管理员、采购员”，不写具体用户画像的姓名。具体用户属于用户章节。

**反例 5**

> 与其他子系统的关系：调用 /api/inventory，依赖 Postgres 和消息队列。

这是技术依赖和接口，不是子系统关系。关系应写共享哪些数据或能力、入口和渠道如何分工、各形态的差异。

**反例 6**

> 子系统：仓库管理系统 Web 端，目标是把库存准确率提升到 99%，由 3 人团队在 Q3 完成。

这是指标、团队和排期，不是子系统描述。指标属于项目文档或后续验收，团队和排期不属于需求文档。

**反例 7**

> 子系统：仓库管理系统移动端，包含创建入库单、扫码和打印三个功能。

这些功能互不衔接，没有共同完成一个端到端目标。子系统应写清闭环目标，功能集必须能共同形成完整解决方案。

### 功能集

#### 定位

功能集通常围绕一个独立概念组织，例如与“订单”相关的功能构成一个功能集。功能集可以包含多个概念，但这些概念必须与核心概念不可独立拆分。判断归属看概念是否独立，而不是看功能是否共同满足一个需求。

#### 原则

1. **固定模板，正文不分字段**：每项功能集只写一段正文，按名称、核心概念、包含的概念、概念关系、边界逐行写成 `字段：值`；不把字段拆成子章节或标题。
2. **围绕独立概念**：一个功能集通常围绕一个独立概念，例如“订单”“入库单”。
3. **按独立性判断归属**：概念是否属于同一功能集，看它们能不能独立管理。
   - “订单”和“账户”独立：账户虽然是订单的前置条件，但账户有自己的管理动作，不属于订单功能集。
   - “订单”和“订单操作历史”不独立：产生订单和产生操作历史的动作是同一个，操作历史应归入订单功能集。
4. **功能只作子项**：功能集正文不罗列功能，也不展开功能的行为细节；故事是顶层章节，不属于功能集。
5. **分界清晰**：明确哪些独立概念不属于本功能集，例如订单功能集不包含账户管理。

#### 写什么

每项功能集正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“订单管理”。
- **核心概念**：这个功能集围绕的独立概念，例如“订单”。
- **包含的概念**：与核心概念不可独立拆分的概念，例如“订单操作历史”；说明为什么不能独立管理。没有就写“无”。
- **概念关系**：核心概念与包含概念的关系，例如“订单创建和状态变化会产生订单操作历史”。
- **边界**：哪些独立概念不属于本功能集，例如“账户”“支付”；它们由哪些功能集管理。

功能作为子项维护，功能集正文只写上述字段。故事是顶层章节，不挂在功能集下。

#### 不写什么

- 功能清单；功能只作为子项存在。
- 单个功能的行为细节、交互步骤和 UI。
- 交互和界面的设计；这些放在功能和后续章节。
- 代码模块、服务、接口、数据模型和技术实现。
- 独立概念的管理功能，例如订单功能集不写账户管理。
- 把同一动作产生、无法独立管理的从属概念拆出去，例如订单操作历史不单独成为功能集。
- 只因为两个概念有依赖关系就合并，例如订单依赖账户，不代表账户属于订单功能集。
- 指标、团队、排期和人力。
- 没有来源的数字或规模。

#### 判断标准

- 名称、核心概念、包含的概念、概念关系、边界是否齐全，且都写在项正文的 `字段：值` 行里？
- 这个功能集是否围绕一个独立概念？
- 包含的概念是否与核心概念不可独立拆分？
- 是否把独立概念错误并入，例如把账户并入订单？
- 是否把同一动作产生的从属概念错误拆出，例如把订单操作历史拆成独立功能集？
- 边界是否写清了哪些独立概念不属于本功能集？
- 功能是否只作为子项，正文没有罗列或展开？

#### 正例

> 名称：订单管理
> 核心概念：订单
> 包含的概念：订单操作历史；它由订单创建和状态变更的同一个动作产生，不能独立管理。
> 概念关系：订单创建和状态变化会产生订单操作历史。
> 边界：不包含账户和支付；账户由账户管理功能集负责，支付由支付功能集负责。

功能作为子项存在，功能集正文不罗列；故事是顶层章节。

#### 反例

**反例 1**

> 功能集：订单管理和账户管理

账户是独立概念，虽然订单依赖账户，但账户有自己的管理动作。应拆成“订单管理”和“账户管理”两个功能集。

**反例 2**

> 功能集：订单管理，包含订单、订单操作历史、账户、支付、退款、报表

账户、支付、退款和报表都是可以独立管理的概念或能力，不应因为和订单相关就并进订单功能集。

**反例 3**

> 把“订单操作历史”单独做成功能集。

订单操作历史由产生订单和变更订单的同一个动作产生，不能独立管理，应归入订单功能集。

**反例 4**

> 功能集：订单服务，提供 /orders API 和订单表。

这是技术实现，不是需求。功能集只写核心概念、包含的概念、概念关系和边界；服务和 API 放到设计阶段。

**反例 5**

> 功能集：订单管理，包含创建订单按钮、订单列表页和弹窗样式。

这些是交互和 UI 细节，不是功能集层面的内容。功能集只写固定字段，交互和界面放到「交互设计」和「UI设计」的对应节点里。

**反例 6**

> 功能集：订单管理，包含创建订单、查询订单、修改订单、删除订单。

功能只作为子项存在，不在功能集正文罗列。正文应写核心概念、包含的概念、概念关系和边界。

### 故事

#### 定位

故事描述一个具体用户（用姓名）为满足一项用户需求，按顺序操作软件完成的过程。故事必须把每个操作落到一个功能上，并写清不跟软件交互的环节、出错时怎么办、以及用户如何得知操作成功。故事不是用户的典型场景：典型场景只描述平时怎么做事，没有一项明确需求和完整的操作过程。

#### 原则

1. **一项需求一个故事**：一个故事只满足用户的一项需求；多项需求拆成多个故事。
2. **需求全面性**：用户所有可能产生的需求都必须被某一个故事覆盖。一个需求的实现可能进一步产生其他需求，例如“购买”的实现会进一步产生“退货”需求；要把这些关联需求分析出来，写进故事的「关联需求」字段，并确保它们也有故事覆盖。
3. **固定模板，正文不分字段**：每项故事只写一段正文，按名称、前置条件、发生频率、故事描述、关联需求逐行写成 `字段：值`；字段只有这五项。
4. **频率用高/中/低**：发生频率只写“高”“中”“低”，不写数字、百分比或其他描述。
5. **用户写姓名**：使用用户肖像中的姓名，不写职业或泛称。
6. **操作落到功能**：故事描述按顺序写用户先干什么、后干什么；每一个操作都必须对应一个功能，用功能名称引用，可以跨功能集和子系统。
7. **覆盖所有可观测变化**：清晰描述系统所有能被用户观测到的反馈和变化。例如不能只写“创建订单”，还要写创建后用户如何确认订单已经创建，以及后续如何通过查询订单跟踪状态。所有可能被观察到的变化都要覆盖，并说明这些信息对用户有什么作用。
8. **非软件环节写清楚**：人工核对、纸质单据、电话沟通等不跟软件交互的环节也要写，并说明它前后如何与软件操作衔接。
9. **错误与成功**：写清可能发生的错误、用户和系统如何处理、用户如何得知；以及用户如何确认操作成功。
10. **不重复细节**：不写交互步骤、页面控件、UI、功能规则和系统结果细节。
11. **不是典型场景**：必须有明确需求和完整操作过程，不是平时做事方式的描述。

#### 写什么

每项故事正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“到货入库”。
- **前置条件**：故事开始前必须成立的条件。
- **发生频率**：故事发生的频繁程度，只写“高”“中”或“低”。
- **故事描述**：一段连续文字，包含：
  - 具体用户的姓名；
  - 按顺序的操作，每一步对应哪个功能；
  - 不跟软件交互的环节；
  - 系统可被用户观察到的反馈和变化，以及这些信息对用户的作用；
  - 出错时发生什么、怎么处理、用户怎么得知；
  - 用户怎么确认操作成功。
- **关联需求**：列出这个故事的实现可能进一步产生的需求，以及这些需求由哪些故事覆盖；没有就写“无”。

#### 不写什么

- 把场景、目标、入口、功能序列、正常结果、异常分支、成功判据拆成独立行或独立字段；这些都写在故事描述里，模板只有名称、前置条件、发生频率、故事描述和关联需求五项。
- 点击、填写、选择、提交等交互步骤；放在交互设计。
- 页面结构、控件、文案和视觉稿；放在交互设计和 UI 设计。
- 功能的前置条件、系统变化和反馈；这些由功能项承载。
- 业务规则、结果细节、状态变化明细、数据影响、异常和权限；需求文档不写。
- 功能、功能集、子系统的定义；只引用名称。
- 技术实现、接口、数据库和算法。
- 指标、团队、排期和人力。
- 多个无关需求混成一个故事。
- 只有正常路径、没有错误处理的故事。
- 只写操作发生，不写用户如何观察结果、确认成功或后续跟踪。
- 漏掉这个故事的实现会进一步产生的关联需求。
- 抽象用户或职业代替姓名。
- 没有来源的数字或规模。

#### 判断标准

- 是否只满足一项用户需求？多项需求是否已拆分？
- 是否写全了故事名称、前置条件、发生频率、故事描述和关联需求，且都在项正文的 `字段：值` 行里？
- 是否分析了这个故事的实现会进一步产生的关联需求，并确保它们都有故事覆盖？
- 发生频率是否只写了“高”“中”或“低”？
- 用户是否用姓名，而不是职业或泛称？
- 每个操作是否都落到了一个功能，先后顺序是否清楚？
- 是否覆盖了所有用户可观察到的反馈和变化，并说明这些信息对用户的作用？
- 是否只写到操作发生，没有写用户如何确认结果或后续跟踪？
- 不跟软件交互的环节是否写清楚，并与前后操作衔接？
- 出错时怎么处理、用户怎么得知、操作成功后怎么确认，是否都写了？
- 是否只是用户的典型场景，缺少明确需求或完整操作过程？
- 是否重复了交互、UI 或功能内部的细节？

#### 正例

> 名称：到货入库
> 前置条件：仓库管理员张伟已登录移动端；入库单已创建并处于待收货状态；待收商品与入库单一致。
> 发生频率：高
> 故事描述：张伟需要把本次到货登记入库，让商品可用于后续出库。他打开“入库单管理”，选择待收货的入库单并进入收货（功能：查询入库单）。他用扫码枪逐件扫描商品（功能：收货入库）。遇到无法扫码的破损商品时，他暂停扫码，先在纸质异常单上人工登记，再回到系统使用“登记收货异常”（功能：收货入库）。全部扫完后提交收货（功能：收货入库）。如果扫码商品与入库单不符，系统拒绝该商品并提示原因，张伟核对后重新扫码或登记异常；如果网络中断，已扫明细保留，恢复后继续。提交成功后页面显示“已收货”，入库单状态变为已收货，张伟在库存中看到对应商品数量增加，以此确认操作成功。
> 关联需求：收货后需要查询库存；发现质量问题时需要退货或换货。

#### 反例

**反例 1**

> 故事：仓库管理员张伟完成收货，并导出报表。

一个故事混了两个需求：收货和导出报表。应拆成两个故事，每个故事只满足一项用户需求。

**反例 2**

> 张伟在系统里完成收货。

没有说明用了哪个功能、先做什么后做什么。故事描述里的每一个操作都必须落到一个功能，并按顺序写清。

**反例 3**

> 张伟点击蓝色“提交”按钮，弹窗显示“提交成功”，随后页面跳转。

这是交互细节，属于交互设计。故事只写“张伟提交收货（功能：收货入库）”，不写控件、样式和提示文案。

**反例 4**

> 仓库管理员操作软件完成入库。

没有用姓名，也没有写具体操作和功能。故事必须用用户章节中的姓名，并逐个写出操作对应的功能。

**反例 5**

> 张伟创建入库单并收货，故事结束。

没有错误处理，也没有说明用户如何确认操作成功。扫码不符、网络中断等错误怎么处理、成功后在系统里看到什么，都要写清。

**反例 6**

> 张伟每天先巡库，再用纸质单据核对到货，最后集中补录。

这是用户的典型场景，没有一项明确需求和完整操作过程，应放在用户章节，不是故事。

**反例 7**

> 场景：供应商到货。
> 目标：完成入库。
> 功能序列：查询入库单 → 收货入库。

故事模板只有名称、前置条件、发生频率和故事描述四行；场景、目标、功能序列要写进故事描述，不新增字段。

**反例 8**

> 张伟扫码后提交收货。

遗漏了破损商品先在纸质异常单登记、再回系统登记异常的非软件环节。不跟软件交互的环节也要写清楚，并说明与前后操作的衔接。

**反例 9**

> 发生频率：每天 3 次。

发生频率只写“高”“中”或“低”，不写数字、百分比或其他描述。

### 功能

#### 定位

功能是用户与系统的一次交互，由用户发起或由系统发起，并产生用户可观测的系统变化。

功能不是内部动作。不产生用户可观测变化的动作不是功能，例如用户无法感知的数据库迁移。功能描述必须落实到系统变化，不能把一系列系统变化笼统地视作一个功能。

功能粒度取决于用户能感知到的变化：如果用户只能看到最终产出，最终产出可以是一个功能；如果用户还能看到需求分析、代码开发、测试等中间状态的变化，这些中间状态应分别成为功能。

#### 原则

1. **固定模板，正文不分字段**：每项功能只写一段正文，按名称、发起方、系统变化、前置条件、反馈（仅用户发起）逐行写成 `字段：值`；功能描述写在功能下的「功能描述」子章节里，不重复写进正文。
2. **用户可观测**：每个功能必须产生用户能观察到的系统变化；内部动作、日志、数据库迁移等用户无法感知的变化不是功能。
3. **两种发起方**：功能可以由用户发起，也可以由系统发起；无论谁发起，都必须产生用户可观测的变化。
4. **反馈仅属于用户发起**：反馈是用户操作完成后立即能观察到的信息，具有瞬时性，之后不能复现。系统发起的功能没有反馈；它的结果通过系统变化和后续可查询的状态体现。
5. **一个功能一个可观测变化**：不能把一系列系统变化笼统合并成一个功能；用户能区分的变化应拆成不同功能。
6. **粒度按用户认知**：用户只能感知最终产出时，最终产出可以是一个功能；用户能感知需求分析、代码开发、测试等中间状态时，这些中间状态应分别成为功能。
7. **单一结果**：一个功能只改变一类业务对象或完成一个结果，不把多个系统变化混成一条。
8. **归属一个功能集**：功能只属于一个功能集。
9. **不写边界**：功能不写“不包含什么”；边界在功能集的“边界”中表达。
10. **不写详细规则**：业务规则、结果细节、状态变化明细、数据影响、异常和权限都不写。

#### 写什么

每项功能正文按下面的字段顺序逐行写，每行一个 `字段：值`：

- **名称**：例如“创建入库单”。
- **发起方**：写“用户发起”或“系统发起”。
- **系统变化**：用户能观察到哪个业务对象、什么状态、从什么状态变成什么状态。
- **前置条件**：功能发生前必须成立的条件。
- **反馈（仅用户发起）**：用户操作完成后立即能观察到的信息，具有瞬时性，之后不能复现；系统发起的功能不写反馈。

功能描述写在功能下的「功能描述」子章节里。交互设计和 UI 设计写在各自的子系统树里，不在功能正文或功能子章节里写。

#### 不写什么

- 用户无法观察到变化的内部动作，例如数据库迁移、日志清理、缓存刷新。
- 把一系列系统变化笼统合并成一个功能。
- 给系统发起的功能写反馈，或把后续可查询的状态当作反馈。
- 业务规则、结果细节、状态变化明细、数据影响、异常结果和权限条件。
- 功能边界，例如“不包含扫码和库存增加”。
- 代码、接口、数据库、算法和技术实现。
- 用户肖像本身；只引用用户肖像章节。
- 指标、团队、排期和人力。
- 没有来源的数字或规模。
- 交互步骤、页面、控件和界面细节。

#### 判断标准

- 名称、发起方、系统变化、前置条件是否齐全，且都写在项正文的 `字段：值` 行里？
- 用户发起的功能是否写了反馈？反馈是否是操作完成后立即能观察到、之后不能复现的信息？
- 系统发起的功能是否没有写反馈？
- 功能描述是否写在功能下的「功能描述」子章节里？
- 用户能否观察到功能产生的系统变化？观察不到就不是功能。
- 发起方写的是“用户发起”还是“系统发起”？
- 功能是否只对应一个用户能区分的系统变化？有没有把一系列变化笼统合并？
- 功能粒度是否与用户能感知到的变化一致？
- 变化的对象和状态是否明确？
- 反馈是否具有瞬时性，而不是后续还能查询到的状态？
- 是否展开了业务规则、结果细节、状态变化明细、数据影响、异常或权限？
- 功能正文是否没有写交互步骤、页面或控件？
- 是否误写了功能边界？
- 是否把交互、页面或技术实现写成了功能？

#### 正例

用户发起的功能：

> 名称：创建入库单
> 发起方：用户发起
> 系统变化：新增一张状态为“待收货”的入库单。
> 前置条件：已选择供应商和仓库；商品明细至少一行。
> 反馈：完成后返回新入库单编号和状态“待收货”。

系统发起的功能：

> 名称：取消超时未支付订单
> 发起方：系统发起
> 系统变化：订单状态从“待支付”变为“已取消”。
> 前置条件：订单超过支付时限仍未支付。

系统发起的功能不写反馈；用户之后在订单详情中看到“已取消”，这是可查询的系统状态，不是反馈。

功能描述写在功能下的「功能描述」子章节里。

#### 反例

**反例 1**

> 功能：迁移数据库

如果用户观察不到这个动作带来的变化，它就不是功能，只是内部实现动作。

**反例 2**

> 功能：创建订单、支付、发货

这是多个用户能区分的系统变化，应拆成创建订单、支付、发货等功能，不能笼统合并成一个功能。

**反例 3**

> 功能：开发软件

如果用户只能看到最终的软件产出，可以把最终产出视作一个功能；如果用户还能看到需求分析、代码开发、测试等中间状态的变化，就应该把需求分析、代码开发、测试分别视作功能。

**反例 4**

> 功能：入库单管理

这是功能集，包含创建、查询、修改和删除等多个功能；单个功能集不能当作一个功能。

**反例 5**

> 功能：创建入库单页面有供应商下拉框、商品表格和提交按钮。

这是 UI 描述，不是功能。页面结构属于交互设计或 UI 设计，不是功能正文。

**反例 6**

> 功能：调用 POST /inbound-orders 写入数据库。

这是技术实现，不是需求。接口、存储和调用方式放到设计阶段。

**反例 7**

> 功能：创建入库单时校验供应商存在、商品数量大于 0，失败时提示“供应商无效”。

这些是业务规则和异常提示，需求文档不写；功能只写发起方、系统变化、前置条件和反馈。

**反例 8**

> 边界：不包含扫码和库存增加。

功能不写边界。某个功能不包含什么，通过功能集的“边界”和功能定义本身表达。

### 功能描述

#### 定位

功能描述是功能下的子章节，只写一两句话说明这个功能的作用，不展开业务规则、结果细节、状态变化明细、数据影响、异常和权限。系统变化和反馈分别写在功能正文的其他字段行。

#### 写什么

- 用一两句话说明这个功能做什么、为什么存在。

#### 不写什么

- 业务规则、校验规则、结果细节、状态变化明细、数据影响、异常结果和权限条件。
- 交互步骤、页面、控件、文案和提示；这些属于交互设计。
- 视觉样式、技术实现、用户画像、指标、排期和没有来源的数据。

#### 判断标准

- 是否只用一两句话说明了功能的作用？
- 是否没有展开业务规则、结果细节、状态变化、数据影响、异常和权限？
- 是否与功能项的名称和系统变化一致，没有重复或冲突？

#### 正例

> 让仓库管理员把一次到货登记成可继续收货的入库单。

#### 反例

**反例 1**

> 商品明细至少一行；商品数量大于 0；同一供应商、仓库和单据日期不能重复。

这些是业务规则，需求文档不写业务规则和结果细节。

**反例 2**

> 新增一张状态为“待收货”的入库单，记录创建人和创建时间。

这是系统结果和状态变化明细。系统变化在功能项里用一句话写清，不在功能描述展开。

### 交互设计

交互设计与需求文档的子系统结构同构：子系统 → 功能集 → 功能。层级和名称必须一一对应，但视角不同：需求写系统变化，交互写用户怎样在界面上完成这个变化。

#### 全局约定

跨功能、跨子系统的默认交互规则，只写一次；功能里只写与全局约定不同的部分。

- 反馈与状态：加载、成功、失败、空、确认、撤销的默认呈现和持续时间。
- 错误与恢复：错误提示的位置、文案风格和可恢复操作。
- 文案：按钮、提示、错误和空状态的文案风格和用词。
- 无障碍：键盘、焦点、读屏和触控的基线要求。

#### 子系统

标题必须与需求文档中的软件名称完全一致。正文写交互概述（可选）。子系统包含：

- 信息架构：导航层级、区域划分、页面之间的关系。
- 页面清单（列表）：每项写
  `页面：登录页`、`区域：认证`、`入口：启动页`、`主要跳转：首页、找回密码`、`支撑功能：登录、找回密码`。
- 功能集：标题必须与需求文档中的功能集名称一致。

页面清单是这个子系统的唯一页面来源。功能里的页面结构只能引用清单中的页面，不能创造新的页面名。

#### 功能集

标题必须与需求文档中的功能集名称一致。正文写交互上下文：

- 共享页面和区域；
- 统一入口；
- 共同状态和反馈；
- 跨功能的连续操作。

不要把功能集写成功能列表或概念清单；功能是它的子项。

#### 功能

标题必须与需求文档中的功能名称一致。正文写：

- 发起方：用户 / 系统。
- 触发：什么操作或条件触发。
- 入口：用户从哪里进入；系统发起的功能写用户在哪里看到结果。
- 观察点：系统发起时，用户在哪个页面或区域观察到结果。

功能下的子章节：

- 页面结构：涉及哪些页面或区域、层级和跳转；页面名称来自页面清单。
- 操作（列表）：每项写 `操作：...`、`控件：...`、`结果：...`。
- 反馈与状态：加载、成功、失败、空、确认、撤销和错误提示的具体表现；与全局约定不同的地方写清楚。
- 文案：按钮、提示和错误文案的关键内容。
- 无障碍：键盘、焦点、读屏和触控在这个功能里的具体要求。

#### 不写什么

- 业务规则、系统结果、状态变化明细、数据影响、异常结果和权限。
- 视觉样式、颜色、字体、间距、圆角、图标、图片和设计 token；这些属于 UI 设计。
- 技术实现、接口、数据库和算法。
- 用户肖像、指标、团队、排期和人力。
- 重复需求文档里的系统变化和前置条件。

#### 判断标准

- 每个需求子系统的软件名称、每个功能集名称、每个功能名称都在交互设计里有对应节点，名称完全一致。
- 每个子系统有信息架构和页面清单；每个页面有区域、入口、跳转和支撑功能。
- 每个功能集有交互上下文。
- 每个用户发起的功能有触发、入口和操作；每个系统发起的功能有触发条件和观察点。
- 每个功能都有页面结构、反馈与状态、文案和无障碍。
- 页面结构引用的页面都在页面清单里，没有未定义页面。
- 交互设计与功能、故事和反馈一致，不重复需求内容，也不写视觉或技术实现。

### UI设计

UI 设计与交互设计使用同一套子系统划分和页面清单。交互设计回答用户怎么操作，UI 设计回答页面长什么样。

#### 全局视觉规范

跨子系统的默认视觉规则：

- 色彩：主色、辅助色、语义色、背景和文字色。
- 字体与排版：字体、字号、行高和字重层级。
- 间距与圆角：间距刻度、圆角、边框和阴影。
- 图标与图片：图标风格、尺寸、图片比例和裁切规则。
- 动效：过渡时长、缓动和触发条件。
- 布局栅格与响应式：栅格、断点和适配规则。

子系统有差异时，在子系统的「视觉差异」里写差异，不重复全局规范。

#### 子系统

标题必须与需求文档中的软件名称一致。子系统包含：

- 视觉差异：与全局视觉规范不同的部分（可选）。
- 组件规范：跨页面复用的组件。每个组件写用途、结构、状态和规格。
- 页面：标题必须与交互设计的页面清单一致。

#### 页面

每个页面写：

- 关联功能（列表）：这个页面支撑的功能名称，必须能在交互设计里找到。
- 布局：区域划分、主要内容与操作区的位置。
- 信息层级：视觉优先级和信息组织。
- 组件（列表）：每项写 `组件：...`、`位置：...`、`状态：...`；复用组件必须来自组件规范。
- 状态（列表）：每项写 `状态：...`、`表现：...`，覆盖默认、加载、空、错误和成功。
- 设计稿（列表）：每项写 `状态：...`、`图片：...`、`说明：...`。

设计稿的图片使用 Markdown 图片引用，例如：

```text
状态：默认
图片：![订单列表-默认](/api/v1/projects/{project}/assets/{asset_id})
说明：列表项展示订单摘要
```

图片规则：

- 每个页面至少有默认状态的设计稿；有关键状态时补对应设计稿。
- 图片引用必须指向真实可访问的资产，不能写不存在的链接。
- 图片必须有 alt 文本；图片不能是唯一的信息载体，关键信息仍要写在正文里。
- 颜色、字体、间距等通用数值放到全局视觉规范或组件规范，不在每个页面重复。

#### 不写什么

- 业务规则、系统结果、状态变化明细和权限。
- 用户操作步骤、交互流程、页面跳转和控件行为；这些属于交互设计。
- 技术实现、接口、数据库和前端框架。
- 指标、团队、排期和人力。
- 重复全局视觉规范或组件规范里已经写过的内容。

#### 判断标准

- 每个交互设计子系统的页面清单都在 UI 设计中有对应子系统，页面名称完全一致。
- 每个页面有关联功能、布局、信息层级、组件、状态和设计稿。
- 每个页面至少有一张默认状态设计稿；图片引用可访问且有 alt 文本。
- 组件引用与组件规范一致。
- UI 设计与交互设计的页面、控件和状态一致，不混入操作流程或业务规则。
