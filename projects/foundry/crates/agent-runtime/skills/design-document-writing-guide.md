# 详细设计说明书

## 目录结构

```text
详细设计
├─ 设计概览
├─ 子系统（多项，标题 = 软件名称）
│  ├─ 设计约束
│  └─ 模块（多项，标题 = 模块名称）
│     ├─ 职责
│     ├─ 接口
│     ├─ 数据
│     ├─ 错误处理
│     ├─ 依赖（列表）
│     ├─ 配置
│     ├─ 实现约束
│     └─ 测试要点（列表）
├─ 任务分解（多项，标题 = 任务名称）
│  ├─ 关联模块
│  ├─ 交付物
│  ├─ 依赖
│  └─ 验收条件
└─ 质量门禁
```

## 定位

详细设计回答“每个模块怎么做”，架构设计回答“系统由哪些组件组成、为什么”。详细设计不重新划分架构边界，不写代码，也不重复需求。

## 各项写什么

### 设计概览

用一段话说明详细设计的范围、模块划分原则和实现顺序。不要罗列全部模块。

### 子系统

标题必须与需求文档和架构设计中的软件名称一致。只写该子系统的设计约束：技术栈、运行环境、必须遵守的架构决策、不能改变的接口。

### 模块

标题是模块名称。模块是代码组织和交付的单位，通常对应一个包、服务或一组内聚文件。

- **职责**：这个模块负责什么、不负责什么。职责必须内聚，不能是“处理所有业务”。
- **接口**：对外暴露的入口，包括函数/命令/API/消息的签名、输入输出、错误、幂等性和版本兼容性。不要只写“见接口文档”。
- **数据**：模块拥有或读取的数据、数据所有权、一致性要求和迁移方式。不要写数据库表结构或 ORM 代码。
- **错误处理**：可预期的错误、错误分类、重试/降级/回滚策略，以及不能吞掉的错误。
- **依赖（列表）**：每个依赖写清依赖对象、用途和失败影响；不要列无关库。
- **配置**：必须由外部提供的配置、默认值、敏感项来源和校验方式。
- **实现约束**：语言/框架约束、并发模型、性能边界、安全要求、必须复用的现有能力。
- **测试要点（列表）**：这个模块必须验证的行为、边界和失败路径，供测试计划引用。

### 任务分解

任务是可以独立交付和验收的工作项，不是模块的重复列表。

- **关联模块**：这个任务改哪个模块。
- **交付物**：代码、迁移、配置、文档或证据。
- **依赖**：前置任务或外部条件。
- **验收条件**：可验证的完成条件，必须能对应到需求、架构约束或测试用例。

### 质量门禁

列出进入开发前必须满足的条件，例如接口兼容性确认、数据迁移方案、性能预算、安全评审、测试计划就绪。

## 原则

1. 详细设计只展开架构已经确定的组件，不重新定义系统边界。
2. 每个模块必须有明确的职责、接口、数据、错误处理和测试要点。
3. 接口必须写清输入、输出、错误、幂等性和兼容性。
4. 数据必须写清所有权和一致性；不要写表结构和 ORM 代码。
5. 任务分解必须能映射到模块和验收条件，不能是“继续开发”这类空任务。
6. 不复述需求和架构；引用名称即可。
7. 不写代码、伪代码或具体实现细节到无法评审的程度。

## 判断标准

- 架构设计中的每个组件是否都有对应模块或明确的“不单独成模块”的理由？
- 需求中的每个功能是否至少被一个模块承接？
- 每个模块是否写清职责、接口、数据、错误处理、依赖、配置和测试要点？
- 每个接口是否可调用、可测试、可兼容？
- 每个任务是否有交付物和可验证的验收条件？
- 是否与需求、架构和项目约束矛盾？
