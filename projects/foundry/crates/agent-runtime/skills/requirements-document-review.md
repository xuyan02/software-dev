# 需求文档审查技能

## 目标

审查需求文档是否完整、一致、闭环、可实现、操作成本合理。审查不能只逐字段对照，必须重建覆盖矩阵，沿着目标、领域模型、用户肖像、故事、功能、功能集、子系统走通，找出断链、遗漏、矛盾和不合理设计。

本技能只审查需求分析内容，不审查交互设计和 UI 设计，不修改文档，不审批或发布。

## 审查前必须读取

每一轮开始前重新读取，不依赖上一轮记忆：

1. `task_links_list`：找到当前任务的 Issue。
2. `issue_get`：读取 Issue 标题、正文和全部评论。
3. `project_get`：读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"`：读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"`：读取需求文档全文。
6. `document`，`action = "toc"`，`kind = "requirements"`：读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"`：读取已有批注，避免重复。
8. `task_allowed_operations`：确认当前任务允许哪些操作。

内容规则以《需求文档写作说明书》为准；分析方法以《需求分析技能》为准。

## 审查方法：先重建覆盖矩阵

不要从章节顺序开始挑字段。先重建矩阵：

```text
项目目标 G
  → 用户肖像 U
    → 需求 N
      → 故事 S
        → 功能 F
          → 功能集 FS
            → 子系统 SS

领域模型 C
前置条件 P
关联需求 RN
```

然后做正向和反向检查。

## 完整性审查

以下每一项都是阻塞问题。

### 1. 目标与需求链路

- 每个项目目标是否至少有一条“目标 → 用户需求 → 故事 → 功能 → 功能集 → 子系统”的完整链路？
- 每个目标是否落到了具体用户需求和故事，而不是只停在项目文档？
- 每个非目标是否没有被故事、功能或功能集实现？
- 每个约束是否没有被违反？

目标没有落到用户需求或故事，是阻塞问题。

### 2. 用户肖像与需求覆盖

- 每个用户肖像是否至少有一个需求？
- 每个需求是否至少有一个故事？
- 是否有故事使用了未定义的用户？
- 是否有需求找不到归属用户？
- 是否有新需求属于未发现的用户，但没有创建用户肖像？
- 是否有完全相同的用户被重复拆成多项？
- 是否有需求差异会影响软件设计的用户被合并成一项？
- 是否出现“所有用户”“普通用户”这类无法定位的泛称？
- 用户画像、职业、典型场景和故事是否矛盾？

### 3. 故事、前置条件和关联需求

对每个故事：

- 是否只满足一个用户需求？
- 是否用具体用户姓名，而不是职业或泛称？
- 每个操作是否落到一个功能，或明确是不跟软件交互的环节？
- 是否覆盖所有用户可观察到的反馈和变化，并说明这些信息对用户的作用？
- 错误是否写清：发生什么、怎么处理、用户怎么得知？
- 成功是否写清：用户怎么确认？
- 是否混入交互步骤、页面、控件、文案、业务规则或技术实现？

前置条件：

- 每个前置条件是否有来源，不是凭空成立？
- 前置条件由系统或外部保证的，是否记录为假设、约束或外部依赖？
- 前置条件需要用户完成动作或能力时，是否产生了新需求？
  - 例如“已登录”是否产生了“注册”“登录”需求？
  - “已有账户”是否产生了“创建账户”“找回密码”等需求？
- 这些新需求是否都有归属用户和故事？
- 超出项目范围的前置条件，是否明确记录为非目标、约束或假设，而不是无限展开？

关联需求：

- 每个故事的「关联需求」是否已分析？
- 每个关联需求是否都有故事覆盖？
- 关联需求产生的故事，是否又产生新的关联需求？
- 新关联需求是否都有归属用户？没有则是否创建了用户肖像？

任何一个关联需求没有故事覆盖，或前置条件需要用户动作但没有对应需求，都是阻塞问题。

### 4. 领域模型

- 每项是否是用户能感知的概念类，而不是功能、页面、动作或技术实体？
- 是否是名词或名词性短语？
- 属性是否用户可感知、对满足用户需求有用？
- 是否混入了 `id`、`created_at`、`status_code` 等技术字段？
- 独立概念是否分别建模？
- 同一动作产生、不能独立管理的从属概念，是否归入主概念？
- 是否有重复概念、同义词或同名异义？
- 概念名称和属性是否与故事、功能一致？

### 5. 功能

- 是否由用户发起或系统发起？
- 是否产生用户可观测的系统变化？用户无法观察的内部动作不是功能。
- 是否只对应一个用户能区分的系统变化？有没有把一系列变化笼统合并？
- 功能粒度是否与用户能感知到的变化一致？
- 用户发起的功能是否有瞬时反馈？反馈是否是操作完成后立即观察、之后不能复现的信息？
- 系统发起的功能是否没有写反馈？
- 是否把后续可查询的状态当作反馈？
- 是否被至少一个故事覆盖？没有故事覆盖是阻塞问题。
- 系统发起的功能是否通过观察或受益该结果的用户故事覆盖？
- 是否属于一个功能集和一个子系统？
- 是否有重复功能：同一对象、同一变化出现多次？
- 功能名称是否与故事中的操作一致？
- 是否写了交互、页面、控件、边界、业务规则、结果细节、状态明细、数据影响、异常或权限？

### 6. 功能集

- 是否围绕一个独立概念？
- 是否混入了独立概念的功能？
- 是否把同一动作产生、不能独立管理的从属概念错误拆出去？
- 功能是否只作为子项，正文没有罗列或展开？
- 边界是否写清哪些独立概念不属于本功能集？
- 对功能集服务的需求和故事，所需操作是否齐全？
  - 不是要求每个功能集都有完整 CRUD。
  - 而是故事需要的操作必须存在。例如故事要求创建后还能查到，就不能只有创建没有查询。
- 是否与相邻功能集职责重叠？
- 是否被某个子系统需要，但没有归属子系统？

### 7. 子系统

- 是否是用户可感知的软件或入口，例如 Web 端、移动端？
- 是否由多个功能集组成？
- 功能集是否共同完成至少一个端到端目标？
- 覆盖用户是否写职业，而不是具体姓名？
- 与其他子系统的关系是否写清；没有时是否写“无”？
- 边界是否清楚，是否与功能集和关系矛盾？
- 是否有功能集悬空？
- 是否有子系统缺少关键功能集？
- 是否把业务领域（库存、采购）或技术服务当成子系统？

### 8. 一致性与可实现性

- 同一用户、概念、功能、功能集、子系统在不同章节中的名称是否一致？
- 故事中的功能名称是否都能在功能章节找到？
- 功能集中的边界是否与功能列表一致？
- 子系统边界是否与功能集列表一致？
- 每个功能是否具体、可验证、可实现？
- 是否把技术方案、接口、数据模型写进需求？
- 是否违反项目约束或没有记录外部依赖？

## 逻辑推演

### 场景推演

把每个故事当成一次真实操作，从头走到尾：

1. 前置条件是否足够让故事开始？
2. 每一步需要的数据是否已经存在？
3. 每个操作是否落到一个功能？
4. 不跟软件交互的环节是否衔接？
5. 出错时用户怎么知道、怎么恢复？
6. 成功后用户怎么确认？
7. 正常路径是否有不必要的步骤、交接或确认？

### 状态推演

对每个业务对象：

- 它有哪些状态？
- 每个状态由哪个功能创建、查询、修改或迁移？
- 用户能否从当前状态到达目标状态？
- 是否有状态只能进入、不能离开？
- 是否有状态没有功能覆盖？

### 矛盾检测

- 用户画像与故事是否矛盾？
- 前置条件与故事是否矛盾？
- 故事与功能是否对不上？
- 功能与功能集边界是否矛盾？
- 功能集与子系统边界是否矛盾？
- 目标与非目标是否矛盾？
- 约束与功能是否矛盾？
- 反馈与成功确认是否矛盾？

### 成本推演

对每个故事计数（只用于审查，不写进文档）：

- 用户操作次数；
- 手工录入次数；
- 人工核对或交接次数；
- 确认或审批次数；
- 上下文切换次数；
- 出错后需要重做的步骤数。

问：

- 这一步是否推进目标？不推进就删。
- 这个数据系统是否已经有了？有就不该再问用户。
- 这个确认或交接是否改变目标？不改变就是成本。
- 高频故事能否批量处理？
- 出错后是否必须从头再来？

## 审查输出

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：用 `toc` 得到的章节锚点。
- `quote`：引用原文。
- `body`：具体缺陷 + 违反的规则 + 具体修改建议 + 通过条件。

每条批注只写一个问题，不写个人偏好或等价写法。

## 标注与决策

**阻塞问题**：

- 项目目标到用户需求、故事、功能、功能集、子系统的链路断裂。
- 用户需求没有故事，或关联需求没有故事。
- 前置条件需要用户动作，但没有对应需求。
- 功能没有故事覆盖，或系统发起的功能没有观察/受益故事。
- 功能不可观测、把多个变化笼统合并，或反馈不符合瞬时性规则。
- 功能集混入独立概念，或错误拆出从属概念。
- 功能集对所服务故事缺少必要操作。
- 子系统不是用户可感知的软件，或功能集没有闭环。
- 违反非目标或约束。
- 功能不可实现或不可验证。
- 需求文档与项目文档、Issue 或自身章节矛盾。

**不要写非阻塞标注**：

- 不改变结论的表述问题、可选补充、位置调整、个人偏好、等价写法，都不要写标注。
- 不值得拒绝的问题不要标注；标注本身就是拒绝理由。
- 风格和语言问题留给文风审查，不在本技能中重复。

## 审查收敛规则

1. **只提必须修改的问题**：每条标注必须写清通过条件；写不出通过条件的不写标注。
2. **不重复**：已解决的问题不得再提；同一问题只保留一条批注。
3. **不写建议性标注**：个人偏好、等价写法、可选润色、可以做得更好，都不标注。
4. **多轮收敛**：第一次拒绝后，下一轮只检查上次标注项是否解决，不新增非阻塞要求。
5. **人类决策项**：只能由人类或外部决定的问题，写明决策项和决策人，交给人工评审，不反复拒绝。
6. **决策一致**：只要写了标注，就必须拒绝；一条标注都没写才通过。

## 审查流程

1. 读取输入，重建目标、领域模型、用户肖像、需求、故事、功能、功能集、子系统的覆盖矩阵。
2. 检查目标与需求链路、用户需求覆盖、关联需求覆盖。
3. 检查每个故事的前置条件和可观测变化。
4. 检查领域模型、功能、功能集、子系统。
5. 做场景、状态、矛盾、成本和可实现性推演。
6. 汇总必须修改的问题；不值得拒绝的不写标注。
7. 用锚点写批注；每条写清缺陷、规则、建议和通过条件。
8. 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `rejected` 操作名。
9. 一条标注都没写时，才调用 `task_operation`，`operation` 使用 `task_allowed_operations` 返回的 `approved` 操作名。
10. 不修改文档，不审批，不发布。

## 审查质量门槛

- [ ] 覆盖矩阵完整，没有未解释的断链。
- [ ] 每个用户需求都检查了故事覆盖。
- [ ] 每个故事的关联需求都检查了故事覆盖。
- [ ] 每个前置条件都检查了来源和是否需要新需求。
- [ ] 每个功能都检查了可观测性、粒度、发起方、反馈和故事覆盖。
- [ ] 每个功能集都检查了独立概念、边界和按故事闭环。
- [ ] 每个子系统都检查了用户可感知性和功能集闭环。
- [ ] 每个故事都做过场景推演。
- [ ] 每个业务对象都做过状态推演。
- [ ] 每条标注都能指出具体矛盾、缺口或不合理成本。
- [ ] 每条批注都有锚点、原文、缺陷、规则依据、修改建议和通过条件。
- [ ] 没有重复批注，没有纯风格、个人偏好或建议性标注。
- [ ] 结论与标注一致：写了标注就拒绝，没有标注才通过。

## 常见审查错误

- 只核对字段是否存在，不检查内容是否讲得通。
- 只看单个章节，不做跨章节对照。
- 不回到项目目标和用户需求，导致局部合理、整体断链。
- 不检查关联需求是否都有故事覆盖。
- 不检查前置条件是否产生新需求。
- 不推演故事，漏掉错误处理和成功确认问题。
- 不推演状态，漏掉无法修改、无法迁移或无法离开的状态。
- 不检查功能集是否混入独立概念，或错误拆出从属概念。
- 要求功能集覆盖完整 CRUD，而不是按所属故事判断闭环。
- 不检查系统发起的功能是否通过观察/受益故事覆盖。
- 把系统发起的功能硬写反馈，或把后续可查询状态当反馈。
- 把操作成本问题当成实现细节而放过。
- 报风格、措辞和个人偏好，淹没真正的问题。
- 有标注时仍然通过。
