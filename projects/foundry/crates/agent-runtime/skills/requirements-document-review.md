# 需求文档审查技能

## 目标

审查需求文档是否完整、一致、闭环、可实现、操作成本合理。审查不能只逐字段对照，必须做逻辑推演：沿着目标、用户、故事、功能、功能集、子系统走通，找出矛盾、遗漏和不合理设计。

本技能只审查需求分析内容，不审查交互设计和 UI 设计，不修改文档，不审批或发布。

## 审查前必须读取

每一轮开始前重新读取，不依赖上一轮记忆：

1. `task_links_list`：找到当前任务的 Issue。
2. `issue_get`：读取 Issue 标题、正文和全部评论。
3. `project_get`：读取项目名称和描述。
4. `document`，`action = "content"`，`kind = "project"`：读取项目文档。
5. `document`，`action = "content"`，`kind = "requirements"`：读取需求文档全文。
6. `document`，`action = "toc"`，`kind = "requirements"`：读取目录和锚点。
7. `document`，`action = "annotations_list"`，`kind = "requirements"`：读取已有批注，避免重复。
8. `task_allowed_operations`：确认当前任务允许哪些操作。

内容规则以《需求文档写作说明书》为准；分析方法以《需求分析技能》为准。

## 审查方法：先推演，再判断

逐项检查字段只能发现“缺项”，发现不了“讲不通”。必须同时做以下推演。

### 1. 正向推演

从项目目标开始：

```text
项目目标 → 用户诉求 → 故事 → 功能 → 功能集 → 子系统
```

每一步问：

- 这个目标由哪个用户诉求承接？
- 这个诉求由哪个故事完成？
- 这个故事用到了哪些功能？
- 这些功能由哪个功能集承载？
- 这个功能集属于哪个子系统？
- 这条链路上有没有断点或多余环节？

### 2. 反向推演

从每个用户、故事、功能、功能集、子系统往回问：

- 这个用户为什么存在？他满足哪个目标或诉求？
- 这个功能为什么存在？哪个故事需要它？
- 这个功能集满足哪个用户需求？为什么单个功能不够？
- 这个子系统完成哪个端到端目标？为什么需要多个功能集？
- 如果找不到上游理由，它就是孤立项或多余项。

### 3. 场景推演

把每个故事当成一次真实操作，从头走到尾：

1. 前置条件是否足够让故事开始？
2. 用户是否知道自己要做什么？
3. 每一步需要的数据是否已经存在，还是要重新录入？
4. 每个操作是否落到了一个功能？
5. 不跟软件交互的环节是否写清楚，衔接是否成立？
6. 出错时用户怎么知道、怎么恢复？
7. 成功后用户怎么确认？
8. 正常路径是否有不必要的步骤、交接或确认？

### 4. 状态与生命周期推演

对每个业务对象问：

- 它有哪些状态？
- 每个状态由哪个功能创建、查询、修改或迁移？
- 用户能否从当前状态到达目标状态？
- 是否有状态只能进入、不能离开，或只能查看、不能处理？
- 是否有状态没有功能覆盖？
- 删除或归档是否必要且安全？

### 5. 反例与边界推演

对每个故事和功能问：

- 数据缺失、无效、重复时怎么办？
- 网络中断、外部系统失败时怎么办？
- 跨子系统交接失败时怎么办？
- 多个用户同时处理同一对象时怎么办？
- 高频执行时是否会产生额外人工步骤？
- 低频但关键的场景是否有功能覆盖？

### 6. 矛盾检测

把文档中的陈述两两对照，找不能同时成立的情况：

- 用户画像与故事：用户的基本状况、典型场景是否与故事要求矛盾？
- 前置条件与故事：前置条件是否与故事中的操作或结果矛盾？
- 故事与功能：故事描述的操作是否在功能中找不到，或功能名称/变化对不上？
- 功能与功能集：功能是否被用了，但不在故事所属功能集的分界内？
- 功能集与子系统：功能集是否超出子系统边界，或子系统闭环缺少该功能集？
- 目标与非目标：故事或功能是否实现了非目标？
- 约束与设计：功能是否违反项目约束？
- 反馈与成功确认：功能反馈的信息是否足以让用户确认故事成功？
- 频率与操作成本：高频故事是否依赖不必要的纸质登记、人工核对或多重交接？

### 7. 成本推演

对每个故事计数（只用于审查，不写进文档）：

- 用户操作次数；
- 手工录入次数；
- 人工核对或交接次数；
- 确认或审批次数；
- 上下文切换次数；
- 出错后需要重做的步骤数。

问：

- 这一步是否推进目标？不推进就删。
- 这个数据系统是否已经有了？有就不该再问用户。
- 这个确认或交接是否改变目标？不改变就是成本。
- 高频故事能否批量处理？
- 出错后是否必须从头再来？

如果成本高但项目约束要求，记录为约束；否则作为阻塞问题。

### 8. 可实现性推演

对每个功能和功能集问：

- 这个系统变化是否具体、可观察、可验证？
- 是否依赖未定义的能力或外部系统？
- 是否违反项目约束？
- 是否把技术方案、架构或数据模型写成了需求？
- 范围是否过大，或与其他功能/功能集矛盾？
- 是否能用现有功能组合完成，而不需要新增功能？

## 标题检查

- 用户标题是否就是姓名。
- 子系统标题是否就是软件名称。
- 功能集、故事、功能的标题是否就是各自的名称。
- 标题是否与正文中的姓名、软件名称或名称一致。
- 是否出现“用户 1”“功能 2”这类序号标题，或标题与内容不符。

## 主要检查项

### 1. 用户

- 标题是否就是姓名。
- 固定字段是否齐全：姓名、年龄、基本状况、爱好、职业、典型场景、诉求、主次。
- 字段是否写在用户项正文中，每行一个 `字段：值`，而不是拆成子字段或子章节。
- 基本状况和典型场景是否只在与系统有关时写。
- 诉求是否是结果，不是功能或方案。
- 典型场景是否被写成了故事。
- 是否用姓名，不用“所有用户”“普通用户”。
- 是否有孤立用户：没有诉求，或没有故事使用。
- 是否有故事使用了未定义的用户。
- 是否有重复用户，或把多个用户合并成一项。
- 主次是否明确；主要用户是否对应项目目标或核心故事。
- 用户的职业、典型场景和诉求之间是否矛盾。

### 2. 故事

- 标题是否就是故事名称。
- 是否只满足一项用户需求。
- 名称、前置条件、发生频率（高/中/低）、故事描述是否齐全，且都写在项正文的 `字段：值` 行里。
- 故事描述是否用姓名写清具体用户。
- 每个操作是否落到一个功能，顺序是否清楚。
- 不跟软件交互的环节是否写清，并与前后操作衔接。
- 错误是否写清：发生什么、怎么处理、用户怎么得知。
- 成功是否写清：用户怎么确认。
- 是否混入交互步骤、页面、控件、文案、业务规则。
- 频率是否与操作方式矛盾，例如高频却依赖大量人工步骤。
- 是否只是用户的典型场景，没有明确需求和完整操作过程。

### 3. 功能

- 标题是否就是功能名称。
- 名称、功能描述、系统变化、前置条件、反馈是否齐全，且都写在项正文的 `字段：值` 行里。
- 系统变化是否可观察，是否只改变一类业务对象或完成一个结果。
- 是否是最小单位；能否拆成多个各自产生系统变化的功能。
- 是否被至少一个故事使用；如果没被使用，是否有明确理由。
- 功能名称是否与故事中的操作一致。
- 是否有重复功能：同一对象、同一变化出现多次。
- 反馈是否足以让用户确认成功。
- 是否写了交互、页面、控件、边界、业务规则、结果细节、状态明细、数据影响、异常或权限。
- 前置条件是否与故事和功能集分界矛盾。

### 4. 功能集

- 标题是否就是功能集名称。
- 名称、满足的用户需求、覆盖用户（职业）、协作关系、闭环位置、分界是否齐全，且都写在项正文的 `字段：值` 行里。
- 是否包含多个功能；单个功能是否被误当成功能集。
- 功能是否必须协作才能满足该需求，而不是无关功能堆砌。
- 是否覆盖必要生命周期：创建、查询、修改、状态迁移、必要的删除或归档。
- 是否只满足一个用户需求；是否混入多个需求。
- 与相邻功能集是否职责重叠。
- 分界是否与其故事和功能矛盾：是否排除了自己实际使用的能力。
- 是否被某个子系统闭环需要，但没有归属子系统。
- 功能与故事是否只作为子项，没有在正文罗列或展开。

### 5. 子系统

- 标题是否就是软件名称。
- 软件名称、软件形态、覆盖用户（职业）、闭环目标、与其他子系统的关系、边界是否齐全，且都写在项正文的 `字段：值` 行里。
- 是否是用户可感知的软件，而不是业务领域（库存、采购）或技术服务。
- 功能集是否共同完成至少一个端到端目标。
- 覆盖用户是否写职业，而不是具体姓名。
- 与其他子系统的关系是否单独写清；没有时是否写“无”。
- 关系是否与边界矛盾：是否共享了边界中排除的能力。
- 是否有功能集悬空，或子系统缺少关键功能集。
- 同一能力跨子系统时，是否说明主责子系统和差异，是否造成重复定义。

### 6. 闭环与覆盖

- 项目目标 → 用户诉求 → 故事 → 功能 → 功能集 → 子系统是否逐层可达。
- 每个用户诉求是否至少有一个故事。
- 每个故事的操作是否都有功能。
- 每个功能是否至少被一个故事使用，或属于一个功能集。
- 每个功能集是否属于一个子系统，并支撑其闭环。
- 每个子系统是否至少有一个端到端目标。
- 非目标是否没有被实现；约束是否没有被违反。
- 跨子系统交接是否写清输入、输出和负责方。
- 错误分支、非软件环节和边界场景是否遗漏。

### 7. 一致性与可实现性

- 同一用户、功能、功能集、子系统在不同章节中的名称是否一致。
- 状态名称、业务对象名称是否一致。
- 故事中的功能名称是否都能在功能章节找到。
- 功能集中的分界是否与功能列表一致。
- 子系统边界是否与功能集列表一致。
- 每个功能是否具体、可验证、可实现。
- 是否把技术方案、接口、数据模型写进需求。
- 是否违反项目约束或没有记录外部依赖。

## 逻辑推演示例

**矛盾示例**

> 用户：张伟，60 岁，基本状况：不会使用智能手机。
>
> 故事：张伟在移动端扫码收货。

用户能力与故事要求矛盾。要么调整用户画像，要么调整故事的使用形态。

**边界示例**

> 功能集：入库单管理
> 分界：不含库位分配。
>
> 故事：创建入库单后，张伟分配库位。

故事使用了功能集分界排除的能力。要么把功能归入正确的功能集，要么调整分界。

**闭环示例**

> 功能集：入库单管理
> 功能：创建入库单、查询入库单、删除入库单。

缺少修改或状态迁移。用户创建后无法修正错误，生命周期不完整。

**成本示例**

> 发生频率：高
>
> 故事：张伟先在纸质异常单上登记，再回系统录入，最后打电话让主管确认。

高频故事依赖纸质登记、重复录入和人工确认，操作成本不合理。检查是否有必要，或是否可以合并、复用数据、去掉不改变目标的确认。

**反馈示例**

> 功能反馈：返回新入库单编号。
>
> 故事成功确认：张伟看到入库单状态变为“已收货”。

功能反馈不足以确认故事成功。要么补充状态反馈，要么调整成功确认。

**覆盖示例**

> 项目目标：业务人员无需研发介入即可获得可运行应用。
>
> 需求文档：只有管理员创建应用的诉求和故事，没有业务人员。

项目目标没有落到用户诉求和故事，存在覆盖断链。

## 审查输出

### 每条问题的写法

用 `document`，`action = "annotate"`，`kind = "requirements"`：

- `anchor`：用 `toc` 得到的章节锚点。
- `quote`：引用原文。
- `body`：具体缺陷 + 违反的规则 + 具体修改建议 + 通过条件。

每条批注只写一个问题，不写个人偏好或等价写法。

### 标注与决策

**阻塞问题**：

- 目标、用户、故事、功能、功能集、子系统之间存在断链。
- 用户、故事、功能、功能集、子系统之间有矛盾。
- 功能集或子系统没有闭环。
- 缺少关键生命周期、错误处理或成功确认。
- 高频故事存在明显不合理的操作成本。
- 违反非目标或约束。
- 功能不可实现或不可验证。
- 功能集只有单个功能，或明显是无关功能堆砌。

**不要写非阻塞标注**：

- 不改变结论的表述问题、可选补充、位置调整、个人偏好、等价写法，都不要写标注。
- 不值得拒绝的问题不要标注；标注本身就是拒绝理由。
- 风格和语言问题留给文风审查，不在本技能中重复。

## 审查收敛规则

1. **只提必须修改的问题**：每条标注必须写清通过条件；写不出通过条件的不写标注。
2. **不重复**：已解决的问题不得再提；同一问题只保留一条批注。
3. **不写建议性标注**：个人偏好、等价写法、可选润色、可以做得更好，都不标注。
4. **多轮收敛**：第一次拒绝后，下一轮只检查上次标注项是否解决，不新增非阻塞要求。
5. **人类决策项**：只能由人类或外部决定的问题，写明决策项和决策人，交给人工评审，不反复拒绝。
6. **决策一致**：只要写了标注，就必须拒绝；一条标注都没写才通过。

## 审查流程

1. 读取输入，建立目标、用户、故事、功能、功能集、子系统的覆盖矩阵。
2. 逐项检查用户、故事、功能、功能集、子系统。
3. 做正向推演和反向推演，找断链和孤立项。
4. 对每个故事做场景推演，对每个业务对象做生命周期推演。
5. 做反例、边界、矛盾、成本、可实现性推演。
6. 汇总必须修改的问题；不值得拒绝的不写标注。
7. 用锚点写批注；每条写清缺陷、规则、建议和通过条件。
8. 只要写了标注，就调用 `task_allowed_operations`，再调用 `task_operation`，`operation = "rejected"`。
9. 一条标注都没写时，才调用 `task_operation`，`operation = "approved"`。
10. 不修改文档，不审批，不发布。

## 审查质量门槛

- [ ] 覆盖矩阵完整，没有未解释的断链。
- [ ] 每个故事都做过场景推演。
- [ ] 每个业务对象都做过生命周期推演。
- [ ] 每条标注都能指出具体矛盾、缺口或不合理成本。
- [ ] 每条批注都有锚点、原文、缺陷、规则依据、修改建议和通过条件。
- [ ] 没有重复批注，没有纯风格、个人偏好或建议性标注。
- [ ] 结论与标注一致：写了标注就拒绝，没有标注才通过。

## 常见审查错误

- 只核对字段是否存在，不检查内容是否讲得通。
- 只看单个章节，不做跨章节对照。
- 不回到项目目标和用户诉求，导致局部合理、整体断链。
- 不推演故事，漏掉前置条件、错误处理和成功确认问题。
- 不推演状态，漏掉无法修改、无法迁移或无法离开的状态。
- 不检查功能集分界与故事、功能的矛盾。
- 不检查子系统边界与功能集、关系的矛盾。
- 把操作成本问题当成实现细节而放过。
- 报风格、措辞和个人偏好，淹没真正的问题。
- 有标注时仍然通过。
