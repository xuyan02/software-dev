# 代码总结技能

本技能说明 CodeSummary 如何从源码反推设计，以及不同用户提示词下应该执行什么任务。

- ds 命令、qname、对象关系和 staging 见 `design-space` 技能；
- 文档块、写什么、怎么写、正例和反例见 `design-writing` 技能；
- 本技能只讲任务判断、设计反推方法、各任务的具体流程和写权限。

## 1. 先看用户提示词，判断当前任务

每一次 LLM 调用的用户提示词都说明了当前任务。先看用户提示词；当前任务需要的 kind、path 已经渲染在提示词里，LLM 不会收到单独的 Input JSON。不要依赖节点名。

| 用户提示词 | 对应任务 | 输出 |
|---|---|---|
| `总结工作项。当前工作项：kind=file，path=<path>。` | 文件总结 | `{"ok":true}` |
| `总结工作项。当前工作项：kind=directory，path=<path>。` | 目录总结 | `{"ok":true}` |
| `修改工作项。当前工作项：kind=file，path=<path>。Review 未通过。请查看评论列表。` | 文件修改 | `{"ok":true}` |
| `修改工作项。当前工作项：kind=directory，path=<path>。Review 未通过。请查看评论列表。` | 目录修改 | `{"ok":true}` |
| `检查文件 <path> 的本次总结。` | 文件 Review | `{"passed":...,"sections":[...]}` |
| `检查目录 <path> 的本次总结。` | 目录 Review | `{"passed":...,"sections":[...]}` |
| `检查全部已暂存改动。` | 整体 Review | `{"passed":...,"files":[...],"directories":[...]}` |

补充规则：

- 下表中的用户提示词是识别前缀；实际提示词还会包含输出格式等要求，以当前实际提示词为准。
- 总结任务和修改任务使用不同的用户提示词：“总结工作项”是总结，“修改工作项”是修改。
- 修改任务只收到“Review 未通过，请查看评论列表”；Review 的问题正文和 Section 列表不进入修改提示词，必须从 open 评论读取。Review JSON 里的 Section 只用于内部路由。
- `kind` 已经在用户提示词中写明，决定当前是文件还是目录。
- Review 文件/目录的用户提示词会给出具体路径，并明确写“本次总结”；这是 Review，不是修改。
- Review 全部的提示词明确写“全部已暂存改动”；它检查整个已暂存改动，不是单个工作项。
- 如果当前用户提示词不在上表中，按当前系统提示词和更保守的写权限执行；不要自行假设可以修改。
- 当前系统提示词也包含阶段说明；如果与本技能冲突，以当前用户提示词和系统提示词为准，并取更保守的写权限。
- 只执行当前任务对应的流程；其他任务的流程只用于理解前后关系，不要执行它们的写操作。
- 暂存、验证、提交不是本技能的 LLM 任务；只有当前提示词明确要求时才执行，且不要借机写新设计。

## 2. 代码总结的本质

代码总结不是把代码机械翻译成文字。它的目标是从代码反推设计思路，解释代码为什么这样组织，以及未来修改时必须保留哪些设计约束。

机械总结会写：

- 这个类有哪些字段和方法；
- 方法按什么顺序调用；
- 控制流、分支和循环怎样展开；
- 把代码或注释改写成自然语言。

代码总结要写：

- 这个对象存在的目的和定位；
- 它负责什么、不负责什么；
- 它对外保证什么契约和不变量；
- 谁拥有状态，生命周期如何管理；
- 失败、重试、降级和部分失败如何处理；
- 并发、性能和资源约束是什么；
- 它和哪些对象协作，依赖方向是什么；
- 扩展点、变化点和关键权衡是什么；
- 哪些实现机制是高风险要求，必须保留。

设计文档要让后来者不用重读实现，就能判断新代码应该放在哪里、哪些行为不能破坏。

## 3. 从代码反推设计

### 3.1 证据顺序

优先级从高到低：

1. 公共 API、接口、类型和函数签名；
2. 调用方和被调用方；
3. 测试用例和测试数据；
4. 错误类型、错误处理和边界检查；
5. 状态、生命周期和所有权；
6. 并发、缓存、重试、超时和资源限制；
7. 配置、开关和部署约束；
8. 命名、代码结构和注释；
9. 版本历史和变更痕迹（如果工作区可读）。

单个证据不够时，要交叉验证。例如名字暗示“缓存”，但调用方没有任何缓存语义，就不能只凭名字写“负责缓存”。

### 3.2 可以猜测，但不能编造

代码通常不会直接写出设计意图，所以需要合理猜测：

- 猜测是从证据推出最可能的设计，不是凭空发挥；
- 猜测必须能解释现有代码、调用方式和测试；
- 多个设计都说得通时，选择证据最强、约束最少的解释；
- 不要凭空增加需求、外部系统、技术方案或未来功能；
- 代码和推断冲突时，不要把冲突藏起来。

确定的设计写进正文。不确定、证据不足或代码与设计明显冲突的地方，写成文档评论，说明缺什么证据或哪里矛盾。不要把猜测伪装成确定结论。

如果代码明显是权宜实现或缺陷，不要把偶然行为写成设计目标；写出证据支持的最合理设计意图，并用评论说明代码与设计的偏差。

### 3.3 不同对象反推什么

| 对象 | 反推重点 |
|---|---|
| Directory | 整个子树在系统中的位置，放哪类内容，边界在哪里 |
| File | 这个文件承担的职责或放置的顶层类型 |
| Namespace | 这个命名空间代表的模块和模块边界 |
| Class | 定位、职责、非职责、功能、非功能、字段列表、不变量、约束、设计原则、父类/接口/混入、用法、设计要点 |
| Interface | 抽象目的、契约、实现者义务、失败语义和扩展约束 |
| Method / Function | 意图、输入输出契约、前置后置条件、副作用、错误和并发语义 |
| Mixin | 增加的行为、应用前提、组合规则和冲突处理 |

文档块和写作格式以 `design-writing` 技能为准。本技能只决定“设计是什么”，不重复定义每个块怎么写。

## 4. 文件总结

用户提示词是“总结工作项”，其中 `kind = "file"`，`path` 是当前文件。

### 4.1 任务

读当前文件的源码，反推这个文件和文件内代码元素的设计，更新 design-space 对象和文档。

### 4.2 流程

1. 用 `ds source cat <path>` 读取源码；需要时读取调用方、测试和相关文件；
2. 用 `ds show files/<path>` 查看 File 对象、`document` 字段和已有子对象；
3. 找出 `source` 指向当前文件的已有 namespace、class、interface、method、function、part、mixin；
4. 根据源码反推设计：
   - 这个文件放什么功能或顶层类型；
   - 每个类型/函数的职责、边界、契约和关键约束；
   - 对象之间的关系和依赖方向；
5. 创建、更新或删除对象；类型走 Namespace 或父类型，不要挂在 File qname 下；Namespace 对象和文档也要按现有规则更新；
6. 更新 File、Namespace 和除 Part 外代码对象的 `document` 引用；
7. 按 `design-writing` 写文档：
   - File、Namespace 写一个单句；
   - Class、Struct、Enum、Interface、Method、Function、Mixin 的块写成 `document-topic`；
   - 设计要点写反推出的设计，不写代码流水账；
8. 不确定的设计点写成文档评论；
9. 输出 `{"ok":true}`。

### 4.3 注意

- File 文档只描述本文件，不描述整个目录；
- 不要因为文件里有多个类型，就跳过文件级定位；
- 不要只根据目录结构决定 Namespace；
- 不要在总结阶段 `ds add`、`ds commit` 或 `ds push`；
- 不要只在最终回复里输出设计正文。

## 5. 目录总结

用户提示词是“总结工作项”，其中 `kind = "directory"`，`path` 是当前目录。

### 5.1 任务

读当前目录和直属子项，反推这个目录在系统中放什么内容，更新 Directory 对象和它的文档。

### 5.2 流程

1. 用 `ds show files/<path>` 查看 Directory 对象、`document` 字段和子对象；
2. 用 `ds status --porcelain`、`ds source ls` 或源码读取确认直属子项；
3. 根据直属子项反推目录定位：
   - 整个子树放哪类内容；
   - 为什么这些内容放在一起；
   - 目录边界在哪里；
4. 更新 Directory 对象和 `document` 引用；
5. 按 `design-writing` 写一个单句，抽象概括整个子树，不枚举子项；
6. 不确定的目录边界写成文档评论；
7. 输出 `{"ok":true}`。

### 5.3 注意

- 目录文档不是子目录/文件清单；
- 不要为子目录或文件写本该由子工作项处理的文档；
- 不要只写“放代码”这类无法指导判断的内容；
- 不要 `ds add`、`ds commit` 或 `ds push`。

## 6. 文件或目录修改

用户提示词是“修改工作项”，并给出 `kind`、`path`，以及“Review 未通过，请查看评论列表”。提示词不包含 Review 的问题正文或 Section 列表。

### 6.1 任务

处理上一轮 Review 通过评论留在当前工作项文档上的阻塞问题。整体 Review 的失败结果也会按文件/目录拆分后进入对应的修改任务。

### 6.2 流程

1. 根据 `kind` 和 `path` 找到当前工作项相关的文档 Section：
   - 文件：当前 File、该文件内代码对象和相关 Namespace 的 `document:` 指向的 Section；
   - 目录：当前 Directory 的 Section；
   - 用 `ds status --porcelain` 找到本次改动对象，用 `ds show <qname>` 读取 `document:`；
2. 对找到的每个 Section 运行 `ds doc comment list`；
3. 只处理 `open` 评论；
4. 重新读相关源码、调用方和文档，确认评论指出的问题是否真实存在；
5. 找到问题的根因：是设计判断错了、证据不够，还是文档表达错了；
6. 修正对象、关系或文档；
7. 一条评论真正解决后，运行 `ds doc comment resolve`；
8. 如果评论不成立，写一条说明理由的评论并保留原评论，不要假 resolve；
9. 发现新的独立问题时可以新增评论，但不要重复已有评论；
10. 输出 `{"ok":true}`。

### 6.3 文件修改和目录修改的区别

- 文件修改：范围是当前文件及其关联的代码对象；
- 目录修改：范围是当前目录及其目录文档；
- 除非修正关联关系所必需，不要修改与当前工作项无关的对象。

### 6.4 注意

- 不要只改措辞来让评论消失；
- 不要删除被评论的内容来“消除问题”；
- 不要输出 Review 结论，下一轮 Review 才会判断；
- 不要在修改阶段 `ds add`、`ds commit` 或 `ds push`。

## 7. 文件 Review

用户提示词是“检查文件 `<path>` 的本次总结”，并说明需要修改的问题写成 `ds doc comment add`。

### 7.1 任务

检查当前文件的本次总结是否从代码正确反推出了设计。

### 7.2 流程

1. 从提示词取得文件路径；
2. 读取源码、File 对象、文件内代码对象、相关 Namespace 和对应文档；
3. 检查：
   - 文档是否解释设计意图、边界和约束，而不是复述代码；
   - 设计结论是否能从源码、测试或调用方式得到支持；
   - 是否遗漏关键职责、契约、生命周期、失败语义或扩展约束；
   - 是否把偶然实现细节当成设计；
   - 对象类型、关系、qname 和 `document` 引用是否正确；
   - 是否存在凭空编造的设计；
4. 发现必须修改的问题，用 `ds doc comment add` 写到对应 Section；
5. 返回 `{"passed":...,"sections":["<section-qname>", ...]}`；
6. 不要修改对象或文档，不要 resolve 评论。

### 7.3 注意

- 只写阻塞问题，不写建议性或非阻塞评论；
- 不要要求文档机械列出每个字段、方法或分支；
- 代码有缺陷但不影响设计理解时，不作为本阶段问题；
- 没有阻塞问题时才返回 `passed = true`。

## 8. 目录 Review

用户提示词是“检查目录 `<path>` 的本次总结”，并说明需要修改的问题写成 `ds doc comment add`。

### 8.1 任务

检查当前目录的本次总结是否从直属子项正确反推出了目录定位。

### 8.2 流程

1. 从提示词取得目录路径；
2. 读取 Directory 对象、目录文档和直属子项；
3. 检查：
   - 是否抽象概括整个子树，而不是枚举子项；
   - 是否说明了放哪类内容、边界在哪里；
   - 是否与子项的实际用途一致；
   - `document` 引用是否正确；
   - 是否存在凭空编造的目录职责；
4. 发现必须修改的问题，用 `ds doc comment add` 写到对应 Section；
5. 返回 `{"passed":...,"sections":["<section-qname>", ...]}`；
6. 不要修改对象或文档，不要 resolve 评论。

### 8.3 注意

- 目录文档不要求列出子目录和文件；
- 不要把目录文档写成子项的流水账；
- 只写阻塞问题。

## 9. 整体 Review

用户提示词是“检查全部已暂存改动”，并说明需要修改的问题写成 `ds doc comment add`。

### 9.1 任务

检查本次已暂存的全部设计改动是否一致、完整，并且正确反推了设计。

### 9.2 流程

1. 用 `ds status` 查看已暂存改动；
2. 用 `ds diff --staged`、`ds show --staged`、`ds ls --staged`、`ds doc show` 核对；
3. 检查：
   - 对象、关系、文档和源码是否一致；
   - 是否存在机械总结或凭空编造；
   - 跨文件、跨目录的对象关系和文档链接是否完整；
   - 是否有未暂存但应当属于本次改动的对象；
   - 是否存在重复、遗漏或互相矛盾的设计；
4. 对必须修改的问题，用 `ds doc comment add` 写到对应 Section；
5. 返回：
   `{"passed":...,"files":[{"path":"...","sections":[...]}],"directories":[{"path":"...","sections":[...]}]}`
6. 不要修改对象或文档，不要 resolve 评论。

### 9.3 注意

- 整体 Review 的范围是已暂存改动，不是单个工作项；
- 问题要落到具体文件/目录和 Section；
- 只写阻塞问题；
- 本阶段不修改文档；失败结果包含多个文件/目录，不能直接作为一个单工作项修改任务的输入，会按文件/目录拆分后逐个进入修改任务。

## 10. 通用禁止事项和自检

### 10.1 禁止事项

- 不把代码机械翻译成设计文档；
- 不列举字段、方法、分支和调用顺序来冒充设计；
- 不编造代码不支持的需求、技术、外部系统或未来功能；
- 不在 Review 阶段修改对象或文档；
- 不在 Review 阶段 resolve 评论；
- 不在总结、修改、Review 阶段自行 `ds add`、`ds commit` 或 `ds push`；
- 不把 Review 意见写进 JSON 正文或最终回复；
- 不只在最终回复里输出设计文本。

### 10.2 自检

- 当前用户提示词对应的是哪个任务？
- 当前任务允许哪些写操作？
- 文档回答的是“为什么这样设计”，还是只回答“代码做了什么”？
- 读者能否据此判断新代码该不该放进这个对象或目录？
- 是否区分了核心职责和偶然实现细节？
- 所有推断是否有代码、测试或调用方式支持？
- 不确定的地方是否写成了评论，而不是伪装成结论？
- 对象类型、关系、qname 和文档引用是否正确？
- Review 是否只加评论？修改是否只处理 open 评论？
