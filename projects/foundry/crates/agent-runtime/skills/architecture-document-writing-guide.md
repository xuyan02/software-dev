# 架构设计说明书

## 目录结构

```text
架构设计
├─ 架构概览
├─ 系统上下文
├─ 组件
│  └─ 组件（多项）
│     ├─ 职责
│     ├─ 接口（列表）
│     ├─ 依赖（列表）
│     └─ 数据
├─ 接口与契约（列表）
├─ 数据与存储
├─ 部署与运行
├─ 质量属性（列表）
├─ 关键决策（列表）
├─ 技术债（列表）
└─ 风险（列表）
```

## 各项写什么

### 架构概览

写整体架构风格和关键选择：采用什么结构、为什么、主要边界在哪里。不要在这里罗列全部组件，也不写代码。

### 系统上下文

写系统与外部的关系：谁使用系统、系统依赖哪些外部系统、输入和输出是什么、信任边界在哪里。

### 图表

架构文档只在文字无法清楚表达跨组件关系时画图，使用 `document-mermaid`：

- **系统上下文图**：外部参与者、外部系统或信任边界多于一个短列表时画；只画系统和外部，不画内部组件。
- **组件图**：组件不少于三个且依赖关系不是一眼可见时画；节点名称必须与“组件”章节的组件名完全一致，边只表示依赖，不画类、文件、目录或调用细节。
- **部署/运行拓扑图**：运行时单元、环境、网络边界或信任边界无法用文字说清时画；不画部署脚本和具体配置。
- **流程图/状态图/时序图**：只有在跨组件的关键行为本身就是架构决策时才放进架构文档；单个组件的流程或状态迁移写在技术设计文档里。

共同规则：

- 一张图只表达一个主题；组件清单、依赖列表已经清楚时不要重复画图；
- 图前后的正文写边界、约束和决策理由，不要逐句复述图；
- 不画代码目录、类图、技术分层图或装饰图；
- Mermaid 源码不渲染概念引用，术语解释写在正文里。

### 组件

组件是多项章节，每个组件的标题是组件名称，正文下包含：

- **职责**：这个组件负责什么，不负责什么。
- **接口**（列表）：它对外提供或消费的接口，每条写清名称、提供方、消费方和版本。
- **依赖**（列表）：它依赖哪些组件或外部系统。
- **数据**：它拥有或负责哪些数据。

一个组件只承担一组内聚职责；不要按代码目录或技术分层拆组件。

### 接口与契约

每条写清接口或契约的名称、类型、提供方和消费方、版本与兼容性要求。不要只写“见接口文档”。

### 数据与存储

写数据所有权、存储方式、一致性要求和迁移策略。不要写数据库表结构或 ORM 实现。

### 部署与运行

写运行时单元、环境、部署边界、配置和可观测性要求。不要写具体部署脚本。

### 质量属性

每条质量属性写清场景、度量、目标和验证方式。不可度量或没有验证方式的质量属性不写。

### 关键决策

每条决策写清背景、考虑过的选项、结论、后果和影响范围。不可逆决策要说明理由和批准人。

### 技术债

每条写清位置、影响、风险和偿还计划。没有负责人和偿还计划的债务不写。

### 风险

每条写清风险事件、影响、缓解措施和负责人。不要把已发生的问题或普通任务当成风险。

## 原则

1. 架构写决策、边界和约束，不写代码和实现细节。
2. 组件按职责划分，不按代码目录或技术分层划分。
3. 接口和契约必须明确提供方、消费方、版本和兼容性。
4. 质量属性必须可度量、可验证。
5. 关键决策必须写明选项、权衡和后果。
6. 不写 UI 设计、页面和交互细节。
7. 不复述需求文档；只写架构如何支撑需求。
