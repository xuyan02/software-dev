# 项目简报撰写指南

本指南是项目简报的**统一标准**，供 Clarifier、Project Brief Writer、Style Reviewer 和 Content Reviewer 共同使用。相关智能体必须先通过 `load_skill` 加载本技能，再提问、撰写或评审。

## 0. 一句话

项目简报回答：**项目背景和现状是什么、要解决什么问题、要实现什么变化、边界和约束是什么、有什么风险**。它是项目级承诺，不是需求、设计、任务清单，也不是证据台账。

## 1. 写什么、不写什么

**应该写：**

- 项目背景和现状、描述性目标、非目标、约束、风险、术语表。
- 从澄清 Issue 的对话中提炼出的**结论和决策**。未决事项留在 Issue，不进入简报。

**不应该写：**

- **证据、举证过程和论证**：调查记录、访谈/会议记录、谁说过什么、谁没有提供什么、证据是否充分、结论是否被证明、以及“本节是否足以证明……”之类的自评。证据属于 Issue、证据系统或 Artifact；简报只写结论和承诺。
- **个人原话、引文和历史演变过程**：用最终结论代替“某人原话”和“早期定位如何变化”。被推翻或放弃的方向放进 非目标（`non_goals`）（标注“已排除 / 不再采用”），不要写成当前现状。
- 验收标准、验收场景、given / when / then、具体验收步骤——这些属于需求文档与需求分析；简报只写描述性目标。
- **成功指标和任何量化标准**：需求尚未分析，本阶段不能定义指标、基线、目标值、测量方式或统计窗口；这些属于需求分析及后续阶段。
- 具体数据、统计明细、调查数据、客户名单、日志或示例数据。简报不承载原始数据。
- 术语表里塞入基础通用词、自解释词、正文没有使用的词，或需求/设计/任务术语。
- 具体功能需求、用户故事、操作/交互/验收场景——这些属于需求文档与需求分析。
- 架构、模块、接口、技术选型、数据模型——这些属于设计文档与 ADR。
- UI、交互细节、页面布局——这些属于设计阶段。
- 任务拆分、排期、里程碑、人力分配——这些属于路线图与迭代。
- Issue 对话原文、会议纪要、状态汇报。
- 没有依据的答案；不要替创建者“补全”事实。
- 把解决方案伪装成问题，例如“需要一个微服务”。
- 过于笼统或口号化的目标，例如“提升体验”“尽快上线”；改写成具体要发生的变化。

> 判断标准：如果一段内容在解释“我们怎么知道这件事”“谁说过/没说过”“证据够不够”，它就不属于简报。把结论写进简报；把依据和未解决的问题留在 Issue 或证据系统。

## 2. 每个章节写什么、不写什么

### 背景（字段 `problem`，草稿操作 `set_problem`）

**写什么：**

- 现状：现在这件事是怎么做的、由谁做、做到什么程度。
- 需求：为什么需要改变、需要什么样的能力。
- 痛点：现状中具体哪里不行、造成了什么影响。
- 价值：改变之后对用户、团队或业务意味着什么。
- 只写与本系统相关的背景，用结论性陈述。

**不写什么：**

- 目标、决策、方案或技术选型；这些放到对应章节或 非目标（`non_goals`）。
- 与本系统无关的公司历史、组织架构、其他项目或泛泛的行业背景。
- 证据、调查/访谈记录、谁说了什么、谁没有提供什么、证明问题存在的论证。
- 具体数据或统计明细。
- 未决项；留在 Issue，不进入简报。

坏例：需要一个微服务重构；目标是把失败率降到 0.5%（目标和方案混入背景）。  
好例：退款目前只能整单处理，客服需要人工核对金额，用户常因部分商品无法单独退款而重复申请；业务希望退款能按商品拆分处理。

### goals

**写什么：**

- **按重要程度排序，最重要的目标在最前面。**
- **第一条必须是本系统要实现的核心结果**：这个系统存在的根本目的是什么。
- 后续目标是支撑核心结果的次要结果或使能条件，按重要性依次排列。
- **描述性目标**：用文字描述要实现的结果或变化，面向用户或业务，而不是交付物清单。
- 3–7 条；每条描述一个结果或方向，不写量化标准。
- 用最终确定的表述；目标之间不重复。

**不写什么：**

- **只写次要目标而缺少核心目标**：例如只写“多团队使用”“审核环节可配置”“支持公有云模型”，却没有写“业务人员无需研发介入获得可运行应用”，视为目标不完整。
- 解决方案、功能清单、技术选型、架构或实现方式。
- **任何量化标准**：数字、比例、百分比、时限、阈值、基线/目标值、测量方式或验收标准。本简报不定义成功指标；量化标准留到需求分析及后续阶段。目标是描述性的，不是指标。
- 任务拆分、里程碑、排期、人力分配。
- 背景现状或痛点；放进背景章节。
- 证据、引文或论证。
- 与本系统无关的目标。
- 被推翻或放弃的目标；如必须提及，放进 非目标（`non_goals`）。
- 把“上线某系统 / 完成某项目”当作目标；这是交付动作，不是结果。
- 无法判断是否达成的口号；拆成可判断的阶段目标，或留在 Issue 继续澄清。

排序示例：

1. 业务人员无需研发介入，即可从需求描述获得可运行应用；  
2. 应用所有者能自行审阅和验收 AI 生成的应用；  
3. 多个团队可以在同一平台内使用；  
4. 审核环节可以按应用配置，包括零审核。

第 1 条是核心目标；第 2–4 条是支撑它的次要目标。只有第 3、4 条而没有第 1 条，是不合格的。

区分：目标用**描述性文字**写“要发生什么变化”；量化标准和成功指标不属于项目简报，留到需求分析阶段。

### 非目标

紧跟在目标之后。

**写什么：**

- 主要写**容易被错误当成目标**的内容：逐条明确“不做 / 本期不做”，例如容易与核心目标混淆的相近能力、对外承诺或商业模式。
- 讨论过程中已经澄清不做、且容易被重新提出或误解的方向，可以写进去；必要时给一句原因。
- 被推翻或放弃的方向，写成“已排除 / 不再采用”并注明原因。
- 只收需要划清边界的内容，不是穷举所有排除项。

**不写什么：**

- 与本系统无关的排除项。
- 显而易见的非目标。
- 模糊的“相关功能”。
- 把排除项写成当前承诺。
- 长篇证据或论证；一句原因即可。
- 需求、设计或任务拆分细节。

非目标是 `non_goals` 字段，通过 `set_non_goals` 提交。

### constraints

约束是**用户（创建者）明确提出的硬性限制或条件**，不是撰写者推断出来的。

**写什么：**

- 用户明确提出、必须满足的限制：合规、兼容性、期限、技术限制、部署与运维约束、指定的技术路线或采购边界。
- 每条写成可判断的“必须 / 不得 / 仅限”陈述，例如“MVP 仅在公司内部使用，不对外提供产品”。
- 只写与本系统相关的约束。

**不写什么：**

- 用户没有明确提出、只是撰写者推断的约束；未确认的留在 Issue 并向创建者确认。
- 偏好或愿望，例如“希望高性能”“尽量简单”，除非用户明确说成硬性要求。
- 约束的证据、来源、引文或调查过程。
- 具体数据明细。
- 需求、设计、方案或任务拆分细节。
- 目标；它们属于对应章节。
- 与本系统无关的约束。

### risks

风险是**现在还无法解决、需要等到以后解决**的事项。它不是已经解决的问题，也不是当前就能处理的事项。

**写什么：**

- 当前无法解决、必须留到以后解决的事项；说明为什么现在不能解决。
- `description`：未解决项和暂缓原因；
- `probability` / `impact`：如果不解决，可能发生什么；可选，但建议填写；
- `mitigation`：以后如何、何时解决；这是后续处理计划；
- `owner`：以后由谁负责解决。

覆盖交付、质量、安全、运维、外部依赖等。

**不写什么：**

- 已经解决的事项、当前能立即处理的事项，或已经决定不做的方向（放非目标）。
- 只写“进度风险”或泛泛的不确定性。
- 没有后续处理计划或 owner 的风险；如果还不知道怎么解决，不要写成风险，留在 Issue 或先要求给出计划。
- 证据、事故记录或历史案例。
- 把风险写成已经发生的事实。
- 需求或设计细节。

### terms

**写什么：**

- 正文中出现的缩写、行话、内部名称和容易混淆的概念。
- 每条写 `term` 和 `definition`；解释要用读者能理解的语言。

**不写什么：**

- 基础通用词、自解释词。
- 正文没有使用的词。
- 需求/设计/任务术语。
- 同一术语的多种解释或长篇教程。
- 证据或来源说明。

定义必须和正文用法一致；同一术语只出现一次。

## 3. 质量门槛

- 背景只描述现状、需求、痛点和价值，不混入目标、决策、方案或与本系统无关的内容。
- 每个陈述都必须有来源（写作时自行核对），但简报正文**不写来源、引文或举证过程**；无法确认的内容不要写进简报，留在 Issue 或继续澄清。
- 不包含成功指标或任何量化标准。
- 非目标覆盖容易被误认为目标的方向，具体、可判断。
- 第一条目标是系统核心结果并且是简报的重点；关键约束、非目标和风险不被次要细节淹没。
- 约束是用户明确提出的硬性限制，不是推断或偏好。
- 风险是当前无法解决、留到以后解决的事项，且有后续处理计划和 owner；没有计划的不要写成风险。
- 正文中需要解释的术语都在 terms 中，定义与正文用法一致，没有重复或未使用的词。
- 术语一致，无自相矛盾。
- 不包含需求、设计或任务拆分内容。
- 不包含验收标准、原始数据明细或被推翻的旧结论（作为排除项保留的除外）。
- 不包含证据、举证过程、访谈/会议记录、个人原话，或“是否足以证明”之类的论证。

## 4. 写作流程

1. 读取 Issue 全部评论、当前简报和未解决批注。
2. 先列覆盖清单：背景（现状/需求/痛点/价值）、users、goals、非目标、constraints、risks、terms、decisions。
3. 缺少关键信息：在 Issue 提出具体问题，然后 `continue_clarification`。
4. 信息足够：在服务端草稿上逐项填写，每次一个 operation。
5. 逐条处理批注：接受的修改进简报；不接受的也要 resolve，并写明理由。
6. 完成条件：没有未解决批注，且 Issue 中的重点内容已被简报覆盖；提交草稿后调用 `completed`。

## 5. 评审分工

- **所有 Reviewer**：只提必须修改、且能说明具体缺陷和规则依据的问题；个人偏好、等价写法、可选润色不是阻塞项。无法说清具体危害的，不提。
- **Style Reviewer**：只看语言和表达，不判断内容完整性；具体规则见其提示词。
- **Content Reviewer**：按本指南检查规范符合性、与澄清 Issue 的一致性、覆盖与遗漏、重点是否突出，并检查是否混入证据、引文或论证，以及是否出现成功指标或量化标准。
- **人类验收**：最终批准；Agent 不能批准。

## 6. 常见反例

| 反例 | 问题 | 改法 |
|---|---|---|
| “提升用户体验” | 过于笼统 | 描述具体要发生的变化；本阶段不写量化标准 |
| “上线退款微服务” | 把方案当目标 | 写业务结果：退款失败率降到多少 |
| “上线某系统 / Q3 完成开发” | 交付动作不是结果 | 写用户或业务上要发生什么变化 |
| 目标里写“失败率降到 0.5%”“3 个月内完成” | 量化标准混入目标 | 项目简报不定义指标；目标只做描述性表述，量化标准留到需求分析 |
| “实现无人化软件开发”但无法判断是否达成 | 口号不可验收 | 拆成可判断的阶段目标，或留在 Issue 继续澄清 |
| 只写“多团队使用、审核可配置”等次要目标 | 核心目标缺失 | 第一条写本系统的核心结果，再按重要程度列支撑目标 |
| 目标顺序随意 | 看不出优先级 | 按重要程度排序，最重要在前 |
| 把 Issue 评论原文粘进简报 | 没有提炼 | 归纳成问题、目标、非目标、风险等字段 |
| 不写非目标 | 没有边界 | 非目标紧跟目标；明确写出 `non_goals` |
| 非目标写成所有排除项清单或显而易见的事项 | 稀释边界 | 只收容易被误认为目标或讨论中已澄清不做的方向 |
| 把撰写者推断的限制或偏好写成约束 | 约束不是推断 | 只写用户明确提出的硬性限制；未确认的留在 Issue 并向创建者确认 |
| 在约束里写方案、设计或证据 | 混淆章节职责 | 约束只写必须/不得/仅限条件；方案交给设计，证据留在 Issue |
| 风险只有“进度风险” | 不可行动 | 写具体未解决项、暂缓原因、后续处理和 owner |
| 把已解决或当前能处理的事项写成风险 | 风险定义错误 | 只写现在无法解决、以后才处理的事项；已解决的删除 |
| 风险没有后续处理计划或 owner | 无法执行 | 补上以后如何/何时解决和负责人；还不知道的不要写成风险，留在 Issue |
| 关键决策没有在 Issue 中解决却写进简报 | 隐藏未决项 | 留在 Issue，完成前解决，不写进简报 |
| 把验收标准、given / when / then 写进简报 | 属于需求文档 | 删除，只在简报写描述性目标 |
| 粘贴具体数据、统计明细或客户名单 | 简报不承载原始数据 | 删除，数据留在 Issue 或证据系统 |
| 把讨论中被推翻的旧结论写成当前现状 | 容易误导 | 不写；如必须提及，放进非目标标注“已排除 / 不再采用” |
| 在背景里写目标、决策、方案或技术选型 | 混淆章节职责 | 目标放 goals，决策/排除方向放非目标，方案交给设计阶段 |
| 在背景里写与本系统无关的公司历史、组织架构或其他项目 | 偏离本系统 | 删除，只保留与当前系统相关的现状、需求、痛点和价值 |
| 在背景里写调查、访谈、谁没提供数据、证据够不够 | 简报不是证据台账 | 只写结论；依据和未决项留在 Issue 或证据系统 |
| 引用个人原话或描述定位的历史演变 | 属于论证/历史 | 写最终结论；被推翻方向放非目标 |
| 在正文写“本节不足以证明……” | 自评/论证 | 删除；缺依据的结论不要写进简报，继续澄清或留在 Issue |
| 术语表塞入基础词或正文没用的词 | 稀释重点 | 只收需要解释且正文实际使用的术语 |
| 同一术语出现两种解释 | 定义不一致 | 合并为一条，与正文用法对齐 |
