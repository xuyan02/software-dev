# 立项与“机会”讨论记录

- 日期：2026-11-09
- 状态：讨论结论，待统一并入 RFC 0008 / RFC 0017 / RFC 0011 / 术语表 / 领域模型 / 状态机
- 参与：用户 + Claude

## 结论

1. **不单独设计 Opportunity。** 取消“机会”对象、机会列表和机会详情。
2. **项目是唯一容器。** Issue 必须属于项目；没有项目就没有 Issue。
3. **项目增加“评估中”状态**，作为立项前的讨论和决策容器。
4. **所有需要讨论和决策的事项都用 Issue 跟踪。** 证据、分歧、建议都放在 Issue 里。
5. **立项 = 项目从“评估中”转为“进行中”**；Root Task 在批准立项时创建，而不是创建项目时创建。
6. **拒绝、延期、归档保留项目和 Issue**，作为决策记录；不物理删除。
7. **项目列表的“评估中”筛选替代机会列表**；组合视图就是项目列表的一部分。
8. **Issue 在评估中项目内展示决策建议字段**（价值、成本、风险、置信度、建议），但不产生承诺。
9. **跨项目/组合级事项暂不引入新对象**，先作为待决问题；需要时再决定用候选项目、主导项目还是组合项目承载。

## 设计含义

- 项目创建是便宜的；真正的承诺门禁在 ProjectBrief 批准和进入需求阶段之前。
- 项目列表需要“我的项目/全部项目”筛选，避免所有用户创建导致列表失控。

- 智能体创建项目的审批是未来扩展，不影响当前模型。

## ProjectBrief 起草与目标澄清（已确认）

- **默认由 Agent 起草 ProjectBrief 并主导目标澄清。** 包括与创建者讨论、追问意图、补证据、发现矛盾、建议指标、标注假设和开放问题。
- **创建者审批。** Agent 不能批准；创建者是意图的所有者和最终批准人。
- **创建者可以选择自己写。** 此时 Agent 转为按需辅助（审阅、建议指标、找证据、检查完整性）。
- **Agent 起草的产物必须带来源和假设。** 哪些来自创建者、哪些是 Agent 推断、哪些待确认，不能静默填空。
- **Agent 负责把模糊意图变成可验证的目标。** 例如把“提升体验”追问成可度量的指标。
- **Agent 需要上下文访问。** 项目信息、已有 Issue、历史决策和证据；受项目权限约束。
- **Agent 的能力需要定义和评测。** 目标澄清角色需要 AgentDefinition、绑定、提示词和评测；起草质量差时创建者可以接管自己写。
- **ProjectBrief 批准后是基线。** 后续目标/范围变化走 ChangeRequest，不原地修改。

## 澄清阶段同时产出初始需求（已确认）

- **目标澄清的产出不是只有 ProjectBrief，还包括初始需求。** 两者在同一次澄清对话中产生。
- **ProjectBrief**：项目级承诺——为什么做、成功标准、范围、约束、风险。
- **初始需求**：功能级承诺的候选——第一批要交付什么，关联到目标/问题。
- **每条初始需求至少包含**：关联目标、为谁解决什么问题、初步验收场景、优先级、non-goals（可继承项目级）。
- **初始需求是草稿，不是批准后的承诺。** 后续需求分析补全验收场景、holdout、约束、追溯，再走正常批准；简单的可以快速批准，但不能跳过验收。
- **Agent 起草，创建者审阅。** ProjectBrief 由创建者批准；初始需求按需求流程批准。
- **初始需求必须服务目标。** 不能凭空发明与 ProjectBrief 目标无关的需求；有来源的 Issue 要链接。
- **流程影响**：需求发现不再从零开始；澄清阶段给出初始需求，需求发现继续收集外部信号，需求分析负责补全和批准。
- **初始需求的详细结构留到需求阶段统一解释。** 此处只记录“澄清同时产出初始需求”这一结论，不展开字段和形态。

## 需求管理与需求设计的边界（已确认）

- **收集、分诊、需求分析、需求批准**属于需求管理，不是需求设计。
- **需求设计的输入是已经批准的需求。** 未批准的需求不进入设计。
- 需求设计包含：故事设计、操作设计、交互设计、UI 设计。
- 设计输出必须追溯到已批准需求；设计不能静默改变需求。
- 如果设计发现需求有问题，回到需求管理走变更/重新批准，不在设计阶段偷偷改。
- 验收场景和 holdout 在需求批准时确定；设计可以细化行为级场景并补充设计证据，但不能降低验收标准。
- 需求设计的产物是设计包：Story、OperationFlow、InteractionSpec、UISpec/Prototype、DesignReview、DesignEvidence、追溯边。
- 设计有独立评审和门禁；设计负责人批准，Agent 可以起草和检查但不能批准。

## 故事与操作设计（修正）

用户指出：**故事设计和操作设计不能分成两个阶段；操作是在故事中被逐步发现的。**

- 它们是**同一个设计阶段里的两个共同演进的视角**，不是先后两个阶段。
- 故事提出问题：谁、为什么、什么场景；操作在故事推进中被发现：经过哪些步骤、状态、权限、异常。
- 操作会反过来暴露故事缺失的分支、角色和异常；故事随之修订。
- 交互和 UI 同样在这个循环中被逐步发现，不是设计完故事和操作后再开始的独立阶段。
- 产物仍然是 Story、Operation、Interaction、UI，但它们是一个 DesignPackage 的不同视图，不是各自的阶段交付物。
- **评审是对整个 DesignPackage 的一致性评审**，不是先评审故事、再评审操作。
- 评审发现项在同一個设计循环内修订：
  - 故事/操作/交互/UI 问题 → 回到循环修订；
  - 需求问题 → 回到需求管理走变更或重新批准。
- 连续多轮不收敛，说明需求太大、太模糊或缺少领域知识：拆分需求、缩小范围、补充调研或重写需求，而不是继续加阶段。
- 基线是 DesignBaseline（整个设计包），不是 StoryBaseline 和 OperationBaseline 两个独立阶段。
- 上一版“故事阶段 → 操作阶段”的拆分是错误的，已废弃。

## 需求设计三阶段（已确认）

用户确定：**需求设计阶段分为三个阶段，每个阶段审批后才能进入下一步。**

```text
需求设计
  ├─ 阶段 1：需求分析
  ├─ 阶段 2：交互设计
  └─ 阶段 3：UI 设计
```

### 阶段 1：需求分析

- **根据已批准需求撰写故事，明确操作。** 故事和操作在同一个阶段内共同演进：故事推进中发现操作，操作反过来暴露故事缺失的分支和异常。
- **维护用户模型。** 角色、目标、场景、痛点、权限、使用频率、约束、可访问性需求；贯穿三个阶段持续更新。
- 产出：Story、Scenario、Journey、StoryMap、OperationFlow、StateModel、PermissionMatrix、ExceptionPaths、用户模型、追溯边。
- 审批：产品/用户代表评审；通过后进入交互设计。
- 失败：本阶段内修订；需求问题回到需求管理。

### 阶段 2：交互设计

- 输入：已批准的故事和操作、用户模型。
- 内容：每一步的信息流、用户选择、反馈、错误、加载、空状态、成功状态、无障碍、文案；交互原型。
- 产出：InteractionSpec、交互状态图、反馈规则、错误文案、原型、交互评审记录。
- 审批：UX、产品、无障碍、技术、QA 评审；通过后进入 UI 设计。
- 失败：交互问题本阶段修订；故事/操作问题回到阶段 1；需求问题回到需求管理。

### 阶段 3：UI 设计

- 输入：已批准的交互设计、用户模型、设计系统/品牌约束。
- 内容：界面、布局、组件、视觉、设计 token、响应式/自适应、可访问性、资源。
- 产出：UISpec、高保真界面/原型、组件引用、设计 token、UI 评审记录。
- 审批：设计负责人、品牌、前端、无障碍、产品评审；通过后交给架构与实现。
- 失败：UI 问题本阶段修订；交互问题回到阶段 2；故事/操作问题回到阶段 1；需求问题回到需求管理。

### 用户模型

- 是需求设计阶段的持续维护对象，不是一次性文档。
- 包含：用户角色、目标、场景、痛点、权限、频率、约束、心智模型、可访问性需求。
- 三个阶段都要读取和更新；新发现要回写到用户模型。
- 版本化；重大变化需要评审。
- 用户模型不能替代需求；它帮助故事、交互和 UI 保持一致的用户视角。

### 阶段流转与变更

- 每个阶段有评审和基线；审批后才能进入下一阶段。
- 下游发现上游问题，回到对应阶段，不在下游打补丁。
- 需求变更会作废三个阶段的基线，重新进入需求分析。
- 故事/操作变更作废交互和 UI 基线。
- 交互变更作废 UI 基线。
- Agent 可以起草、生成、检查；每个阶段的批准由人负责。

## 需求分析中派生需求的处理（修正）

用户明确：**没有跨项目需求。** 所有 Requirement 都属于一个项目。上一版跨项目需求/依赖 Issue 的设计作废。

- **派生需求属于同一个项目。** 购物需求派生支付、账户管理，如果它们是同一个系统/产品的一部分，就是同一项目内的新需求或子需求。
- **外部系统不是“另一个项目的需求”。** 如果某个能力由外部系统提供，它是当前需求的**外部依赖/约束/假设**，当前项目记录依赖和契约，不创建、不管理其他项目的需求。
- **新系统/新产品不是跨项目需求。** 由人类决定是否新建项目；当前项目把它记录为外部依赖/假设/提案，不把需求转移过去。
- **不存在跨项目需求对象、跨项目依赖 Issue、目标项目承接流程。**

分类：

| 类型 | 例子 | 处理 |
|---|---|---|
| 实现细节 | 内部数据结构、算法 | 进入设计/任务，不算需求 |
| 同项目子需求 | 结算拆成购物车、支付、订单确认 | 同项目内子需求/父子关系 |
| 同项目新需求 | 购物需要地址管理 | 同项目内新建 Issue/Requirement |
| 外部依赖 | 支付由外部系统提供 | 记录为 assumption/constraint/dependency，写清外部系统、负责人、状态、契约 |
| 新系统/新产品 | 需要自建支付平台 | 当前项目记录提案；人类决定是否新建项目；当前项目保留外部依赖 |
| 暂不处理 | 观察到但当前不做 | 建 Issue 标记延期/观察，保留来源 |

流程：

1. 在故事/操作走查中发现派生需求。
2. 分类：实现细节、同项目子需求、同项目新需求、外部依赖、新项目提案、暂不处理。
3. 同项目派生：在当前项目建 Issue/Requirement，建立 `derives_from` / `refines` / `depends_on` 链接。
4. 外部依赖：在当前需求的 assumptions/dependencies 中记录，写清外部系统、负责人、状态、契约；不建跨项目需求。
5. 更新原需求的 scope、assumptions、dependencies。
6. 评审：派生需求是否显式、分类是否正确、链接是否完整、外部依赖是否有状态。
7. 原需求批准门禁：依赖必须“已满足 / 已承诺计划 / 显式接受风险”之一。

规则：

- 派生需求不能静默扩大原需求范围；范围变化要显式批准。
- 同项目派生需求独立走需求和优先级，不自动继承原需求的批准。
- 外部依赖未确认时，原需求只能条件批准或延期，不能当作已完成前提。
- Agent 可以发现、起草、在同项目建草稿；不能创建项目；不能替人接受外部依赖。
- 新系统/新产品由人类决定；当前项目不管理其他项目的需求。

## 需求文档模型（用户确定）

系统为每个项目维护**唯一的“需求文档”**。它是需求分析阶段的结构化真相。

### 结构

```text
RequirementsDocument
  ├─ users（用户模型 / persona）
  └─ functions（功能模块）
       ├─ stories（故事）
       └─ operations（操作）
```

- **用户模型**：把用户细化成想象中的具体的人（姓名、年龄、性别、职业、爱好、习惯、目标、痛点、权限、场景、证据、置信度）。
- **功能模块**：粒度是功能模块，例如“购物”。
- **操作**：粒度是用户的一次不可分割的交互，例如“搜索”。输入关键字、点击搜索按钮属于交互概念，在操作层面不区分。
- **故事**：在一个场景下，用户为实现一个目标所进行的操作的总和。故事归属一个功能模块，引用一个或多个用户模型和一组有序操作。
- 同一个操作可以被多个故事引用；操作归属功能模块，故事是场景化的组合。

### 文档的两种形态

- **对人类**：一份可阅读的需求文档，由结构化数据渲染生成。
- **对 Agent**：结构化数据；Agent 不通过编辑文档文本，而是通过结构化操作修改：
  - `user.add` / `user.update` / `user.remove`
  - `function.add` / `function.update` / `function.remove`
  - `story.add` / `story.update` / `story.remove`
  - `operation.add` / `operation.update` / `operation.remove`
  - `story.set_operations`（设置故事的操作序列）
  - `document.get` / `document.diff` / `document.validate`

### 版本、草案、冲突

- 需求文档有版本号；已发布版本不可变。
- 编辑在草案上进行；草案有 revision 和 base_version。
- 每次结构化操作带 `op_id`、`base_revision`、目标对象和 payload。
- 多 Agent 并发：
  - 不同对象的操作可以顺序应用；
  - 同一对象/字段的并发修改产生冲突；
  - 冲突返回当前状态和 diff，Agent 重新读取、重放或请求人工决策；
  - 不能用 last-write-wins 静默覆盖。
- 操作日志只追加，可审计、可重放。
- 草案评审通过后发布新版本，形成需求基线。
- 可选：热点对象使用 ETag/租约，减少冲突。

### 规则

- 每个项目只有一个需求文档；没有跨项目需求。
- 故事必须引用至少一个用户模型和至少一个操作。
- 操作必须归属一个功能模块；故事引用的操作应属于同一功能模块，跨功能模块的场景用更上层的故事或链接表达。
- 用户模型、功能、故事、操作都有稳定 id；重命名不改 id。
- 文档渲染是投影；结构化数据是真相。
- 人工编辑也走结构化操作，不直接改渲染文本。

## 需求管理（暂不补，Issue 承担未批准需求）

- **不新增专门的需求管理阶段或系统。**
- **未批准的需求、候选、讨论和证据，全部用 Issue 管理。**
- **Requirement 只表示已批准的承诺**；需求设计从已批准的 Requirement 开始。
- Requirement 是否保留 Draft/InReview 状态，等评估 Issue 是否足够后再定；当前不展开。
- 后续评估 Issue 是否足够的标准：
  1. 能否承载问题、用户、验收、non-goals、约束、假设、开放问题；
  2. 能否表达优先级、风险、依赖；
  3. 能否支持分诊、分析、评审、批准前的讨论；
  4. 能否建立追溯：Issue → Requirement → 设计 → 任务 → 测试；
  5. 是否造成语义污染：Issue 是问题空间，Requirement 是承诺空间。
- 如果不够，再补需求管理；如果够，保持现状。
- 需求批准时，从 Issue 形成 Requirement；Requirement 记录承诺，Issue 保留来源和讨论。
