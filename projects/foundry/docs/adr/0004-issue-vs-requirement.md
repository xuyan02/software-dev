# ADR 0004：Issue 是问题空间，Requirement 是承诺空间

- 状态：已接受
- 日期：2026-11-02

## 背景

最初的 Requirement 聚合把“收集反馈”和“承诺要做什么”混在了一起：任何人都能直接创建 Requirement，字段（问题、用户、验收场景、非目标）却按“已想清楚的需求”设计。这带来两个错误：

1. 客户反馈、客服工单、监控告警、内部想法被迫伪装成需求，产生大量低质量草稿。
2. 真正的需求（产品经理做出取舍后形成的契约）失去了稀缺性和权威性。

软件工程里，这两件事发生在不同阶段、由不同角色负责、要求不同质量门槛。它们不应该是同一个对象的两个状态。

## 决策

采用两层模型：

| 层 | 对象 | 回答的问题 | 特征 |
|---|---|---|---|
| 问题空间 | **Issue** | 世界上发生了什么？谁想要什么？哪里需要讨论？ | 便宜、量多、允许模糊、先收集后分类 |
| 承诺空间 | **Requirement** | 我们决定解决什么、不解决什么、怎样算解决？ | 昂贵、量少、可验证、需要批准基线 |

数据流：

```text
客户反馈 / 客服记录 / 监控告警 / 数据分析 / 内部想法
  → Issue（收集 → 讨论 → 处置）
      ├─► 关闭：重复、已回答、不处理
      ├─► Bug：确认的缺陷（Issue kind = bug，修复工作另建 Task）
      ├─► Task：工程事务
      └─► 需求分析 → Requirement（契约）→ Design / Task / Test
```

关键约束：

- Issue 是统一入口。所有“需要讨论的问题”先成为 Issue，不直接成为 Requirement。
- Issue 的分类、严重度、负责人、影响范围在创建时确定；没有独立的分诊步骤。状态从 `Open` 直接进入 `InProgress`、`Resolved`、`Rejected` 或 `Duplicate`。
- Bug 是 Issue 的一种 `kind`，带有环境、影响版本、复现步骤等字段；修复工作通过 Task 和链接表达，不另立一套 Bug 生命周期。
- 关闭 Issue（`Closed`）、拒绝（`Rejected`）、判重（`Duplicate`）是处置决定。默认策略下智能体可以接收、评论、推进和报告已解决，但不能代替人类做最终处置。
- Requirement 从“随手创建”改为“需求分析/设计的产物”。它会通过链接引用驱动它的 Issue，并补充假设、开放问题、非功能需求和变更请求。

## 当前实现范围

本轮先实现 Issue 全链路：领域模型、用例、内存适配器、REST、MCP、Web 控制台、CLI 和迁移。现有 Requirement 代码暂时保留，但不再是首页入口，也暂不扩展；后续按承诺空间重新设计。

## 后果

- 首页从“需求列表”变为工作台，议题收件箱作为主要入口，符合“先收集、再决定”的工作顺序。
- 智能体工具围绕 Issue 扩展（创建、评论、状态推进），与人类共用同一套对象和策略。
- 需要明确 Issue 与 Requirement 的链接关系（`motivated_by` / `addresses`），避免两个对象再次漂移。
- 数据模型多一个聚合和一张讨论表；这是为了让“讨论”和“承诺”各自拥有正确的生命周期和权限。
