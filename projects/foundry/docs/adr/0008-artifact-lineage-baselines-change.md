# ADR 0008：产物血缘、基线与变更是贯穿主线

- 状态：Proposed
- 日期：2026-11-09

## 背景

软件生命周期的阶段很多：需求、架构、设计、实现、测试、发布、运维、退役。如果只定义阶段和工作项状态，系统能回答“现在到哪一步”，但回答不了：

- 改一个需求，影响哪些架构决策、契约、任务、测试和发布？
- 一个发布包含哪些需求和证据？
- 一个事故由哪些变更引起？
- 已批准的内容何时被谁改过？
- 哪些证据已经过期？

现有 `links` 表和 `documents` 表只能做局部关联，无法支撑影响分析、基线和受控变更。

## 决定

用**产物血缘、基线和变更**作为贯穿生命周期的主线：

1. **Artifact 是连接件。** 需求、架构决策、契约、设计、任务、补丁、测试报告、发布记录都是 Artifact；有类型、所有者、状态和不可变版本。
2. **内容与元数据分离。** 长文本、代码在 Git；大证据在对象存储；Postgres 存元数据、状态、索引和内容引用（SHA-256 或 commit + path）。
3. **血缘边有类型。** `derives_from`、`satisfies`、`refines`、`implements`、`verifies`、`depends_on`、`supersedes`、`deploys`、`causes`、`mitigates` 等；边有来源（manual/derived/inferred）和置信度。
4. **影响分析由图驱动。** 上游变化沿实现/验证/依赖边传播，标记下游产物和证据为 stale；门禁拒绝过期证据。
5. **基线不可变。** 基线是某一时刻批准的一组 ArtifactVersion；批准后不可修改，变更产生新基线。
6. **变更受控。** 已批准产物和基线的修改走 ChangeRequest，带影响分析、验证计划、回滚计划和批准；紧急变更可以后补批准，但不能跳过证据。
7. **外部事实只引用。** Commit、PR、CI run、镜像 digest、监控指标只存引用和哈希，不复制内容。

## 备选方案

- **只靠 links 表**：无法表达版本、基线和影响分析。否决。
- **只靠 Git 历史**：无法表达需求、发布、证据和跨仓库关系。否决。
- **引入图数据库作为真相**：查询强，但增加运维和一致性复杂度；先用关系表 + 递归查询，规模扩大再评估。否决当前引入。
- **把血缘做成可编辑的图**：容易产生第二真相；图必须是投影，边通过对象字段或显式动作建立。

## 后果

- 需要从现有 `links`/`documents` 迁移，保留兼容视图。
- 需要递归查询、失效传播、基线 diff 和变更影响分析。
- 证据必须带 Provenance；配置/模型/提示词/工具版本缺失时降级。
- 已批准内容和基线不可原地修改；团队需要适应“变更走 ChangeRequest”的节奏。
- 生命周期阶段、工作项状态和产物血缘三者分离：阶段回答“项目走到哪”，状态回答“对象走到哪”，血缘回答“改动影响什么”。
