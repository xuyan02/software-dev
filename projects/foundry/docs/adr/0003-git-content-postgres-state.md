# ADR 0003：Git 存内容，Postgres 存状态

- 状态：Accepted
- 日期：2026-11-02

## 背景

需求、设计文档、ADR 是长文本，需要 diff、评审、回滚和离线阅读；工单状态、所有权、租约、事件则需要事务、索引和并发控制。用一套存储同时满足两者，通常两边都做不好。

## 决定

- **Git**：Markdown + YAML front matter，一门项目一个仓库。文档变更走分支和合并请求；合并后的 commit 即文档版本。
- **Postgres**：工作项状态、版本号、事件、决策、链接、幂等键、文档元数据镜像。
- **对象存储**：测试报告、截图、trace、SBOM 等大体积证据，按 SHA-256 内容寻址。
- **事件表**：状态变更写入追加式 `events` 表；事件是审计与历史视图的持久记录。

## 一致性规则

1. 文档 front matter 中的 `id` 与 Postgres `documents.id` 一致。
2. Git 合并后，CI 调用 `POST /internal/documents/sync` 更新元数据镜像；失败则重试，Git 始终是内容真相。
3. 工作项引用文档时存 `(path, revision)`，不存可变分支名。
4. 删除文档不删除历史；在元数据中标记 `superseded`。

## 备选方案

- **全部放 Postgres**：diff/评审体验差，且把代码评审和文档评审割裂。
- **全部放 Git**：状态查询、并发控制、租约和审计需要自己造数据库。否决。
- **文档放对象存储**：失去 diff 和合并语义。

## 后果

- 需要维护 Git 与元数据之间的同步，且要能重建索引。
- 人类可以直接用熟悉的工具阅读和评审文档。
- 智能体通过 API 写文档时，实际是在分支上提交，天然留下作者和评审痕迹。
- 当前实现中，聚合保存与事件发布仍是两个端口调用；后续需要把事件写入纳入聚合事务。
