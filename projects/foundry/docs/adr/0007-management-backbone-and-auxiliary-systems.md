# ADR 0007：管理主干与辅助系统分离

- 状态：Proposed
- 日期：2026-11-09

## 背景

完整软件生命周期需要大量智能工作：需求歧义分析、架构方案权衡、代码理解、测试生成、发布风险评估、事故根因分析。这些能力变化快、供应商多、质量参差。把它们写进 Foundry 的领域模型会导致：

- 领域对象被工具细节污染，替换工具就要改领域和数据库；
- 范围无限膨胀，Foundry 变成所有工具的拼装体；
- 工具输出被误当成领域状态或批准，责任边界模糊；
- 无法比较、评测、降级或回退工具能力。

## 决定

Foundry 只做**管理主干**：对象、流程、角色、权限、证据、审计、血缘、基线、变更。

智能工作由**辅助系统**提供，遵守以下规则：

1. 辅助系统以 `AuxiliarySystem` 注册，以 `AuxiliaryCapability` 声明能力；能力有输入/输出 schema、权限、成本、超时、确定性和默认信任等级。
2. 每次调用经过能力网关授权，写入 `ToolInvocation`；无记录的调用不能成为产物或证据。
3. 辅助输出写入 Artifact 或候选证据，不直接修改领域状态；批准仍由策略和授权的人类/Agent 完成。
4. 辅助系统可替换；领域模型只依赖能力 id 和契约，不依赖具体实现。
5. 辅助系统本身要被评测：质量、一致性、成本、延迟、漂移；低质量能力降级或停用。
6. 能力按最小权限授予项目、文件、网络、密钥和工具范围。

## 备选方案

- **全部自研并写进领域模型**：控制力强，但范围膨胀、替换困难、领域污染。否决。
- **完全依赖外部 SaaS**：接入快，但审计、权限、证据和替换性无法保证。否决。
- **只做集成层，不做契约**：实现简单，但无法比较和评测，输出不可追溯。否决。

## 后果

- 需要建设能力网关、调用记录、证据验证和评测机制。
- 需求分析、架构推理、测试 oracle、独立验证等 AI 原生能力优先自研；静态分析、扫描、监控、IaC 等通用能力优先集成。
- 辅助系统的质量成为系统指标的一部分；不能把“工具这么说”当成“事实”。
- 领域模型保持稳定，工具可以替换；但需要维护能力契约和版本兼容。
